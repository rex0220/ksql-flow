## 1. レビューの枠（最重要 — 蒸し返し防止）

本設計書は 4 回のレビュー（v1→v2.0 設計レビュー、v2.1 第三者レビュー、v2.2 設計評価レビュー、v2.5 エンジン申し送り反映）を経ており、**付録 C が裁定済み決定の履歴**である。

* **付録 C に載っている決定事項は、新しい事実（エンジン実装の実挙動・kintone API 仕様など）を根拠にできる場合を除き、再提案しない。** 好み・別解の提示は不要（例: ASSERT / EXIT の分離、ロック二層方式、リポジトリ分離、全面 MIT、ドメイン単位の設計思想などは決着済み）。
* レビュー対象は次の 3 つに**限定**する:
  1. **実装可能性**: 実装指示書 M1〜M7 を書き始めたとき、設計書の記述だけでは決められない・矛盾して手が止まる箇所
  2. **章間の整合**: v2.5 で前提訂正（100 件チャンク等）を入れた際の直し漏れ・数値の不整合
  3. **エッジケースの穴**: 排他 / リラン / ログ再送 / Exit Code 集約など、状態機械としての未定義遷移

## 2. 重点確認項目（この順で）

1. **5.5（排他）× 6 章（リラン）× 8 章（ログ）の状態遷移の網羅性**: RUNNING レコードが残る全パターン（クラッシュ・タイムアウト・ネットワーク断・force-unlock）で、次回実行と `--resume` の挙動が一意に決まるか。
2. **10.3 Exit Code 集約**: すべてのジョブ結果の組み合わせで終了コードが一意か。特に `NO_DATA` と `SKIPPED` の混在、バッチロック失敗と個別ロック失敗の混在。
3. **7.2 API カウント**: 「単一カウンタ・ログ / ロック含む」の規定と、maxApiCalls 超過時の安全停止が、ログ書き込み自身のカウントで矛盾しないか（超過後にログを書くと更に消費する問題）。
4. **as-of（5.3）**: `--resume` の as-of 引き継ぎと `--from` / `--only` の as-of の扱いが定義されているか（--from / --only は新規バッチか、元バッチの継続か）。
5. **9 章 config**: 実装に必要な全キーが揃っているか。`env:` 解決の失敗時挙動、`extends` の継承規則の網羅。
6. **申し送りとの残差**: 申し送りの記述で v2.5 に反映されていない事項がないか（機械的に突合すること）。

## 3. 出力形式

`docs/reviews/spec_review_codex-YYYYMMDD.md` として、指摘を重大度順に:

```
## 指摘 N: <一行要約>
- 重大度: BLOCKER（実装不能・矛盾）/ MAJOR（手戻り誘発）/ MINOR（曖昧・軽微）
- 該当箇所: §x.y（および矛盾相手の §a.b）
- 内容: <欠陥の説明。エッジケースは具体的な事象列で>
- 提案: <最小修正案。設計の別解ではなく、現行設計の欠陥を埋める案>
```

* 指摘ゼロの節は列挙不要。**「問題なし」の網羅的な確認宣言は最後に 1 行**で良い。
* 判断が割れる指摘には「裁定が必要」と明記する。裁定者は Takashi。決定は設計書の付録 C に追記され、以後の再提案対象外になる。
