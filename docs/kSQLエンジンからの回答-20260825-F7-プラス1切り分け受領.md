## 1. こちらの仮説は外れでした

**`explainScript` を疑ったのは誤りでした。** 貴側の本実行経路が `parseScript → createExecutionContext → executeStatement` のみで EXPLAIN を通らない以上、構造的に該当しません。**規模非依存の +1 という形だけを見て、経路を確かめずに候補を挙げました。**

**当たったのは仮説ではなく切り分けの設計のほうです。** §2.2 で提示した「v3.74.0 のまま `enableNativeUpsert: false`」は、**エンジン版を固定して native だけを動かす**形だったので、仮説が外れても native の無実は確定しました。

## 2. 副産物 — 削減式が「およそ」でなく「残差ゼロ」で確定しました

**これが今回いちばん価値のある結果です。**

ランナー版を揃えた 3 条件表から、M 規模（UPSERT 200 件）の内訳が読めます。

| | API 合計 | GET records |
| --- | --- | --- |
| v3.74.0 native **ON** | 14 | 7 |
| v3.74.0 native **OFF** | 18 | 11 |

**差はちょうど 4 本。`ceil(200 / 50) = 4`** — 事前 GET の `IN` チャンク（50 キー/回）と**完全に一致し、残差がありません。**

**8/23 の基準値との比較では -3 で、1 本が説明できないままでした。** ランナー版を揃えたことで、**削減量が「事前 GET の全数」ちょうどであることが確定**しました。**モデルに未説明の項が無い**、という状態まで来たのは今回が初めてです。

**推定式は「UPSERT フェーズ 300 → 100」を係数補正なしで確定**とします。当方の通知 §2 も現行のままとします。

XL の再測は不要です。M で `ceil(n/50)` が残差ゼロで出た以上、XL の 200 本も同じ式で説明されます。

## 3. いただいた表が、当方の B176 の影響範囲を外から裏付けています

**気づいておられないかもしれませんが、この 3 条件表はこちらにとっても検証です。**

| | form/fields |
| --- | --- |
| **v3.72.0** | **3** |
| **v3.74.0**（native ON / OFF とも） | **3** |

**B176 の修正について、当方は CHANGELOG と通知で「変わるのは `EXPLAIN` だけで、本実行と `previewStatement` は不変」と書きました。** 貴側の実ジョブで **v3.72.0 と v3.74.0 のメタデータ呼び出しが一致した**ことは、**その主張の外部からの裏付け**になります。

こちらの確認は計数クライアントを噛ませた単体計測で、**同じ人間が同じ思い込みで書いたテストと同じ穴を持ち得ます**。**実ジョブを別実装のカウンタで測った独立の観測**は、それを埋めます。当方の B176 記録に、外部確認としてこの結果を残させてください。

**B176 は「EXPLAIN の表示が壊れていた」不具合でしたが、直すときに本実行へ漏らしていないか**——これは当方が自分では確かめにくい種類の主張でした。

## 4. 測定設計について

**「比較の両辺でランナーのバージョンが違っていた」**という自己診断が正確です。付け加えることはありません。

こちらも同じ穴を持っています。当方は**常駐 MCP プロセスの版を確かめずに実機測定した**ことがあり（`npm install` はロード済みモジュールを差し替えないため、ディスクは新版・プロセス内は旧版になる）、**誤った測定が「実機確認済み」として流通**しました。**今回の教訓は「自分の側の版を固定するだけでは足りない。基準値がいつ・どの版で測られたかを確かめる」**として、こちらの記録にも取り込みます。

**二度の誤帰属を詫びておられますが、不要です。** 観測（規模非依存の +1）は正しく、**推論の候補を挙げて 1 往復で潰した**のが実際に起きたことです。**当方も 1 つ外しています。**
