# F-1（不具合）: ASSERT の大小比較が辞書順比較になる

## 現象

`ASSERT <スカラーサブクエリ> <大小比較> <数値リテラル>` の比較が、数値比較ではなく**辞書順（文字列）比較**で評価される。

言語リファレンス §26 は「比較の型規則は WHERE 句と同一（大小比較は**双方が数値なら数値比較**）」と定めており、`COUNT(*)` の結果と数値リテラルの比較は数値比較になるはずだが、実測は文字列比較の挙動と一致する。

## 再現（実測マトリクス）

`COUNT(*)` が返る件数 n に対して `ASSERT (SELECT COUNT(*) FROM ...) <演算子> <境界>` を実行した結果:

| n | 条件 | 数値比較なら | 実測 | 辞書順なら |
| --- | --- | --- | --- | --- |
| 3 | `= 3` | 成立 | **成立** | 成立 |
| 3 | `<= 10` | 成立 | **不成立（AssertError, actual: 3）** | 不成立（'3' > '10'） |
| 3 | `< 10` | 成立 | **不成立** | 不成立 |
| 3 | `BETWEEN 0 AND 10` | 成立 | **不成立** | 不成立（'3' <= '10' が偽） |
| 3 | `<= 9` | 成立 | **成立** | 成立 |
| 12 | `<= 9` | **不成立** | **成立** | 成立（'12' < '9'） |
| 3 | `> 2` | 成立 | **成立** | 成立 |

実測はすべて辞書順比較の予測と一致し、`= 3` の等値比較のみ期待どおり。

再現環境: kSQL Flow ランナーの `run`（`/flow` の `parseScript` → `executeStatement`）+ モック kintone（fetch 差し替え）。比較はエンジン内メモリで行われるためモックの影響はない。dialect 1 スクリプト:

```sql
-- @ksql name: t
-- @ksql dialect: 1
ASSERT (SELECT COUNT(*) FROM LAPP_案件管理) <= 10, 'over';
SELECT COUNT(*) AS c FROM LAPP_案件管理;
```

（レコード 3 件で AssertError。`actual: 3` と表示される）

## 影響

- **件数ガードが fail-open になり得る**: `ASSERT (...) <= 9` はレコード 12 件でも成立してしまう（'12' < '9'）。大量更新・大量削除の前段ガードとしての ASSERT の意味が崩れる
- 公開ドキュメントの推奨例にも波及: 言語リファレンス §26 の `BETWEEN 1 AND 500`、Qiita 記事の `ASSERT (SELECT COUNT(*) FROM #tgt) BETWEEN 1 AND 10000` は、実測挙動では意図どおりに動かないケースがある（例: 件数 3 は `BETWEEN 1 AND 10000` の上限比較 '3' <= '10000' が偽で不成立）
- ASSERT WARN・EXIT SUCCESS IF の条件部も同じ比較器なら同様の影響が疑われる（EXIT の `= 0` 等の等値比較は影響なし）

## 期待動作

§26 の記載どおり、双方が数値（`COUNT(*)` 結果・NUMBER 値・数値リテラル）の場合は 10 進の数値比較で評価されること。

## 参考: ランナー側の暫定回避

kSQL Flow 側の開発用ジョブでは、境界を 1 桁（`<= 5` 等）に抑えて「実際の件数が 1 桁である限り両解釈で正しい」形にし、コメントで本件を注記して回避している（`ksql-flow-template/dev/cleanup_test_deals.sql`）。修正リリース後に通常の境界へ戻す。

## 検出経緯

Qiita 記事②（AI 連携編）用のテストデータ投入・クリーンアップジョブ（`dev/seed_test_deals.sql` / `dev/cleanup_test_deals.sql`）のモック E2E 検証中、`3 <= 10` のガードが AssertError になり発見。あわせて確認した関連事項（不具合ではないが記録）:

- `DELETE` の WHERE に `LIKE` は使えない（WHERE_RESIDUAL エラー・仕様どおり）。完全一致 `IN` で回避

# F-2（機能依頼）: dialect 1 の `INSERT ... VALUES` で as-of 関数を許可

## 現状

`INSERT ... VALUES` の値はリテラル限定（数値・文字列・配列リテラル・CASE WHEN）で、dialect 1 の as-of 関数を書くと検証エラーになる:

```sql
-- @ksql dialect: 1
INSERT INTO LAPP_案件管理 (会社名, 売上, 受注予定日)
VALUES ('KSQL-FLOW-TEST-山田商事', 100000, @TODAY());
-- → KSQL1202 INSERT の値には文字列・数値・配列リテラル・CASE WHEN が必要です
```

`CASE WHEN 1=1 THEN @TODAY() END` で包んでも通らない（実測）。

## 依頼理由

1. **メンタルモデルとの不一致**: dialect 1 の `@` 関数は「as-of からリテラル展開される」仕様であり、利用者の認識は定数。リテラルが書ける場所に書けないのは驚きになる。AI にジョブを生成させると高確率でこの形を書く（実際、記事②の作業で最初に踏んだ）
2. **回避策が不自然**: 現行回避は `INSERT ... SELECT 定数, @TODAY() FROM <app> LIMIT 1` だが、①意図が読み取りにくい、②ソースアプリが空だと静かに 0 件挿入になる、③読取 API を 1 回余計に消費する
3. **用途**: シード/フィクスチャ投入・バックフィル用データ作成など、日時を「バッチ基準時刻で」入れたい INSERT は今後も発生する

## 仕様案

- **対象は as-of 関数 4 つのみ**: `@NOW()` / `@TODAY()` / `@MONTH_START()` / `@NEXT_MONTH_START()`。一般式・bare 時刻関数（`NOW()` 等・as-of 非固定）は引き続き拒否
- **dialect 1 限定**。dialect 0 の挙動・出力は 1 行も変えない
- **意味論**: prepare 時に as-of からリテラル展開（既存の内部予約変数→変数解決と同一経路）。展開後は純粋な定数
- **受入基準**: ①VALUES 内の 4 関数が実行・dry-run（previewStatement）・EXPLAIN の 3 面で同値に展開される ②同一バッチ内の全出現が同一 as-of ③dialect 0 では従来どおり KSQL1202

## 修正までの小改善（任意）

KSQL1202 のメッセージに「dialect 1 の as-of 関数は `INSERT ... SELECT` で注入してください」等のヒントを追記すると、修正リリース前でも利用者（特に AI）が自力で回避に辿り着ける。
