# kSQL エンジンへの依頼 F-7: UPSERT 書込経路の `updateKey + upsert: true` 採用検討

- 依頼日: 2026-08-25
- 依頼元: kSQL Flow（ランナー）開発
- 対象: `@rex0220/kintone-sql-tools` v3.72 系の UPSERT 実行経路（`/flow` を含む）
- 種別: 性能改善の機能依頼（優先度中 — 機能は成立しており、API 消費削減が目的。F-5 bulkRequest とは独立）
- 根拠: スケール検証 XL（100,000 件）の実測（`ksql-flow/verification/scale-notes.md`）と仕様書 §3.4 の実装注記

## 背景

現行エンジンの UPSERT は **read-then-write**（事前 GET でキー照合 → POST / PUT に振り分け。50 キー/リクエスト）で実装されている（kSQL Flow 公開仕様書 §3.4 に注記済み）。一方、kintone REST API のレコード更新（PUT /k/v1/records.json）には `upsert: true` + `updateKey` があり、**キー存在の判定を kintone 側に委ねて 1 リクエスト（100 件）で挿入 / 更新を書き分けられる**。

XL 実測では、UPSERT 10,000 件の内訳が「事前 GET 200 回（10,000 キー ÷ 50）+ 書込 100 回」で、**事前 GET が UPSERT の API 消費の 2/3** を占めた。native upsert に置き換えられれば:

| 指標（XL: 読取 10 万 → UPSERT 1 万） | 現行 | 置き換え後（試算） |
| --- | --- | --- |
| UPSERT フェーズの API | 300 回（GET 200 + 書込 100） | **100 回** |
| ジョブ全体の API | 511 回 | **約 311 回（約 4 割減）** |

F-5（bulkRequest）と重畳すれば書込 100 回 → 5 回まで縮む余地がある。

## 依頼内容

UPSERT の**本実行の書込経路**について、`updateKey + upsert: true` の採用を検討いただきたい。

前提条件はランナー側の既存制約と整合している:

- kSQL Flow の UPSERT キーは「値の重複を禁止する」設定済みの単一フィールド（文字列 1 行 / 数値）に限定済み（KSQL1301〜1303 で fail-closed）— native upsert の updateKey 要件と一致
- 複合キーは指定不可（連結キーフィールド運用を定石化済み）

## 設計上の論点（エンジン側の判断に委ねる）

1. **dry-run は対象外が妥当**: 差分プレビュー（before/after）には既存レコードの読取が本体であり、現行の GET 照合を継続する前提で依頼する（本実行と dry-run で API 消費が変わる点は、ランナー側の推定式 7.2 / 10.2 を追随修正する）
2. **insert / update 件数の分離**: ランナーはログに書込内訳を記録している。native upsert のレスポンス（`records[].revision`）で新規（revision = 1）と更新を判別できる想定だが、確実性の確認をお願いしたい。判別不能な場合、内訳レポートの扱いを協議したい
3. **権限要件の変化**: read-then-write は「閲覧 + 追加 + 編集」、native upsert も同等のはずだが、キー未存在 → 挿入経路でのトークン権限エラーの出方が変わる可能性。fail-closed の検査タイミングへの影響を確認したい
4. **多重ヒット解決規則の廃止**: 現行の「キー多重ヒット時は最大 `$id` を選択」は native では発生し得ない（重複禁止制約が前提）。挙動差が出るのは重複禁止設定前の既存重複データがある場合のみで、これは validate の fail-closed で既に弾かれている認識 — 認識違いがあれば指摘いただきたい
5. **適用範囲**: opt-in オプションにするか既定にするか。dialect 0（MCP / CLI 対話系）への影響範囲

## 受入基準（案）

1. XL 相当（UPSERT 10,000 件）で事前 GET 200 回が消え、UPSERT フェーズが書込約 100 回になる（実測はランナー側で実施・共有する）
2. 挿入 / 更新の結果件数が現行と同値（内訳の分離が可能な場合）
3. dry-run の差分・件数・API 消費は現行と同一（経路変更なし）
4. 冪等性が維持される（同一データでのリランが最終状態を変えない）
