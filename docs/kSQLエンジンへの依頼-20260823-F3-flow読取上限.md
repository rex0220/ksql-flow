# kSQL エンジンへの依頼 F-3: `/flow` の読取候補上限（maxRecords）の設定可能化

- 依頼日: 2026-08-23
- 依頼元: kSQL Flow（ランナー）開発
- 対象: `@rex0220/kintone-sql-tools` v3.72.0 の `/flow` 公式 API
- 種別: 機能依頼（優先度高 — スケール検証 L 段階のブロッカー）
- 関連: F-1/F-2（対応済み・v3.72.0）、kSQL Flow 側 `docs/internal/scale_verification_plan.md` と同 Codex レビュー（BLOCKER 2）

## 背景

kSQL Flow のレコード増加 3 段階検証（200 / 2,000 / 20,000 件）を企画したところ、Codex レビューで以下が判明した（ランナー側でも実物確認済み）:

- `/flow` の読取経路は候補行数上限が **既定 10,000 件**（dist-flow バンドル内 `maxRecords ?? 1e4`）
- `/flow` の公開オプションにこの上限を変更する手段が見当たらない（ランナーは `tempTableMaxRows` のみ渡している）
- kSQL Flow 公開仕様書 11 章は「単純 GROUP BY はストリーミング逐次集約（メモリ一定）で処理し、行数上限の対象外」と記載しているが、実装は fetch-all 方式であり、**20,000 件の単純 GROUP BY 集計は読取上限で停止する見込み**

つまり、仕様書 11 章が公表している性能目標（読取 10 万件 → 書込 1 万件）は、現行の `/flow` では到達できない。

## 依頼内容（いずれか、または両方）

### 案 A（最小・優先）: `/flow` に読取上限オプションを追加

- `executeStatement` / `previewStatement` / `validateScript` / `explainScript` の options に `maxRecords`（文単位の読取候補行数上限）を追加
- **未指定時の既定は現行どおり 10,000**（後方互換・fail-closed 維持）
- 上限到達時は現行同様の明示エラーで安全停止（silent truncation にしない）

### 案 B（本命・別途でも可）: 単純 GROUP BY のページ逐次集約

- 仕様書 11 章の記述どおり、JOIN・ソート・ウィンドウを伴わない単純 GROUP BY をカーソルページ単位の逐次集約（メモリ一定）にし、読取行数上限の対象外にする
- 案 A が入れば検証は前進できるため、案 B は規模・工数を見て別リリースでも構わない

## 提案仕様（案 A）

| 項目 | 提案 |
| --- | --- |
| 既定値 | **10,000（現行維持）** — 明示指定がない限り挙動不変 |
| 設定可能範囲 | 正の整数。**設計上のサポート目安は 100,000** — 公開仕様 11 章の性能目標（読取 10 万件 → 書込 1 万件）と同値で、サポート宣言と公表目標が一致する。メモリ概算: 実測 1.5KB/件 × 10 万 ≈ 150MB。10 万超は kintone 側の実用帯域も超えるため、ジョブ分割（または将来のスピル）を案内する。TEMP TABLE 合計 20 万行の目安とも「読取 10 万 + 集計・中間 10 万」で整合 |
| 適用単位 | 文単位（1 文の物理アプリ読取候補行数）。バッチ累計ではない |
| エラー | 超過時は現行と同系の明示エラー（コード・件数・上限値・引き上げ方法のヒントを含む） |
| EXPLAIN | 分解形の読取見積にこの上限値を反映（上限仮定表記との整合） |

## ランナー側の対応予定（参考）

承認・リリース後、kSQL Flow は `limits.maxReadRows`（仮称・既定 null = エンジン既定に委譲）を config に追加し、engineClientConfig 経由で `maxRecords` として引き渡す。スケール検証 L 段階では **25,000** を設定して実施する（必要量 20,000 + 余裕。ガードの意味を保つため過大にしない）。

## 受入基準

1. `maxRecords: 25000` を指定した `/flow` 実行で、20,000 件の読取を伴う単純 GROUP BY バッチが完走する
2. 未指定時は現行どおり 10,000 で明示エラー停止する（挙動不変）
3. `executeStatement` / `previewStatement`（dry-run）/ `EXPLAIN` の 3 面で同じ上限が適用・表示される
4. dialect 0 の CLI / MCP / プラグインの既定挙動は変えない（それぞれの既存上限設定はそのまま）

## 補足（仕様書側の整合）

案 A のみ対応の場合、kSQL Flow 公開仕様書 11 章の「ストリーミング最適化（行数上限の対象外）」は実装と乖離したままになるため、ランナー側で「将来対応（現状は maxReadRows で明示引き上げ）」へ記述を修正する。案 B 対応時に元へ戻す。
