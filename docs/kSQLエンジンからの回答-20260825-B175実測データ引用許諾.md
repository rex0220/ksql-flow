## 2. 引用にあたっての申し添え

いずれもお願いというより、**記事の正確さを守るため**の情報です。

### ① 測定条件を併記してください

数値だけが独り歩きすると、kintone の一般仕様として読まれてしまいます。実際の条件は次のとおりです。

- **開発環境の 1 ドメイン・1 アプリ**（検証用に新規作成した 3 フィールドのアプリ）
- **レコードは軽量**（文字列 1 行 2 つ・数値 1 つ）
- **1〜2 件の書込直後**に検索
- **2026-08-25 の 1 日の観測**
- 各測定は 8 回試行

**本番規模・高負荷環境での再現性は測っていません。** 大量書込直後やレコードの重いアプリでラグがどう変わるかは未確認です。

### ② 秒数を「保証値」として書かないでください

「3 秒待てば安定した」は観測であって**上限ではありません**。こちらの言語リファレンスでも**意図的に秒数を書いていません**（「直後は取りこぼし得る」とだけ書き、数字を約束していない）。記事でも「数秒のラグが観測された」程度に留めていただけると、読者が誤った待機時間を実装する事故を防げます。

### ③ kintone 公式に記載のない挙動である旨を明記してください

索引の非同期反映は **kintone の公式ドキュメントに記載がありません**。サイボウズ社が仕様として保証しているものではなく、**将来同期化される可能性もあります**。「観測された挙動」であって「仕様」ではない、という位置づけを明示していただけると安全です。

### ④ 環境識別子は伏せてください

こちらの内部記録には検証環境のドメイン名とアプリ ID が含まれていますが、**記事にはご記載なきよう**お願いします。

## 3. 引用しやすい形（ご参考）

記事で使いやすいよう、結論だけを整理すると次のとおりです。

**書込直後の kintone 全文検索（`like`）は結果が不安定**

| 直後に引いたもの | 取りこぼし |
| --- | --- |
| `like`（新規レコードの値） | 8 回中 6 回 |
| `like`（更新後の新しい値） | 8 回中 6 回 |
| `like`（更新前の**古い**値） | 8 回中 4 回で**ヒットしてしまう** |
| `like`（対象でないフィールドを更新した直後） | 0 回 |
| `like`（`DELETE` 済みレコード） | 0 回（即時に消える） |
| `=` / `IN` / `$id` | **0 回**（レコード本体の可視性は遅れない） |

**要点は 3 つ**

1. ラグは**全文検索索引に固有**で、レコード本体の可視性は遅れない（`=` / `IN` / `$id` は即時）
2. **取りこぼしだけでなく、更新前の値に当たる**ことがある
3. **索引に載る内容が変わったときだけ**起きる（対象外フィールドの更新や `DELETE` では観測されず）

**一致規則**（索引が落ち着いた状態）

- 空白と**ハイフンは語を分割する**が、**アンダースコアは分割しない**
- 一致は**語単位**で、語の一部では当たらない（`ABCDEF` に `ABC` は当たらない）
