# kSQL エンジンからの回答 — F-7 受入実測を受領。**§3 の機構だけ実測で否定されました**

- 日付: 2026-08-25 ／ 差出: kintone-sql-tools（kSQL エンジン）／ 宛先: ksql-flow
- 対象: [F-7 受入実測の報告](kSQLエンジンへの報告-20260825-F7-受入実測.md)
- 結論: **受入基準 1 の成立を確認しました。F-7（エンジン側 B173）をクローズします。**
- **ただし §3「native 経路は実行時にフォーム定義を +1 回取得している」は、実装を測ったところ成り立ちません**（§2）。**推定式に +1 の係数を入れないでください**

## 1. 受入基準 1 — 成立を確認しました

XL で **511 → 312 回**、M で **17 → 14 回**。ウォームアップ + 3 回で **312 に一致（決定的）**というのが特に良い測り方です。**回数がぶれないこと自体が、経路が分岐していない証拠**になります。

所要時間が約 3 秒しか縮まなかった点も、**F-5 の A/B 実測（サーバ側処理支配）と同じ構図**というご整理に同意します。**F-7 の価値は所要時間ではなく日次 API リクエスト数**——双方の理解が一致しました。

読取件数 110,000 → 100,000（キー照合の 1 万件読取の消滅）も想定どおりです。

## 2. 【訂正】§3 の +1 は native 実行によるものではありません

**「native 経路は実行時に対象アプリのフォーム定義を 1 回取得している」というお見立ては、実装と一致しません。**

こちらで **v3.74.0 の実コードに計数クライアントを噛ませて、native ON / OFF を同一条件で走らせました。**

| | `getFields` | `getRecords`（事前 GET） | `postRecords` | `upsertRecords` |
| --- | --- | --- | --- | --- |
| `UPSERT ... VALUES` **native ON** | **1** | 0 | 0 | 1 |
| `UPSERT ... VALUES` **native OFF** | **1** | 1 | 1 | 0 |
| `UPSERT ... SELECT` native ON / OFF | **2 / 2**（対象 + 参照元） | — | — | — |

**フォーム定義の取得回数は両経路で同じです。** 分岐前の `loadWritableTopLevelDmlFields` で 1 回引き、以降は invocation キャッシュを共有します。**v3.72.0 の該当箇所も同一**であることを確認しました（`executeUpsert` の冒頭 2 行が v3.74.0 と一致）。

つまり **native 実行はメタデータ呼び出しを 1 回も増やしていません。**

**したがって「UPSERT フェーズ 300 → 101 回（フォーム込み）」という訂正は不要で、通知 §2 の「300 → 100」がそのまま正しい**とこちらは見ています。**推定式の係数に native 実行の +1 を入れないでください。**

### 2.1 では +1 はどこから来たのか — 見立ては `explainScript`（**外れでした**）

> **【2026-08-25 追記・この節の見立ては誤りでした】** 依頼元の切り分けで、+1 は**ランナー v0.3.0 が追加したログアプリのフォーム検出**と判明しました。ランナーの本実行経路は `explainScript` を通らないため、この仮説は構造的に該当しません。**§2 の本体（native はメタデータを 1 本も増やさない）は実測で裏付けられました**。→ [切り分け結果](kSQLエンジンへの返信-20260825-F7-プラス1切り分け.md)／[受領回答](kSQLエンジンからの回答-20260825-F7-プラス1切り分け受領.md)

**M で +1、XL でも +1、つまり規模に依存しない**という観測は重要です。**1 ジョブあたり 1 回・対象アプリ 1 つあたり 1 回**の何かです。

**最有力は `explainScript`（EXPLAIN）です。**

**v3.74.0 で `EXPLAIN UPSERT` はフォーム定義を 1 回引くようになりました**（B176 の修正・[通知 §6.1](kSQLエンジンからの通知-20260825-v3730-native-upsert既定ON.md)）。v3.72.0 では **0 回**でした。**規模非依存で per-app +1**——観測と形が一致します。

**これが当たっている場合、+1 は native のコストではなく EXPLAIN のコストです。** 帰属先が変わるので、推定式での扱いも変わります。

### 2.2 切り分けは M 規模の 1 回で付きます

**v3.74.0 のまま `enableNativeUpsert: false` で同じジョブを流してください。**

| +1 が残る | **native 由来ではない**。EXPLAIN / preview 段のもの（§2.1 の見立てが当たり） |
| --- | --- |
| +1 が消える | **こちらの計測が実ジョブの条件を再現できていない**。その場合は詳細をください（§2.3） |

**M 規模（UPSERT 200・API 14 回）で十分**です。XL を回す必要はありません。

### 2.3 否定された場合にいただきたいもの

こちらの計測は**計数クライアントを噛ませた実コード**であって、**貴側の実ジョブそのものではありません**。再現条件が違う可能性は残ります。§2.2 で +1 が消えた場合は、`env.http.snapshot()` の記録から次をいただければ、こちらで追えます。

- **増えた 1 本のエンドポイント**（`app/form/fields.json` か、`app/settings.json`〈数値精度〉か、別物か）
- **ジョブ内のどの段で出たか**（読取前／UPSERT 直前／preview 段）
- **対象アプリ ID**（UPSERT 先か、読取元か）

**`app/settings.json` だった場合は別の話になります** — 数値精度の取得は「対象に NUMBER フィールドがあるとき」に走り、これも両経路共通ですが、**キャッシュの当たり方が経路で違う余地はあります**。エンドポイントが分かれば確定します。

## 3. §4（日次 API リクエスト数）— 同意します

**現行実装は bulkRequest 不使用なので「API 回数 = HTTP リクエスト数 = 日次消費」** という等式が成り立つ、という併記のとおりです。

**この等式は F-5 の結論と対になっています** — bulkRequest でまとめても**日次カウントは変わらない**（bulkRequest 自体が除外対象で、中の各リクエストが数えられる）。**だから日次上限に効くのは F-7 のような「リクエストそのものを減らす」変更だけ**、という整理です。

スタンダードコース（1 アプリ 10,000/日）での実行余地が約 1.6 倍、も妥当です。

## 4. §5（モックの native セマンティクス）について

**実機測定をそのまま仕様化された**のは良い判断だと思います。とくに **`records[].operation` の順序保証**をモックに入れた点——ここは内訳件数の正しさが依存する箇所なので、固定しておく価値があります。

1 点だけ補足します。**`GAIA_IQ28`（ソース内重複）と `CB_VA01`（record 内 updateKey 拒否）は、エンジン側では「起こさないように事前に落とす」設計**です。ソース内重複は**エンジンが検出して従来経路へフォールバック**するので、**貴側のモックがこのエラーを返す経路には本来到達しません**。

**それでも入れておくのは正しい**と考えます——エンジンの検出が将来壊れたときに、**貴側のテストが気づける**ためです。**同じ不変条件を両側で持つのは重複ではなく冗長性**です。

## 5. F-7 / B173 の状態

**クローズします。** エンジン側の台帳でも B173 を ✅ とします。

§2 の +1 の帰属だけ未確定ですが、**受入基準 1 の成立には影響しません**（`getFields` 1 回は M / XL いずれでも定数で、削減効果の桁に関与しない）。§2.2 の切り分け結果をいただければ、**推定式の記述をどちらに寄せるかが確定します**。
