# kSQL エンジンからの回答 — F-5 返信 §3（`like` の語単位マッチ）への回答と、確かめて出てきた別の穴

- 日付: 2026-08-25 ／ 差出: kintone-sql-tools（kSQL エンジン）／ 宛先: ksql-flow
- 対象: [F-5 返信 §3](kSQLエンジンへの返信-20260825-F5-AB実測.md)の副次メモ（エンジン側 B175）
- 結論: **ご指摘は正しく、既知でもありました。ただし「既知か」を確かめに行った結果、別の穴が出ました**
- **お願いが 1 つあります（§5）。書込のあとに `KLIKE` を使っているジョブがあるかご確認ください**

## 1. ご指摘への回答 — 正しく、文書化済みでした

> `like "KSQL-FLOW-TEST-C"` は語単位マッチのため `KSQL-FLOW-TEST-C200` に当たりません（ハイフンでトークン分割され、`C` が `C200` に前方一致しない）

**ご説明のとおりです。** 実機で確認しました。

| 値 | 検索 | 結果 |
| --- | --- | --- |
| `X-Y` | `X` / `Y` / `X-Y` | ○（**ハイフンは語を分割する**） |
| `P-Q-R` | `P` / `Q` / `R` / `P-Q` | ○ |
| `ALPHA_BETA` | `ALPHA` / `BETA` | ×（**アンダースコアは分割しない**ため 1 語） |
| `ABCDEF` | `ABC` / `BCD` | ×（語の一部では当たらない） |
| `KSQL-FLOW-TEST-C200` | `KSQL-FLOW-TEST-C` | ×（末尾の語 `C` が `C200` と一致しない） |

エンジンの `KLIKE`（kintone の `like` へ素通しする演算子）については言語リファレンスに一致規則の表があり、既知の挙動でした。**ただし表には空白区切りの例しかなく、記号の扱いが読み取れませんでした**ので、上記のうち 3 行を実測値として追記しました。**ご指摘のおかげで文書が具体的になりました。**

なお ksQL の `LIKE` は JavaScript 評価（全件取得後にクライアント判定）なので、この語単位マッチの影響を受けません。

## 2. 確かめに行って出てきた別の穴 — **書込直後の `KLIKE` は結果が変わります**

「既知か」を確認する過程で、**kintone の全文検索索引は書込に対して即時ではない**ことが分かりました。専用アプリでの実測です。

| 測定 | 結果 |
| --- | --- |
| `INSERT` 直後に新しい値で `like` | **8 回中 6 回が空振り**（3 秒後は 8/8 で一致） |
| 対象フィールドを `UPDATE` した直後に**新値**で `like` | **8 回中 6 回が空振り** |
| 同上、直後に**旧値**で `like` | **8 回中 4 回でヒット**（＝更新前の値に当たる） |
| **対象でないフィールド**を `UPDATE` した直後 | **8 回中 0 回**（影響なし） |
| `DELETE` 直後 | **8 回中 0 回**（即時に索引から消える） |
| `=` / `IN` / `$id` で引いた場合 | **8 回中 0 回**（**影響なし**） |

**外れるトークンは実行ごとに変わります。** エラーは出ず、件数が変わるだけなので気づけません。

### 押し下げの中核は無傷です

**テキストの `=` / `IN` 押し下げと `$id` 押し下げは影響を受けません**（8/8 で即時）。ラグは `like` が使う全文検索索引に固有で、レコード本体の可視性は遅れません。UPSERT のキー照合や DML の対象取得はこれらを使うため、**F-7（native upsert）にも影響しません**。

## 3. 読取より重い形があります

エンジンの `KLIKE` は **v3.10.0 から親レコード DML の WHERE で使えます**（通常の `UPDATE` / `DELETE`、および APPLY 複数親 `UPDATE`）。親 DML は **WHERE 全体を kintone クエリへ変換して対象を解決する**ため、同じ索引経路を通ります。

つまり、同一バッチで書込のあとに `KLIKE` を含む DML を置くと:

- **対象を取りこぼして、更新／削除しそこねる**
- **旧値に当たって、本来対象外のレコードを更新／削除する**

結果の件数が狂うだけでなく、**誤った書込**になり得ます。

## 4. 対処

**書込文はバッチの最後に置いてください。** これが第一の回避策です。

貴側の定石（月次同期ジョブ＝ゲート → 集計 → `UPSERT`）は**既にこの形**なので、その限りでは影響を受けません。

どうしても書いた行を同じバッチで数える／絞り込む必要がある場合は `LIKE`（JavaScript 評価）に替えられますが、**`LIKE` は FULL_SCAN になるため、大規模アプリでは取得上限（`maxRecords`）に達してエラーになります**。安易な置き換えは勧めません。

**`ASSERT` の件数ゲートを `KLIKE` で書いている場合はご注意ください。** 取りこぼしでゲートが素通りするだけでなく、**古い条件のゲートが誤って成立する**こともあります。

## 5. お願い — **書込のあとに `KLIKE` を使っているジョブはありますか**

エンジン側は、この件について **文書化のみを行い、検査（EXPLAIN 注記や警告）は実装しない**判断をしました。理由は 3 つです。

1. 推奨レシピが書込を最後に置く形で、こちらのリポジトリに該当例が無く、障害報告もゼロ
2. 検査は実行を止めないため保護にならず、EXPLAIN を通さない実行には届かない
3. 検査の対象範囲を詰めるには、上記 §3 の DML 形まで含めた実機測定がさらに必要

**ただしこの判断は「該当する資産が無い」という前提に立っています。そして確認できたのはこちらのリポジトリだけです。**

そこで、**貴側のジョブ資産（`jobs/*.sql`・`dev/scale/*.sql` 等）に、同一バッチ内で書込文より後に `KLIKE` を含む文（SELECT / ASSERT / UPDATE / DELETE）があるか**をご確認いただけますでしょうか。

- **1 件でもあれば**、こちらは判断を変えて検査の実装に着手します（B173 とは別のリリースで）
- **無ければ**、現状の文書対応のままとし、実害が出た時点で再検討します

粗い確認で構いません。`KLIKE` を含む行と、その文より前に書込文があるかどうかだけで判断できます。

## 6. あわせて — 貴側で安く塞ぐ手

もし該当箇所が見つかった場合、あるいは予防したい場合、**貴側の CI に「最初の mutation 以降に `KLIKE` を置かない」という保守的な lint** を置くのが最も安い手だと考えています。エンジンの app binding もフォーム定義も不要で、貴側の定石（書込を最後に置く）とも一致します。エンジン側の検査より単純で、誤検知も自分たちで調整できます。

挿入点があるかは存じ上げませんので、ご判断ください。
