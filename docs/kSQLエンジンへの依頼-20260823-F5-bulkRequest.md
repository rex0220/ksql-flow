# kSQL エンジンへの依頼 F-5: 書込チャンクの `bulkRequest` 束ね対応

- 依頼日: 2026-08-23
- 依頼元: kSQL Flow（ランナー）開発
- 対象: `@rex0220/kintone-sql-tools` v3.72.0 の DML 書込経路（`/flow` を含む全面）
- 種別: 性能改善の機能依頼（優先度中 — 機能は成立しており、時間短縮のみが目的）
- 根拠: スケール検証 XL（100,000 件）の実測（`ksql-flow/verification/scale-notes.md` / my-ksql-jobs `docs/scale_xl_report.md`）

## 背景 — 起票条件の充足

スケール検証の企画（R2 §9）で「書込 API が所要時間・API 消費の支配項と判明した場合に起票」と定めていた条件が、XL 実測で明確に満たされた:

| 操作 | チャンク数（100 件/回） | 所要 | 秒/チャンク |
| --- | --- | --- | --- |
| UPDATE 100,000 件 | 1,000 | **44.6 分** | **2.67** |
| DELETE 110,000 件 | 1,100 | 8.8 分 | 0.48 |

（注: 実測は 1 文の巨大 UPDATE ではなく、`会社名 IN (250 社)` の UPDATE 文 40 個 ≒ 1 文 2,500 件に分割して実行したもの。秒/チャンクは文の分割方法に依存せず、所要時間はチャンク総数で決まる — L と XL で同値であることが根拠）
| （参考）読取 10 万 + UPSERT 書込 1 万の集計ジョブ全体 | — | 3.3 分 | — |

- 秒/チャンクは L（2 万件）と XL（10 万件）で安定（UPDATE 2.51 → 2.67）— **チャンク数が所要時間を線形に決める**ことが確定
- 同一データ量でも UPDATE は DELETE の約 5.6 倍/チャンク（送信ペイロード差）

## 依頼内容

書込 DML（INSERT / UPDATE / DELETE / UPSERT の書込フェーズ）で、kintone の `bulkRequest`（1 リクエストに最大 20 サブリクエスト）により書込チャンクを束ねられるようにする。

- 期待効果: 書込 HTTP リクエスト数が最大 **1/20**（XL の UPDATE 1,000 → 50 リクエスト）。往復レイテンシ支配のため、**44.6 分 → 数分規模**への短縮が見込める
- 仕様書 11 章は現在「`bulkRequest` はエンジン未実装」と明記しており、対応時はランナー側の推定 API 算出（7.2 / 10.2）も追随修正する

## 設計上の論点（エンジン側の判断に委ねる）

1. **原子性の変化**: `bulkRequest` はリクエスト内が一括成否（どれかが失敗すると全サブリクエストが失敗）。現行の「100 件チャンク単位の部分適用 + fail-fast」から「2,000 件単位の部分適用」に粒度が変わる — 冪等リラン前提の kSQL Flow にはむしろ好都合だが、エラー行の特定粒度・`onChunkWritten`（チェックポイント）の粒度・`last_written_key` の意味は再定義が必要
2. **適用範囲**: opt-in オプション（例 `bulkWrites: true`）にするか既定にするか。CLI / MCP / プラグインの確認ダイアログ・件数ガードとの整合
3. レート制限との関係: bulkRequest 1 回は API 1 回だが kintone 側の負荷は大きい。429 の挙動が変わる可能性（現検証では 429 発生ゼロのため実測データなし）

## 受入基準（案）

1. XL 相当（UPDATE 100,000 件）の書込リクエストが約 50 回に束ねられ、所要時間が大幅短縮される（実測はランナー側で実施・共有する）
2. 束ね有効時も dry-run（previewStatement）の差分・件数が従来と同値
3. 失敗時の挙動（どの単位で止まり、リランでどう収束するか）が文書化される
4. 既定挙動を変えない場合、未指定時の出力・API 数は現行と同一
