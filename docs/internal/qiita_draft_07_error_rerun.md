本記事はその原則の中身です。**失敗の通知が来た朝に、何を見て、何をすればよいのか**。そして「再実行して大丈夫」を支えている設計 — Exit Code の分類・部分適用・冪等 UPSERT・`--resume` の選抜規則・分散ロック — を、実測の裏付けごと説明します。この仕組みは実行環境に依存しないので、今後どの環境（cron・Docker・レンタルサーバー・クラウド）に載せても、この記事の内容がそのまま使えます。

## 失敗は 3 種類しかない — まず Exit Code で分類する

kSQL Flow の終了コードは 6 つありますが（[仕様 §10.3](https://github.com/rex0220/ksql-flow/blob/main/docs/ksql_flow_spec.md)）、**朝の通知で出会う失敗は実質 3 種類**です。初動はそれぞれ違います。

| Exit | 意味 | 典型的な原因 | 初動 |
| --- | --- | --- | --- |
| **2** | 業務異常（ASSERT 違反・`ABORTED`） | マイナス売上・想定外の重複など**データの問題** | データを直す。**直すまで何度流しても止まるのが正しい** |
| **3** | 実行時エラー（`FAILED` / `TIMEOUT`） | API 障害・トークン失効・ネットワーク・タイムアウトなど**基盤の問題** | 基盤側を確認して復旧を待つ / 直す |
| **5** | 多重起動（`LOCKED`） | 前回実行がまだ動いている、またはクラッシュでロックが残った | 前回の状態を確認。ハングなら `unlock` |

残りの 3 つが朝の通知に出てこない理由: **0** は成功（対象 0 件の `NO_DATA` を含む — 後述）、**1** は検証エラーでデプロイ前に検出されるべきもの（#6 の pr-check がまさにこの門番）、**4** は `--continue-on-error` を明示したときだけ現れる部分成功です。

覚え方は **2 = データ（人間が直す）・3 = 基盤（インフラを直す）・5 = ロック（前回の後始末）** です。エラーの詳細は kintone のログアプリの **error 欄**にあります。逆に、**ログアプリに BATCH レコード自体が無ければ、失敗は CLI より手前**（スケジューラ・シェル・パス）です — #4 で実機の障害切り分けに使った「記録が無い = CLI 未到達」の武器がここでも効きます。

## NO_DATA は失敗ではない — 誤アラートが監視を殺す

kSQL Flow は「業務異常による停止」と「対象 0 件の正常終了」を構文レベルで分けています。

```sql
-- 対象 0 件は正常なスキップ（月初・休日など）— 通知しない
EXIT SUCCESS IF (SELECT COUNT(*) FROM 対象) = 0;

-- 業務ルール違反は異常停止 — 通知する
ASSERT (SELECT COUNT(*) FROM 対象 WHERE 売上 < 0) = 0, '【異常中断】マイナス売上があります';
```

これを混同すると、月初のたびに「失敗」通知が飛びます。**誤アラートの本当のコストは、通知が無視されるようになること**です。オオカミ少年になった監視は、本物の異常のときに機能しません。だから `NO_DATA` は Exit 0・通知なし・依存ジョブも通常どおり実行、と徹底しています。

## 部分適用 — 大規模バッチ全体は 1 トランザクションにできない

失敗対応で最初に受け入れるべき事実がこれです。**数万件規模のバッチ書込の全体を 1 つのトランザクションにする手段は、kintone にはありません**。正確に言うと: 1 回の[複数レコード更新 API](https://cybozu.dev/ja/kintone/docs/rest-api/records/update-records/)（最大 100 件）の**内側は原子的**（1 件でも失敗すれば全件キャンセル）で、[bulkRequest](https://cybozu.dev/ja/kintone/docs/rest-api/records/bulk-request/) なら最大 20 リクエスト分の一括ロールバックもあります。しかしそこまでです。kSQL Flow の書込は 100 レコード/リクエストのチャンクで送られるため、**先に成功したチャンクは、後続チャンクの失敗では戻りません**。3 万件の更新が 1.2 万件時点で失敗すれば、**1.2 万件は書かれた状態で止まります**（bulkRequest の 2,000 件ロールバックについては [#5](https://qiita.com/rex0220/items/9cbc1e0e9b5ab292e6a1) で実測込みで扱いました — 大規模バッチ全体は覆えず、時間も縮まないため採っていません）。

kSQL Flow はこれを隠しません。ログアプリには成功したチャンク数と診断用の `last_written_key` が残り、「どこまで書けたか」を確認できます（このキー値は順序保証のない診断情報で、復旧の起点には使いません — 復旧は次節の冪等リランが正です）。

## なぜ再実行して壊れないのか — 冪等 UPSERT + as-of 固定

部分適用を前提にすると、**部分適用した同一ジョブを安全にやり直す基本は、冪等リランに絞られます**。支えているのは、**同じジョブをもう一度流しても最終状態が同じになること** — 冒頭で触れた**冪等性（べきとうせい・idempotency）**です。kSQL Flow の書込がキー指定の `UPSERT` を標準とするのはこのためです — 書けていた 1.2 万件は同じ値で上書きされ、残りが新たに書かれ、結果は「最初から成功した場合」と一致します。なおこれは「**同一 as-of で入力集合が再現でき、書込がキー UPSERT で表現できるジョブ**」を前提にした冪等性です — kSQL Flow の定石（時刻は @ 付き関数・書込は UPSERT・中間結果は TEMP TABLE）に沿って書かれたジョブは、この前提を満たします。

もう 1 つの支えが **as-of（実行基準時刻）の固定**です。`@TODAY()` などの時刻関数はバッチ開始時に確定した基準から計算されるため、**前日に失敗したジョブを翌日リランしても、前日の基準で集計されます**。「金曜の夜に失敗して月曜に直したら、集計対象の月が変わっていた」という事故が構造的に起きません。

これは机上の設計ではありません。[#3 のスケール検証](https://qiita.com/rex0220/items/62e950ab1ccc5b54ff69)では、数万件の書込チャンクの**途中でプロセスを強制切断**し、ロック解除 → 同一 as-of でリランして、**突合ジョブで全件一致まで収束すること**を実測で確認しています。

## `--resume` は何を再実行するのか

復旧コマンドは 1 つです:

```bash
ksql-flow run-all ./jobs --profile prod --resume
```

`--resume` は直近バッチの記録（ログアプリが正）から、**再実行が必要なジョブだけ**を選びます。

| 前回の状態 | resume での扱い |
| --- | --- |
| `FAILED` / `ABORTED` / `TIMEOUT` | **再実行** |
| 失敗の巻き添えでスキップ（依存先失敗・stop-on-error） | **再実行** |
| `RUNNING` のまま残っている（クラッシュ） | **再実行** |
| JOB レコードが無い（未着手のままクラッシュ） | **再実行** |
| `SUCCESS` / `NO_DATA` | **再実行しない** |
| `--from` / `--only` の選抜外だった（filtered） | 再実行しない |

このとき **as-of は元セッションから自動で引き継がれます**（当日基準でやり直したい場合だけ `--as-of` で明示上書き）。#6 の GitHub Actions では、この resume を「Run workflow」のチェックボックス 1 つに載せました — 環境が変わっても復旧手順は同じです。

ちなみに、複数ジョブの途中で 1 本が失敗したときの既定動作は「**失敗ジョブに依存する後続だけスキップし、独立した後続は実行する**」です（全体を即停止したいなら `--stop-on-error`）。この失敗時挙動の全パターンは[仕様 §4.1](https://github.com/rex0220/ksql-flow/blob/main/docs/ksql_flow_spec.md) に一覧表があります。

## リランせずに次のスケジュールが来たら — 休日に失敗したケース

現実の運用で必ず起きるのがこれです。**土曜の朝に失敗し、誰も resume しないまま日曜のスケジュールが来る**。どうなるか。

**きれいに失敗していた場合（Exit 2 / 3）** — ロックは失敗終了時にも解放されるので、**翌日のスケジュールはブロックされず普通に走ります**。その先はジョブの型で分かれます:

- **累積・全量型**（月次集計のような「as-of 時点の全量を計算して UPSERT」）: **翌日の全量再計算が前日の部分適用を吸収**します（いわば自己修復）— 担当者不在でも翌日に正常化し、休み明けの作業はありません。テンプレートの月次集計ジョブはこの形です
- **期間窓型**（「前日分だけ処理する」のような切り出し）: 翌日の実行は翌日の窓しかやらないので、**失敗した日の窓が欠損として残ります**。休み明けにバックフィルで埋めます — `ksql-flow run-all ./jobs --profile prod --as-of "2026-08-25T00:00:00+09:00"` のように失敗日を基準時刻に指定するだけです（失敗の記録と通知はログアプリに残っているので、どの日が欠けたかは休み明けでも追えます）
- Exit 2 の原因データが残っている場合: 翌日も同じ ASSERT で止まり、**直るまで毎日通知が飛びます**。書く前に止まるので被害は拡大しません — 通知が続くこと自体が「まだ直っていない」の表示です

**クラッシュしていた場合（RUNNING が残存）** — 翌日の実行が `started_at + batchTimeoutSec` の超過を検知して**警告付きで自動回収**し（status は `TIMEOUT` に更新 = FAILED 系なので**このとき条件通知も飛びます**）、そのまま翌日分を実行します。担当者不在でも自走復帰します。Exit 5 で止まり続けるのは、タイムアウト時間内に次の実行が来る高頻度スケジュールの場合だけです。

**1 つだけ期限があります** — 翌日のバッチが走った時点で、`--resume` の対象は翌日バッチに移ります。**失敗日を resume で救えるのは次のスケジュールが来る前だけ**で、それを過ぎた復旧はバックフィル（`--as-of`）に変わります。

運用への含意はシンプルです: **「休日に失敗しても放置でよい」設計にしたければ、ジョブを累積型に寄せる**。これが期間窓型との最大の運用差で、ジョブを書く段階（AI に依頼する段階）で意識する価値があります。

### 毎時実行でも成り立つか

この仕組みは毎時などの高頻度スケジュールでも成立しますが、条件が 4 つ付きます。

1. **`batchTimeoutSec` を間隔より短く**する（例: 毎時なら 1800 秒）。既定の 3600 秒のままだと、クラッシュ後の stale 自動回収が次のスロットの境界と重なり、1 回分が Exit 5 で欠けることがあります
2. **実行時間が間隔に収まる**こと。食い込んだ場合は後発が Exit 5 で安全側にスキップされます（滞留はしません）
3. **スケジューラは時刻が正確な環境を選ぶ** — 実測した GitHub Actions の遅延（+30〜99 分）は毎時の間隔と同じオーダーなので、毎時運用は [#4 のタスクスケジューラ](https://qiita.com/rex0220/items/d0a66c133edd42ff91c4)や cron が適します
4. **ジョブは追いつき型に** — 毎時の期間窓型は resume の期限が 1 時間しかありません。「未処理を全部処理する」形にしておけば、スロットが 1 回欠けても次の回が吸収します

もう 1 つ、毎時 × 24 回で**日次 API 上限の消費も 24 倍**になります。小さなジョブなら余裕ですが、大規模ジョブでは [#5 の API 削減](https://qiita.com/rex0220/items/9cbc1e0e9b5ab292e6a1)が効いてくる領域です。

## 多重起動 — kintone アプリがロックサーバーになる

Exit 5 の背後にあるのが、この連載でいちばん kintone らしい設計です。**専用のロックサーバーを立てる代わりに、ログアプリの「値の重複を禁止する」フィールドを分散ロックとして使います**。

実行開始時、ランナーはログアプリへ `job_key` 付きの RUNNING レコードを先行 INSERT します。`job_key` は重複禁止なので、**別のマシンから同じジョブが同時に走ると、後から来た方の INSERT が kintone に拒否され、Exit 5 で即座に停止**します。ロックの実体が kintone 側にあるため、タスクスケジューラと GitHub Actions が同じジョブを偶然同時に起動しても衝突しません — スケジューラをまたぐ排他が、追加インフラなしで成立します。正常終了時にはキーが `job_key_done` へ退避され、ロックは自然に解放されます。

クラッシュでロックが残った場合は:

```bash
ksql-flow unlock --profile prod   # 対象一覧を表示してから解除
```

**1 つ注意（実測で見つけた盲点）**: ロック競合でスキップされたジョブは `SKIPPED` 扱いで、**FAILED 系の条件通知には乗りません**。Exit 5 はスケジューラ側（`LastTaskResult` / Actions の失敗表示）には現れるので、そちらが検知面になります。多重起動が続くようなら、それは通知の問題ではなくスケジュール設計の問題です。

## やってはいけないこと — スケジューラ側の自動リトライ

#4・#6 で「使わない」とだけ書いた理由を、ここまでの材料で説明できます。

1. **Exit 2 に自動リトライは無意味** — 業務異常はデータを直すまで何度流しても止まるのが正しい挙動で、リトライは同じ失敗を繰り返すだけです
2. **ロックと衝突する** — 失敗直後の自動再起動は、前回実行のロック回収と競合して Exit 5 の連鎖を作り得ます
3. **復旧の入口が二重になる** — 「スケジューラが勝手に再実行したかもしれない」状態では、人間の `--resume` 判断ができなくなります

リトライしてよいのは**一時的な API エラーだけ**で、それはランナーが内部で指数バックオフ済みです（HTTP 429/5xx 系のみ・上限超過で Exit 3）。つまり「リトライすべきものはランナーの中で済んでいて、外側に残るのは人間が判断すべき失敗だけ」という分担です。

## 保存版 — 症状から引く対応表

| 症状 | 見る場所 | 対応 |
| --- | --- | --- |
| 通知「バッチ失敗」・Exit 2 | error 欄の ASSERT メッセージ | データを修正 → `--resume` |
| 通知「バッチ失敗」・Exit 3 | error 欄（API/認証/タイムアウト） | 基盤を確認・復旧 → `--resume` |
| スケジューラは失敗・通知なし・Exit 5 | ログアプリの RUNNING レコード | 前回がハングなら `unlock` → 必要なら手動実行 |
| 通知なし・**ログアプリに BATCH が無い** | スケジューラ側のログ | 失敗は CLI 未到達 — 起動経路（パス・シェル・権限）を疑う（#4 の罠参照） |
| そもそも起動していない | heartbeat の不在 | ランナーでは検知不能 — 外部監視か人間の目（#4 参照） |
| 月初に「失敗」通知が来る | ジョブの ASSERT | それは業務異常ではなく対象 0 件では？ `EXIT SUCCESS IF` に書き換え |

## 実機検証の記録（2026-08-27）

本記事の主張は、机上のまとめではなく**すべて実機で再現**しています（kintone 開発環境・KSQL-FLOW-TEST 専有データ 2,000 件・ksql-flow v0.4.0 + エンジン v3.74.0）。

| シナリオ | 結果 |
| --- | --- |
| 業務異常（マイナス売上を投入 → run-all） | ジョブ 1 が ABORTED（Exit 2・error 欄に原因と件数）、依存する後続が SKIPPED (dependency)、バッチ Exit 2・条件通知発火 |
| データ修正 → resume | as-of を失敗時刻で引き継ぎ、ABORTED と失敗起因 SKIPPED の**両方を再実行** → 全 SUCCESS |
| 部分適用を意図的に作る（--max-api-calls で書込途中停止） | **書込 100 / 200 件で安全停止**（FAILED・Exit 3）— 200 社中 100 社だけ更新された状態を確認 |
| リランせず翌日相当の通常実行 | 新 as-of の全量再計算が 200 社を上書き → **突合ジョブで全件一致 = 部分適用の吸収を実証** |
| その後の resume | 「再実行が必要なジョブはありません」— **resume の対象が新バッチへ移る期限を実証** |
| クラッシュ（プロセスツリーを強制 kill）→ 即再実行 | ローカルの stale ロックは自動回収・**分散ロック（RUNNING レコード）が Exit 5 で多重起動を検知** |
| batchTimeoutSec 超過後の再実行 | 「**警告: stale ロックを自動回収しました**」→ 残存レコードは TIMEOUT に更新（**このとき条件通知も発火**）→ そのまま完走 |
| バックフィル（--as-of 過去日） | 指定日の 0:00 JST に as-of が固定されて SUCCESS |

副産物の実証も 1 つ — kill が甘くランナーが生き残ったケースでは、**生きている実行との二重起動が Exit 5 で正しく弾かれました**。死んだロックは回収し、生きている実行は守る、という判定が実機で分かれることの確認になっています。

## まとめ

- 失敗は Exit Code で 3 分類 — **2 = データを直す / 3 = 基盤を直す / 5 = 前回を確認**。初動が全部違う
- **大規模バッチ全体を 1 トランザクションにはできず**、失敗時は**部分適用**で止まり得る。だから書込は冪等 UPSERT を標準にし、**復旧 = 同一 as-of の `--resume`** に一本化する（強制切断からの収束は実測済み）
- 排他は **kintone アプリの重複禁止フィールドがロックサーバー** — スケジューラをまたぐ多重起動も Exit 5 で止まる。ただし Exit 5 は kintone 通知に乗らない点だけ注意
- スケジューラ側の自動リトライは使わない — リトライすべき失敗はランナー内で処理済みで、外に残るのは人間が判断すべき失敗だけ
- この仕組みは実行環境に依存しない。だから環境を乗り換えても運用は変わらない — 連載を通した主張の種明かしがこの記事です
