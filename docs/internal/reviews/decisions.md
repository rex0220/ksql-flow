裁定者: Takashi ／ 記録方式: kSQL エンジン側の裁定 Q1〜Q11 方式を踏襲。**裁定済み事項は再提案しない**（CLAUDE.md）。

## Q1. heartbeat と NO_DATA（2026-08-21 裁定）

- **裁定**: heartbeat は Exit 0 完了（`SUCCESS` / `NO_DATA`）で**送る**。設計書 3.2 の「通知しない」は失敗アラート（onFailure）に限定する読みを正とする。
- 理由: heartbeat の意味論は「完走したか」であり、通知抑制の目的は誤アラート防止。月次ジョブでは NO_DATA が常態のため、NO_DATA で送らないと dead man's switch が毎日誤発報する。
- 反映: 設計書 v2.6 §3.2 / README。実装変更なし（現実装どおり）。

## Q2. 依存停止伝播の判定（2026-08-21 裁定）

- **裁定（ホワイトリスト形式）**: 「**依存先が実行されるのは、依存元が `SUCCESS` または `NO_DATA` で終了した場合のみ。それ以外（`FAILED` / `ABORTED` / `TIMEOUT` / `SKIPPED` / `LOCKED`）はすべて `SKIPPED`**」。
- 理由: ブラックリスト列挙では漏れが再発する（レビュー時の列挙からも LOCKED 起因が漏れていた）。LOCKED は別プロセスが実行中で結果不明のため依存先を動かすべきでない。ホワイトリスト 1 文で未定義遷移が構造的に消える。
- 反映: 設計書 v2.6 §3.3。実装は現状挙動と一致 — 差し戻しは **LOCKED 起因の伝播テスト追加のみ**。

## Q3. チェックポイント縮退（2026-08-21 裁定・期限付き容認）

- **裁定**: エンジンがチャンクのキー値を公開するまで（依頼 E-1）、次の縮退を容認する:
  - `last_written_key` は `chunk:<書込チャンク数>` 形式
  - ログアプリへの反映は 25 チャンクごと or 60 秒ごと（毎チャンク更新は API 消費が倍増するため不採用）
  - ローカル JSONL には毎チャンク記録（障害調査の実用性はこちらで担保）
- **期限条件**: E-1 解消（エンジンがキー値を公開）時点で、キー値記録へ差し替え、本縮退記述を設計書から除去する。
- 更新間隔の config 化は**行わない**（設定項目の追加は実例が先行してから）。
- 反映: 設計書 v2.6 §5.1 / §8.2。受入判定は当面 `chunk:<n>` 形式で行う。
- **縮退解除（2026-08-22 / v3.70.0 / fix3）**: E-1 の `onChunkWritten` / `lastKeyValue` 公開により期限条件が成立した。`last_written_key` はキー値ベースへ差し替え、ログアプリの 25 チャンク/60 秒間引きとローカル JSONL 毎チャンク記録は維持する。キー値の意味は Q7 の「順序保証なしの診断情報」に従い、ウォーターマークには使用しない。
- 反映: 設計書 v2.7 §5.1 / §8.2、ランナー fix3。

## Q4. リトライ対象の 5xx 範囲（2026-08-21 裁定）

- **裁定**: リトライ対象は **429 / 500 / 502 / 503 / 504 / 520 / 522 / 524**（列挙方式を維持し、GW/CDN 系タイムアウトを追加）。「5xx 全般」は採用しない（501 / 505 等は再試行しても無駄）。
- 反映: 設計書 v2.6 §7.1。実装は `src/http.ts` の `RETRYABLE_STATUS` へ 504 / 522 / 524 を追加 + テスト。

## Q5. 単発 run のログレコード構成（2026-08-21 裁定）

- **裁定**: 単発 `run` は **JOB レコードのみ**（batch_id は発行・`parent_batch_id` 空・BATCH レコードは作らない）を正式仕様とする。
- **通知レシピ（README 推奨手順）**: kintone 標準通知は次の **2 条件の組**で設定する（複数条件設定で run-all は 1 通に集約・単発 run も漏れない）:
  1. `record_type = BATCH` かつ status が FAILED 系
  2. `record_type = JOB` かつ `parent_batch_id` が空 かつ status が FAILED 系
- 反映: 設計書 v2.6 §8.1 / §8.5 / README。実装変更なし。

## Q6. --resume の選抜規則と選抜実行の記録（2026-08-21 裁定）

- **裁定**: `--from` / `--only` の選抜実行では、**選抜外ジョブに `SKIPPED`（理由 filtered）の JOB レコードを残す**。これにより「JOB レコード不在 = クラッシュによる未着手 = `--resume` で再実行」の不変条件を維持する。
- **確認条件**（差し戻し時に必須）:
  - (a) `SKIPPED (filtered)` レコードは `job_key` を持たない（ロックに関与しない）
  - (b) filtered は依存伝播・通知・Exit 集約のいずれからも**中立**（10.3 の集約で 5 として扱わない。Q2 の伝播判定にも影響させない — filtered は「選抜外」であり依存判定上は満たされたものとして扱う）
  - 実装ノート: `--resume` が failure 起因 SKIPPED と filtered を判別できること（現行 `listBatchJobs` は status のみ取得のため、判別手段の追加が必要）
- 反映: 設計書 v2.6 §6 章。実装は小改修 + テスト。

## Q7. `last_written_key` の単調性前提の廃止（2026-08-22 裁定）

- **裁定**: エンジンへ DML のキー昇順整列を追加依頼しない。`last_written_key` は復旧ウォーターマークから、**最後に成功した書込チャンクの最終キー値（順序保証なし）という診断情報**へ再定義する。
- 理由: 整列は大規模データでメモリ・処理コストを増やす一方、得られるのは将来の途中再開拡張の前提だけである。現在の復旧戦略は §5.1-1 の冪等リランで完結している。
- 運用規則: `last_written_key` を単調な値、途中再開位置、処理済み範囲の上限として使用しない。キー値が取得できない操作はチャンク情報のみを診断用に残す。
- 反映: 設計書 v2.7 §5.1 / §8.2 / 付録 C、ランナー fix3。

## Q8. 限定的な自動 resume（案 F）の却下（2026-08-27 裁定）

- **裁定**: 固定時刻スロットで `--resume` を自動実行する案（`rerun_trigger_design.md` 案 F）は**却下**する。連載および仕様の方針「**スケジューラ側の自動リトライは使わない。復旧は冪等リランに一本化する**」は文言変更せず維持する。
- 理由:
  - 当日の定期実行が**そもそも起動しなかった**日、自動 resume は直近バッチ = **前日のバッチ**を拾い、前日の as-of で再実行する（`findLatestBatch` は `order by started_at desc limit 1`。`logapp.ts:300`）。安全に運用するには対象バッチ固定のガードが前提となり、「cron 1 行」の手軽さという唯一の利点が消える。
  - 「救えるのは #8 のクラス A（時間が解決する一時障害）だけ」という当初の想定も不正確だった。データが偶然直っていればクラス B も走り、原因未解消なら Exit 2 を再発させる。
  - 「失敗検知連動の再起動」と「独立スロットでの 1 回限りの resume」は技術的には区別できるが、運用上はいずれも**人間の判断を挟まずに外側から `--resume` する**仕組みであり、方針の実質的な変更にあたる。
- **再提案しない**。復旧の起動手段は案 B（kintone を指示キューにする）に一本化する。
- 反映: `rerun_trigger_design.md` v3 §5。仕様・記事の文言変更なし。

## Q9. リラン実行権限の実現手段（2026-08-27 裁定）

- **裁定**: リランの実行権限は **kintone 標準のアクセス権（アプリ / レコード / フィールド単位）で実現する**。ランナー側に権限機構を持たせない。
- 内訳:
  - 指示アプリの**レコード追加権限** = リランを起こせる人。運用側がグループを充てて決める（通知先グループと同一にするか分けるかは運用判断であり、設計上の制約としない）
  - **フィールド単位のアクセス権**で、依頼者に `状態` / `終了コード` / `実行バッチ ID` 等の結果フィールドを編集させない
  - VPS のトークンには指示アプリの**閲覧 + 編集**のみを与える（**レコード追加は不要**）
  - 「誰が指示したか」は、人間が kintone UI から追加する以上 `作成者` に自動で残る（ポーラーは編集のみなので `更新者` はトークン側になる）
- 理由: 指示キューを kintone アプリとして持つ設計の主眼は、**権限と証跡を kintone に委ねられること**にある。専用の権限モデルを持ち込むと、この利点が失われ二重管理になる。
- 反映: `rerun_trigger_design.md` v3 §4.7。実装変更なし（設計要件）。

## Q10. リラン指示は手動リランと同一動作とする（2026-08-27 裁定）

- **裁定**: kintone 指示キュー（`rerun_trigger_design.md` 案 B）から起動するリランは、**SSH で `./run_batch.sh --resume` を叩くのとまったく同じ動作**とする。起動手段だけを変え、**リランの意味論は変えない**。
  - 検討途中で必須要件としていた「指示に対象バッチ ID を持たせ、実行時の直近バッチと一致しなければ実行しない」は**撤回**する。
  - `git_ref` の突合も、実行を止める条件にはしない（**記録のみ**）。
  - ランナー側の仕様変更（`--resume-batch` / `--expect-batch` の追加）は**行わない**。
- 理由:
  - 対象バッチの「ずれ」は**手動リランにも等しく存在する**。土曜の失敗通知を見た担当者が日曜に SSH で resume すれば拾われるのは日曜のバッチであり、これは §6.3 および #7 で「resume で救えるのは次のスケジュールが来る前だけ」として**既に文書化した仕様**である。指示キューが新たに持ち込む欠陥ではない。
  - **キューのほうが窓は狭い**（ポーラー 5 分間隔 < 人間の反応時間）。より安全な経路により厳しい制約を課すことになる。
  - 起動手段ごとに動作が変わると、「スケジューラを変えても運用設計は変わらない」（#9）という連載・製品の一貫性が崩れる。
- **代替**: 指示が長く滞留したまま実行される懸念には、**指示の有効期限**（既定案 6 時間・超過は `期限切れ`）で対応する。これはリランの動作を変えるものではなく、受付側の規則である。
- 反映: `rerun_trigger_design.md` v4 §2・§2.1・§4.5・§4.7。仕様・実装の変更なし。

## Q11. リラン指示はログアプリのフィールドで行う（実行指示アプリを作らない）（2026-08-27 裁定）

- **裁定**: リランの指示は**既存の実行ログアプリの BATCH レコードにフィールドを足して**行う。専用の「実行指示アプリ」は**作らない**。
  - 失敗した BATCH レコードの `rerun_state` を人間が `要求` にすることが、リラン指示になる。
  - ポーラーは同レコードを revision 条件付きで確保し、結果を同レコードへ書き戻す。
- 理由（分離案の根拠 4 点がいずれも成立しないことを確認した）:
  - **権限の非対称性** → Q9 で採った**フィールド単位のアクセス権**で `rerun_state` だけを編集可にできる。同じ機構で解決するため分離の理由にならない。
  - **状態機械の分離** → 失敗した BATCH レコードは以後ランナーに触られない（実行のたびに `crypto.randomUUID()` で別レコードを作る）。`rerun_` 接頭辞でフィールドを分ければ足りる。
  - **通知ルールの分離** → #4 の 2 条件に足すだけで、分離を要するほどではない。
  - **API 枠の分離** → ポーリングは**リラン回数と無関係な固定コスト**（5 分間隔で 288 回/日 = 日次上限の約 3%）。ログアプリの枠が実際に逼迫するとすれば、それは実行回数自体が多いということであり、指示アプリの有無ではなく仕組み側の問題である。
- **技術的な前提の確認**: `checkLogAppCommand`（`src/commands/initLogapp.ts`）は**期待フィールドの存在と型のみを検査し、余分なフィールドを拒否しない**。したがってログアプリへの独自フィールド追加は `--check-logapp` を壊さない。ランナーの書込もフィールド指定であり、レコード全体を上書きしない。
- **利点**:
  - 新規アプリの構築（フィールド定義・アクセス権・通知設定）が不要になる。
  - 追加フィールドは 6〜7 個で済む。`profile` / `host` / `started_at` / `作成者` は BATCH レコードに既にあり、専用アプリの 14 フィールドの多くはその再現だった。
  - 失敗レコードを見ている人がそのレコードで要求するため、**profile / host の取り違えが構造的に起きない**。
  - 失敗・要求・結果が同一レコードに並び、`batch_id` での突合が不要になる。
- **スコープ外の確認**: BATCH レコード自体が存在しない事故（「起動しなかった事故」）は指示を貼る先がないが、`--resume` はそもそも直近バッチの記録が無ければ Exit 1 で失敗するため、指示アプリ方式でも救えない。両案に差はない。
- **将来**: API 枠を分けたい規模になった場合に限り、第 2 段階で指示アプリへの分離を再検討する。
- 反映: `rerun_trigger_design.md` v5、`rerun_trigger_implementation_plan.md` の §4 以降。仕様・ランナー実装の変更なし。

### Q11 追補（2026-08-27・Codex の v5 レビューを受けた訂正）

**裁定の結論（ログアプリ統合）は維持**する。ただし当初の理由づけに次の不正確があったため訂正する。

- **「既存 24 フィールド」は誤り。** `LOG_APP_FIELDS` は **23** フィールド。追加後は 31。
- **「失敗した BATCH レコードは以後触られない」は無条件には成り立たない。** `resendPending()` が前回失敗したログ書込を次回実行時に同じレコードへ再送し、`recoverStale()` も RUNNING を更新する。いずれも revision 条件なし。ただし**ランナーは `rerun_*` を一切書かない**ため、リラン状態が壊れる経路は無い。影響は claim 後の結果書込が revision 競合で失敗しうるという**可用性の問題**に限られ、再 GET + 1 回再適用で扱う。
- **「API 枠はリラン回数と無関係」は固定費のみを指した不正確な表現。** 待機ポーリング 288 回/日は固定だが、リラン 1 回あたり claim PUT・結果 PUT・BATCH 照合 GET で 3〜4 回増える。結論（枠は問題にならない）は変わらない。

**Codex が追加提起した「トークン漏えい時の影響範囲を制御キューに閉じ込められる」は、分離の根拠として採らない。** ポーラーは VPS 上で動き、その `.env` にはランナー用のログアプリ書込トークンが既に存在する。同一マシンでログアプリを書き換える能力はすでにあり、分離案では `.env` にトークンが 2 本になるぶん露出面はむしろ増える。

**設計側で対応する不備**（`rerun_trigger_design.md` v6 に反映済み）:

1. 有効期限の基準を `rerun_requested_at` フィールドに変更。`更新日時` を基準にすると **Exit 5 で `要求` へ戻すたびに期限が延びる**。
2. `init-logapp` は `rerun_*` を作らず `--check-logapp` も不足を検出しないため、**ポーラー側が自前の check** を持つ（ランナーは変更しない）。
3. stale 回収を通常の claim と別処理に分離し、`要求` を受け付ける `status` を失敗系（FAILED / ABORTED / TIMEOUT）に限定する。
4. `rerun_batch_id` の確定規則（0 件 = resume 対象なしで BATCH 未作成 / 2 件以上 = cron 割り込みで帰属不明）を設計に明記する。
5. `rerun_state` の既定は「空という選択肢」ではなく**未選択**と定義する。

**未検証事項**: フィールド単位のアクセス権が API トークンにも適用されるか。効かない場合でも露出面の結論は変わらないが、権限設定手順の記述は実挙動に合わせる。

### Q11 追補 2（2026-08-27・API トークンの権限モデル確定）

**確定事項**: kintone の **API トークンは Administrator 相当の権限で動作し、フィールド単位のアクセス権の対象外**である（追補 1 の「未検証事項」はこれで解消）。

帰結と対応:

1. **ポーラーのトークンを `rerun_*` だけに制限することはできない。** これは受容する。VPS の `.env` にはランナー用のログアプリ書込トークンが既にあり、同じ能力がすでに存在するためである。**専用アプリに分離しても同じ**で、そちらのトークンが Administrator 相当になるだけなので、この点は Q11 の結論に影響しない（むしろ分離不要の根拠が 1 つ増える）。
2. **「誰が要求できるか」の制御は無傷。** フィールド単位のアクセス権は**実ユーザーには効く**ため、「実ユーザーは `rerun_state` だけ編集可」は成立する。効かないのはトークン側だけで、そこは元から書込可能だった。
3. **要求者の証跡が `更新者` に残らない問題が判明した。** トークン操作の `更新者` は Administrator になるため、ポーラーが結果を書き戻した時点で「人間が要求した」という記録が上書きされる。対策として **`rerun_requested_by` フィールドを新設**し、`rerun_requested_at` と同様に**初回確保時（ポーラーがまだ触っていない時点）に `更新者` を退避**する。変更履歴に依存しない恒久的な証跡とする。

追加フィールドは 8 → **9** になる（ログアプリは 23 → 32 フィールド）。

反映: `rerun_trigger_design.md` v6 §4.3・§4.4・§4.6・§4.10。

### Q11 追補 3（2026-08-27・`rerun_state` の値体系）

**`rerun_state` の選択肢は、日本語ではなく大文字 ASCII の識別子とする。**

- 同一アプリ内で `status` が `SUCCESS` / `NO_DATA` / `FAILED` / `ABORTED` / `SKIPPED` / `RUNNING` / `TIMEOUT`、`record_type` が `BATCH` / `JOB` である以上、`rerun_state` だけ日本語では体系が割れる。
- クエリ・ログ・スクリプトでの扱いも識別子のほうが安全。表示上の分かりやすさはフィールドラベルと一覧の設定で担保する。
- 値: `REQUESTED`（人間が設定）/ `CLAIMED` / `SUCCESS` / `FAILED` / `UNKNOWN` / `EXPIRED` / `CANCELED`。既定は**未選択**。
- `SUCCESS` / `FAILED` は `status` と同じ語を意図的に再利用する（意味も一致する）。実行中は `status` の `RUNNING` と紛れるため **`CLAIMED`** とし、`rerun_claimed_host` / `rerun_claim_expires_at` と語を揃えた。

あわせて、追加フィールドは既存と同じく**フィールドコードは小文字スネークケース・ラベルは日本語**とする（`status` / ステータス、`batch_id` / バッチ実行ID と同じ）。

反映: `rerun_trigger_design.md` v6 §4.3・§4.3.1 および状態を参照する全節。

## Q12. リラン要求はチェックボックスで行う（2026-08-27 裁定）

- **裁定**: リランの要求は、ドロップダウン `rerun_state` を人間が `REQUESTED` にするのではなく、**専用のチェックボックス `rerun_request`（選択肢 `REQUEST` 1 つ）にチェックを入れる**ことで行う。`rerun_state` は**ポーラーだけが書く**フィールドとし、依頼者には閲覧のみを与える。
- 理由:
  - **フィールド単位のアクセス権は「そのフィールドを編集できるか」しか制御できず、どの選択肢を選べるかは制御できない。** `rerun_state` を依頼者に編集させると、ドロップダウンの 7 値すべてを書けてしまう。実行していないのに `SUCCESS` を選べば**リランが成功したように見える記録が残り**、`CLAIMED` を選べばポーラーが stale とみなして `UNKNOWN` へ倒す。Q9 で「権限は kintone のアクセス権で実現する」と決めた以上、**アクセス権で守れる形にフィールドを設計する**必要がある。
  - チェックボックスは値が「入っている / いない」の 2 通りしかないため、**誤った値を書く事故が構造的に起きない**。
  - 操作もチェック 1 つで済み、スマホから押しやすい（この設計の動機そのもの）。
- **不変条件**: **チェックが入っている = まだ終端に至っていない要求。** ポーラーは終端状態（`SUCCESS` / `FAILED` / `UNKNOWN` / `EXPIRED` / `CANCELED`）にするとき必ずチェックを外す。Exit 5 の差し戻しだけはチェックを付けたまま `rerun_state = REQUESTED` にする。
  - この不変条件により、候補クエリは「チェックが入っている」1 条件で済む。
  - 再要求は、人間がもう一度チェックを入れるだけでよい（`rerun_state` が終端値のままチェックが入っていれば、ポーラーは新規要求として前回結果をクリアし、要求時刻・要求者を取り直す）。
- **`rerun_state` の `REQUESTED`** は人間が設定する値ではなくなり、**Exit 5 からの継続要求を表すポーラー側のマーカー**に意味が変わる。
- 影響: 追加フィールドは 9 → **10**（ログアプリは 23 → 33）。滞留通知の条件は「チェックが入ったまま `rerun_state` が未選択または `REQUESTED`」に変わる。
- 反映: `rerun_trigger_design.md` v7 §4.1・§4.3・§4.3.0・§4.3.1・§4.4・§4.5・§4.6・§4.9。`my-ksql-jobs/dev/add_rerun_fields.console.js`。実装計画は要改訂。

## Q13. 実行時 SQL エラーの Exit Code と契約 v1 `SQL_ERROR` の定義（2026-08-30 裁定）

- **経緯**: Execution Contract v1（PROPOSED）§4.2 は `SQL_ERROR` を FAILED/Exit 3 と定義していたが、公開仕様 7.1 と `src/errors.ts` `classifyRuntimeError()` は実行時 SQL エラーも Exit 1 に分類しており、「`executionStarted = true` かつ Exit 1」の失敗を契約の安定コードで表現できなかった（`docs/kSQL-FlowからkSQL-FlowNetへの返信-20260830-M1疑義.md` 疑義 1）。
- **裁定（オーナー承認済み）**: kSQL-Flow 側提案どおり**契約側を修正**。`SQL_ERROR` = FAILED/**Exit 1**（`executionStarted` は到達状況どおり）、`VALIDATION_ERROR` = SQL 開始前限定（`executionStarted = false` 必須）。Exit 1 は resultCode + `executionStarted` で判別する。実行時 SQL エラーの Exit 3 再分類案は互換性条件（Exit Code 維持）に抵触するため不採用。
- **反映**: ksql-flownet main `c95cbc4`（契約 §4.2/§12・変更点一覧 §3・draft schema・fixture `sql-error.json`）。本リポジトリは `docs/internal/flow_m1_execution_contract_task.md` §3 の変換表と `schema/execution-result-v1.schema.json`（実装時）へ反映する。裁定文書: `docs/kSQL-FlowNetからの返信-20260830-M1疑義裁定.md`。
- 付随合意: orchestrator モード 4 オプションの全か無か規則・§13 予告 11 項目に異議なし。補足 3 点（result-json 一意パスは FlowNet 責務 / schema 正本は kSQL-Flow 同梱版で `$id`+contract version を含め capabilities から参照可能に / 既存 `job_key` 系の制約は変えない）。

## Q14. FlowNet 固有のログアプリ設定（確認用一覧・相関フィールド ACL）の配布境界（2026-08-30 裁定）

- **裁定**: ksql-flow 同梱の `template/ksql-flow-log-template1.zip` には v0.4 の相関フィールド・CANCELLED 選択肢までを収録し、**一覧「FlowNet相関確認」と相関 5 フィールドの Everyone=閲覧のみ ACL は収録しない**。これらは orchestrator（kSQL-FlowNet）導入時のみ意味を持つ設定であり、(a) 既存アプリへは同梱 Console スクリプト 2 本で適用、(b) **FlowNet 新規導入時のログアプリは FlowNet 側配布テンプレート（ログアプリ同梱・一覧/ACL 設定済み）で作成する**役割分担とする。
- 理由: kintone テンプレートは新規アプリ作成専用で既存アプリへ適用できない（スクリプト経路はどのみち必須）。standalone 製品のテンプレートに orchestrator 固有の運用設定を持ち込まない境界が明確になる。FlowNet 側テンプレートの元は、検証アプリ（v0.4 + 一覧 + ACL 適用済み）のエクスポートを使用できる。
- 反映: `template/README.md`「テンプレートに含まれない設定」4 項、完了報告 §2 JOB 相関移行行。FlowNet へは完了報告でログアプリ同梱テンプレートの整備を提案。
