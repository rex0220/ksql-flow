## BLOCKER 1 — cron 例が営業時間・平日限定で、設計の動機を打ち消している

**該当**: §9

```cron
*/5 7-20 * * 1-5 /opt/ksql/my-ksql-jobs/scripts/poll_control.sh ...
```

この設計が解こうとしている問題は、`rerun_trigger_design.md` §1 に書いたとおり **「休日・外出先で、通知は届くのに直せない」** ことである。平日 7〜20 時限定のポーリングは、**その状況でだけ動かない**。

さらに §5.2 の有効期限（既定 21,600 秒 = 6 時間）と組み合わさると、失敗する。

* 土曜 9:00 に指示を追加 → 次のポーリングは月曜 7:00
* 6 時間の有効期限は土曜 15:00 に切れている
* 月曜 7:00 のポーラーは `期限切れ` にするだけで、**何も実行しない**

つまり **MVP の既定構成のままでは、動機となった週末のケースを一度も救えない**。

**修正案**: 既定を `*/5 * * * *`（終日・288 回/日）とする。API は指示アプリ専用枠（スタンダード 10,000 回/日）に載るため **2.9%** であり、終日でも余裕がある。営業時間限定は「そう運用したい場合の選択肢」として副次的に書く。

営業時間限定を残す場合は、**有効期限をポーリング空白時間より長く取る**制約（例: 週末を挟むなら 72 時間以上）を §5.2 に明記し、両者が独立に設定できてしまわないよう起動時検証に含めること。

## MINOR 2 — ポーラーの `git rev-parse` は不要（ランナーが既に記録している）

**該当**: §6.2「`git rev-parse` は cwd を固定して argv 配列で実行し、hash だけ検証」／§8.1 最終項

`runAll.ts:200` で、ランナー自身が BATCH レコードに `git_ref: resolveGitRef(dir)` を記録している。ポーラーが claim 前に別途 `git` を起動する必要はない。

* §4.7 の裁定（Q10）により `git_ref` は**記録のみで実行可否に使わない**のだから、claim 前に取る必要がそもそもない
* §6.2 は Exit 5 以外でどのみちログアプリを 1 回 GET する。その `fields` に `git_ref` を足せば **API 消費ゼロ**で取れる
* 子プロセス起動が 1 つ減り、§8.1 で守るべき攻撃面も 1 つ減る

**修正案**: `executed_git_ref` はログアプリの BATCH レコードから取得する。ポーラーからの `git` 起動は削除する。

## MINOR 3 — Exit 1 の固定文言が実態と食い違う経路がある

**該当**: §6.1 の固定辞書「`設定または検証エラーで終了しました。VPS の設定とジョブを確認してください。`」

`runAll.ts:94` のとおり、`--resume` は **「直近バッチの実行記録が見つからない」場合にも `EXIT.VALIDATION`（1）を返す**。

```
out("エラー: --resume に必要な直近バッチの実行記録が見つかりません（ログアプリ・profile 別 state とも）");
return EXIT.VALIDATION;
```

これは設定ミスではなく、ログアプリに記録が無いという運用状態である。固定文言は依頼者を「VPS の設定を見ろ」という誤った方向へ誘導する。

**修正案**: Exit 1 の文言を、原因を断定しない形に改める。例:

> `リランを開始できませんでした（設定・検証エラー、または再開できる直近バッチが見つかりません）。実行ログアプリを確認してください。`

## MINOR 4 — 実行バッチ照合の帰属ミスの可能性が残る

**該当**: §6.2「claim 後の started_at に合う最新 BATCH の batch_id を取得」

2 点ある。

1. **resume で対象が無かった場合、BATCH レコードは作られない。** `runAll.ts:105` が `return EXIT.OK` するのは BATCH レコード作成（同 190 行付近）より前である。§10.1 に「該当なしは空欄で安全に完了すること」とあるので**扱いは正しい**が、計画本文に理由が書かれていないため、実装者が「取れないのは異常」と誤解しうる。1 行の注記を推奨する
2. **claim 後に定期 cron のバッチが割り込むと、最新 BATCH がポーラーのものでない可能性がある。** `host` と `profile` では区別できない（同一ホスト・同一 profile のため）。実害は `log_url` が別バッチを指すことに限られるが、§6.2 に「同一条件の BATCH が複数ある場合は帰属を断定せず空欄にする」等の縮退規則を書いておくべき

## MINOR 5 — GitHub Actions（#6）との関係が計画に無い

**該当**: 計画全体（`Actions` の語が 1 度も出てこない）

配備先の多くは #6 のワークフローを併用している。運用手順に次を含めること。

* **ワークフローファイルの変更は不要**（`daily-batch.yml` / `pr-check.yml` とも）
* **案 A（Actions を復旧用に併用）は不要になる。** #9 で「復旧用に `workflow_dispatch` を残すなら書込可トークンを GitHub Secrets にも置く必要があり、露出面が減るという利点とのトレードオフ」と書いた。案 B があれば **GitHub には閲覧のみトークンだけ**という構成が完全に成立する
* **定期実行の主は 1 つに決める。** Actions の `daily-batch` と VPS の cron を両方有効にすると二重スケジュールになる。ポーラーが加わって起動経路が 4 つ（cron・ポーラー・Actions・SSH）になるため、運用手順で明示する。なお衝突自体は分散ロック（Exit 5）が止め、ポーラーは `target_host` でルーティングされるので Actions が指示を拾うことはない
