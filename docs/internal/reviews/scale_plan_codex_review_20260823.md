## [BLOCKER] 2. 現行実装では L の 20,000 件 GROUP BY が既定上限 10,000 件で止まる

- 根拠:
  - `docs/ksql_flow_spec.md` §11 は、単純 GROUP BY を逐次集約・行数上限対象外と規定。
  - エンジン `src/execute.ts` の通常 SELECT/FULL_SCAN は `options.maxRecords ?? 10_000` を使用。
  - `src/core/optimization/sharedPlanner.ts` 21–38 行は `fetchAll()` で全取得しており、ページごとの逐次集約ではない。
  - kSQL Flow `src/executor.ts` 206–215 行は `tempTableMaxRows` は渡すが、`maxRecords` を渡していない。
- 問題:
  - `maxTempRows=200000` にしても、TEMP TABLE 出力上限が増えるだけで、物理アプリの読取上限 10,000 件は増えない。
  - L の GROUP BY は、ストリーミング実証以前に `FetchAllLimitError` 相当で停止する可能性が高い。
  - 現行コード上、「2万件を通せばストリーミングを実証できる」という前提は成立しない。
- 修正案:
  - 実施前にエンジン課題として起票し、次のどちらかを解決条件にする。
    1. 単純 GROUP BY の真のページ逐次集約を実装する。
    2. kSQL Flow が `maxRecords` を明示設定でき、L で20,000超を許容できるようにする。
  - 解決までは L を「既知上限の検出試験」と位置付け、性能目標の実証とは呼ばない。

## [BLOCKER] 3. 中断リラン手順が単発 run と run-all を混同している

- 根拠:
  - 企画書 §4 観点8、§9-3。
  - `docs/ksql_flow_spec.md` §6.1–6.3: `--resume` は直近の run-all バッチを再開する機能。
  - 同 §8.1: 単発 `run` は JOB レコードのみで、BATCH レコードを作らない。
  - 同 §5.5: Ctrl+C 等で残った RUNNING は `batchTimeoutSec` 経過または `unlock` まで分散ロックになる。
- 問題:
  - 単発 `run` を Ctrl+C した直後に `run-all --resume` しても、その単発実行は resume 元バッチにならない。
  - 単発を即時再実行しても、RUNNING の分散ロックが残っていれば LOCKED になる。
  - 単発再実行は元 as-of を自動継承しない。
- 修正案:
  - 試験を明確に2本へ分ける。
    1. **単発 run**: 明示 `--as-of` → 中断 → RUNNING確認 → `unlock` または stale 待ち → 同じ `--as-of` で再実行。
    2. **run-all**: run-all 中断 → BATCH/JOB RUNNING確認 → `unlock` または stale 待ち → `run-all --resume` → 元 as-of 継承確認。
  - `unlock` は同一 profile の全 RUNNING を解除するため、専用 profile を使うことも前提に加える。

## [MAJOR] 11. 突合SELECTは実現可能だが、現記述では欠落を0行成功と誤判定する

- 根拠:
  - 企画書 §3、§4-1。
  - 売上期待式 `10 × i × 1000 + 55` 自体は正しい。
- 問題:
  - `WHERE 実績<>期待値` だけでは、会社レコード自体が欠落した場合、その会社は結果に現れず「不一致0行」になる。
  - INNER JOINによる突合も、片側欠落を落としてしまう。
  - 案件側10件、顧客側1件、余分な会社0件のすべてを見るには単純なSELECTでは足りない。
- 修正案:
  - 1 SQL文にこだわるなら、CTE/UNIONで次を同時に返す。
    - 会社ごとの件数・合計不一致。
    - 期待会社総数Nとの不一致を返すsentinel行。
    - 案件側のみ／顧客側のみの欠落。
    - プレフィックス内の余分な会社。
  - S実施前に実際の突合SQLを企画書へ掲載し、`validate` まで通す。
  - 全体期待売上も記載すると検算しやすい。  
    `10000 × N(N+1)/2 + 55N`、Lでは `20,010,110,000`。
