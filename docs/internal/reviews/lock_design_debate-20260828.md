## 当方の譲歩

- **A を全面受諾**: 「同じ入力から同じ値」は回収経路で誤り — 回収側は**新しい as-of** を固定するため、旧保持者と異なる値を同一キーに書く。結果は「ログ SUCCESS・データは古い as-of」の**沈黙した陳腐化**。保証範囲に「**as-of 非依存のジョブに限る**」を追加。冪等性は「壊れない」を保証し「新しい」を保証しない
- **終了時 1 回の自己検査を受諾**（1 GET/実行・「実態より強い SUCCESS」を消す最小コスト。事実 4 により必要性は確定）
- **C の分類変更を受諾**: 重複起因 400 + 再検索 0 件 → Exit 5（競合の敗北・自己修復・静か）。実装メモ: 重複違反コードの判別には応答 body の code を通す配管が必要（現状は HTTP status のみ）
- **E はほぼ合意**: runId 単体センチネル（26 字・`job_key_done` 維持）で当方の反対 2 点は解消。`releaseMode`（既定 clear）を v0.5 選択肢として受諾。ただし優先度は低 — 追加論拠: **空値重複禁止の遡及施行は既存全アプリを壊すため現実に不可能**（ユニーク制約の空値除外は SQL NULL 意味論に通じる標準）。現実的な破れ方は新規フィールドからの挙動変更
- **P の差し替え案を採用**: 推測でなく**新しい観測**（古い値で like ヒット → 本体の中身が新旧どちらかを見る）にすれば引用条件の外。Drill 4 として採用し、結果を持ってエンジンへ相談

## 統合（新しい発見）

**心拍化（B 変種 + タイマー化）は 3 つの問題を同時に改善する**:
- A の窓（検知がマージン数分に縮む）
- **F の非対称**（解放失敗で残った RUNNING は心拍が止まる → 別ホストからの復旧が batchTimeoutSec 待ちからマージン待ちへ）

記事の構造文として採用価値: 「**ローカル層の救済（生存確認・pending 再送）はすべてホストスコープ。分散ロックだけがグローバル。ホストをまたいだ復旧は必ずタイムアウトに落ちる — だから batchTimeoutSec はチューニングで消せない最後の砦であり、それを縮める唯一の道が心拍**」

# 第 4 ラウンド（Codex 評価 NEEDS-CORRECTION への応答・2026-08-28）

## 当方の誤りの承認

1. **冒頭総括の矛盾（最重要）**: 「静かにデータが壊れる経路はひとつもない」は問題 1 と自己矛盾。DELETE の存在と複数文ジョブの交互適用により、リース窓の実害は鮮度に限定できず**古戻り・混在（torn state）・誤削除**があり得る。正しい総括: 「構造破壊は抑えられているが、リース窓では業務データの整合性障害があり得る。保証はタイムアウト内・stale 回収なしの範囲に限る」
2. **自己検査の過大評価**: SUCCESS 直前の検査は監査証跡しか守らず TOCTOU も残る。対策格上げ: **finishRecord/recoverStale の revision 条件付き PUT 化**（競合時は判別 GET 1 回 → 回収なら新規 ABORTED・自レコード不変更）。ポーラーで実証済みのパターンの移植
3. **心拍化「根本」の言い過ぎ**: 窓短縮でありフェンシングではない。補強: エンジンが onChunkWritten を await する事実（executor.ts:201）により、**revision 条件付き心拍の失敗を throw して以後のチャンクを中断**は実装可能（飛行中は不可）。要件（BATCH/JOB 両心拍・maxApiCalls 算入・ハード期限維持・タイマー多重発火防止）を起票に含める
4. **as-of の場合分け**: `--resume` 経由の回収は as-of を引き継ぎ新旧同値 → 実害消滅。危険なのは「次回定期実行が回収」経路に特定
5. **Exit 5 化の有界化**: 無条件は D（ACL 不可視）の恒久設定不良を静かに隠す。初回 Exit 5 → 連続 N 回で警告/Exit 3 昇格 + validate に ACL 検査
6. **実測証拠の誤帰属**: ドリル 7 は claim PUT（revision）の競合・ドリル 5 は逐次競合であり、**job_key 同時 INSERT の実測は未実施**。#11 実験③の記述は Drill 1 実施まで書けない（記事公開の前提に追加）
7. **job_key 値域は「小物」でなく確定欠陥**（コード裏取り済み: jobs.ts:33 は名前を無検査採用・キーは素の連結）: `__batch__` 予約衝突・`:` の曖昧性・64 文字検査なし → **validate 追加を v0.5 先頭へ**
8. **スコープ 3 点**（ローカルは cwd 単位・同一 profile 別ジョブのローカル直列化・単発 run とバッチロックの非対称）を記事の限定として受諾

# 第 5 ラウンド（最終・2026-08-28）— Codex 残修正 3 点の受諾とオーナー裁定方針

## Codex 残修正の受諾（討論記録の表現を本節で上書き）

1. 「TOCTOU ごと消える」→ **「revision 条件化が防ぐのはログレコードの終了・回収競合の TOCTOU。業務 DML のフェンシングにはならない」**
2. 「--resume なら実害消滅」→ **「同一 as-of かつ入力が as-of で決定的・全書込が冪等のジョブではリスクが縮小する。同時実行自体の安全性は保証しない」**
3. 「心拍失敗で以後のチャンクを中断」→ **「次の文/チャンク境界で中断可能。飛行中の処理に停止保証なし」**（onChunkWritten はチャンク完了後のコールバック。実装には leaseLost フラグ + 各境界での検査が必要）

追加受諾: 心拍・チェックポイント・finishRecord の**自己 PUT 直列化**が必要（自分同士の 409）・**pending 再送に取得時 revision を保存**しないと証跡上書きの穴・`job_key` 検査は **validate 専用にせず buildJobKey 共通不変条件**（run/run-all でも Exit 1）・ACL 全件閲覧は静的検証不能（運用前提 + 疎通検査 + 連続 Exit 5 監視の組合せ）・Drill 1 のバリアは postRecords 直前。

## オーナー裁定方針（2026-08-28）

前提: **しくみで全エラーケースはカバーできない。複雑な機構は想定外のエラーで足かせになる。しくみはシンプルに保ち、リカバリー方法を明確にする。**

この前提での再仕分け:

- **「運用・ジョブ設計でカバーできない明らかな設計誤り」は 1 件のみ**: `job_key` の入力無検査（誤解を招く壊れ方をするため。修正は数行）
- **リース窓・TIMEOUT 上書き・競合誤通知は運用カバー可能** — 検知（TIMEOUT 条件通知は既存・ハングはリマインダーでコードゼロ）+ リカバリー（リラン 1 回で収束・期間窓はバックフィル・厳密確認は #3 の突合ツール）が既に揃っている
- **心拍化の要件連鎖**（タイマー化 → 自己直列化 → pending への revision 伝搬 → API 予算 → 多重発火防止、それでも飛行中は止まらない）は、オーナー前提の「複雑さが足かせになる」の実例。**冪等リラン + as-of 固定が最終防衛線**である以上、半端なフェンシングの費用対効果は成立しない

# 第 6 ラウンド（Codex 最終判定 GO WITH CONDITIONS・2026-08-28）— 条件の全面受諾

## 結論の言い換え（採用）

「明らかな設計誤りは 1 件のみ・それ以外は問題なし」→ **「確定したコード欠陥は `job_key` 無検査の 1 件。それとは別に、stale 自動回収には意図して受容する残余リスクが 1 群あり、適用条件と復旧手順で管理する」**

## 受諾した条件

1. **ランブック必須**（「TIMEOUT を見たらリラン」では不足 — 収束後に旧保持者が復帰し再古戻りし得る）: ①スケジュール一時停止 → ②ログの host/batch_id/started_at で旧保持者特定 → ③旧ホストでプロセス停止確認 → ④生存なら停止し業務書込停止を確認 → ⑤unlock → ⑥同 as-of resume / バックフィル / 全量再計算 → ⑦突合 → ⑧再開。停止確認不能時の縮退: リランを重ねない・静穏期間を置く・最後に全量再計算 + 突合
2. **TIMEOUT 通知の成立条件を明記**: 更新は「次の実行が回収した時点」（logapp.ts:161）。次回起動がなければ RUNNING のまま・旧保持者の SUCCESS 上書きで証跡が消え得る → **長時間 RUNNING リマインダーは必須の運用構成**（推奨から格上げ）
3. **ジョブ二分類を文書化**: 自動 stale 回収を許容できるジョブ（全量再計算/キー付き UPSERT・as-of 決定的・冪等・突合可能・DELETE なし）/ 危険なジョブ（DELETE 含む・外部状態依存・非冪等・全量再計算なし）→ 後者は `batchTimeoutSec` を null/十分長く・profile 分離・死亡確認後の手動 unlock のみ
4. **job_key ガードの追加条件**: v0.5 CHANGELOG に名前制約の追加を移行案内として記載・JS `.length` と kintone 文字数の Unicode 一致（サロゲートペア/絵文字）を境界テストで確認
5. **記事 #11 の必須撤回**: 「同時 INSERT を実測」「必ず 1 件」「実行もちょうど 1 回」・#10 ドリルを job_key 競合の証拠とする記述。代替文言: 「既存ロックへの後発衝突は実測済み。バリア同期した同時 INSERT は未実測であり、公式に CAS として保証された API ではない」
