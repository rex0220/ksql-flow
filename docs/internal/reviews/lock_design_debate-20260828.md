| A. stale 回収の二重実行窓 | **受諾（記事の「ちょうど 1 回」は claim 競合・タイムアウト内に限定すべき）** | リース方式に普遍の窓。ただし本系では書込が UPSERT + as-of 固定で決定的なため、二重ライタの実害は一般系より小さい — 正しさの砦はロックでなく冪等性（#7）。DELETE 含みや非冪等ジョブでは実害化しうる |
| A' フェンシング（毎チャンク自己検査） | **異議** | チャンク毎 GET は #5 で削除した事前 GET と同型のコスト再導入（XL +100 GET）。B' に相乗りが正 |
| B. ハートビート | **変種を採用推奨（v0.5 最有力）** | 新フィールド不要 — ランナーは既に 25 チャンク/60 秒のチェックポイント PUT をしており（Q3）、RUNNING の `更新日時` が実質心拍。stale 判定を「`更新日時` + マージン」基準へ変えるだけで長時間実行と高速検知が両立。チェックポイント応答への相乗りで自己検査（A の中断シグナル）も安価 |

## バックログ（優先度順・実施は別途判断）

1. **仕様 §5.5 の表現改訂**: 「ロック」→「リース（時限付き占有）」・保証範囲の明文化（claim 競合とタイムアウト内は 1 実行・stale 回収経路には理論的な窓）・運用前提（NTP / レコード ACL 禁止 / トークン全件閲覧）
2. **v0.5 候補: stale 判定を `更新日時`（チェックポイント心拍）基準へ** + チェックポイント応答での自己検査（回収されたら ABORTED）+ 回収 PUT の revision 条件化
3. **規約 2 行の拡張**（my-ksql-jobs CLAUDE.md）: バッチ単位の KLIKE 分離・更新系 WHERE の KLIKE 禁止
4. validate: `job_key` 長の検査（重複禁止フィールドの上限値は要実測確認）
5. unlock の `--force` ガード / 解放失敗の警告通知 / 連続 LOCKED 通知
6. 次回ドリル: バリア同期の一斉 INSERT・stale 二重回収競合
7. kintone 側レシピ: `RUNNING` 長時間のリマインダーでハング検知（コード不要）
8. #12 伏線: コンテナでの PID 再利用とローカルロックの限界
