# 第 2 ラウンド（2026-08-28・レビュアーの撤回 4 件と派生問題への応答）

## レビュアー側の撤回（記録）

G（前提誤り: run-all はジョブ個別ロックを取得）・C の「未定義」・F 後半（pending 再送の順序）・stale 二重回収の構造的安全性 — いずれも撤回を受領。

## コードで確定した事実（当方の裏取り）

1. **チェックポイントはチャンク境界評価**（executor.ts:170 — 60 秒条件は `onChunkWritten` 内で判定）。**書込前の問い合わせフェーズでは心拍が出ない** → 心拍化の前提にタイマー化が必要（レビュアー指摘どおり）
2. **ジョブロックとバッチロックの stale 閾値は同一の `batchTimeoutSec`**（executor.ts:140 / runAll.ts:204）→ G 派生（5 分ジョブのハング回収が 3 時間後）は現実装の事実
3. **stale 回収は `$id` 固定**（`recoverStale(record)` → `update(record.id, ...)`）— 「判定と対象の同一性」は実装済み。Drill 2 は e2e 裏取りとして維持
4. **`finishRecord` は revision 条件なしの無条件 UPDATE** → Drill 3 の観測 (b)「TIMEOUT レコードへの SUCCESS 上書き」は現実装の確定挙動

## 当方の譲歩

- **A を全面受諾**: 「同じ入力から同じ値」は回収経路で誤り — 回収側は**新しい as-of** を固定するため、旧保持者と異なる値を同一キーに書く。結果は「ログ SUCCESS・データは古い as-of」の**沈黙した陳腐化**。保証範囲に「**as-of 非依存のジョブに限る**」を追加。冪等性は「壊れない」を保証し「新しい」を保証しない
- **終了時 1 回の自己検査を受諾**（1 GET/実行・「実態より強い SUCCESS」を消す最小コスト。事実 4 により必要性は確定）
- **C の分類変更を受諾**: 重複起因 400 + 再検索 0 件 → Exit 5（競合の敗北・自己修復・静か）。実装メモ: 重複違反コードの判別には応答 body の code を通す配管が必要（現状は HTTP status のみ）
- **E はほぼ合意**: runId 単体センチネル（26 字・`job_key_done` 維持）で当方の反対 2 点は解消。`releaseMode`（既定 clear）を v0.5 選択肢として受諾。ただし優先度は低 — 追加論拠: **空値重複禁止の遡及施行は既存全アプリを壊すため現実に不可能**（ユニーク制約の空値除外は SQL NULL 意味論に通じる標準）。現実的な破れ方は新規フィールドからの挙動変更
- **P の差し替え案を採用**: 推測でなく**新しい観測**（古い値で like ヒット → 本体の中身が新旧どちらかを見る）にすれば引用条件の外。Drill 4 として採用し、結果を持ってエンジンへ相談

## 統合（新しい発見）

**心拍化（B 変種 + タイマー化）は 3 つの問題を同時に改善する**:
- A の窓（検知がマージン数分に縮む）
- **F の非対称**（解放失敗で残った RUNNING は心拍が止まる → 別ホストからの復旧が batchTimeoutSec 待ちからマージン待ちへ）
- G 派生（スコープに関係なく「心拍停止 + マージン」で判定 — 定数分離が不要になる）

記事の構造文として採用価値: 「**ローカル層の救済（生存確認・pending 再送）はすべてホストスコープ。分散ロックだけがグローバル。ホストをまたいだ復旧は必ずタイムアウトに落ちる — だから batchTimeoutSec はチューニングで消せない最後の砦であり、それを縮める唯一の道が心拍**」

追加 caveat の受諾: 心拍マージンは max(タイマー間隔×3, 429 バックオフ上限)。`更新日時` の良性更新問題は本運用では #10 の ACL（全フィールド Everyone 閲覧のみ）が構造的にほぼ塞いでいる（rerun_request チェック → 5 分内 CANCELED の有界 2 回のみ）。チェックポイント PUT の revision 条件化 + conflict 時のみ判別 GET、も受諾。
