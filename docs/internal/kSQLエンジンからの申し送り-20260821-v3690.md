## 2. ランナーが依存する公式 API `@rex0220/kintone-sql-tools/flow`

semver 対象。**文単位実行**（設計書 §3.8 の要件）に対応しています。

```ts
import {
  parseScript, validateScript, explainScript,
  createExecutionContext, executeStatement, disposeExecutionContext,
  createKintoneClient, KsqlFlowError, version,
} from "@rex0220/kintone-sql-tools/flow";

parseScript(source, { apps })            // → { meta, statements, statementRanges, diagnostics }
await validateScript(source, { apps, strict, schema | client })  // → Diagnostic[]（行・列付き）
await explainScript(source, { client, apps, ... })               // → 推定 API 消費行を含む計画

const client = createKintoneClient({ baseUrl, auth: { type: "apiToken", apiToken }, ... });
const ctx = createExecutionContext({ client, script: source, apps, asOf, timezone, ... });
try {
  for (const stmt of statements) {
    const r = await executeStatement(stmt, ctx);
    // r.kind: "STATEMENT" | "ASSERT_PASSED" | "ASSERT_WARNING" | "ASSERT_VIOLATION" | "EXIT_NO_DATA"
    // EXIT 成立後の文は skipped（skippedReason: "exit"）で返る＝正常終了として集計する
  }
} finally {
  await disposeExecutionContext(ctx);   // キャッシュ・カーソルの解放
}
```

- `asOf` / `timezone`（IANA 名）で **§5.3 のバックフィル**を実現できます（省略時は実行開始時刻・ホスト TZ）
- `createKintoneClient` は fetch ベース（Node 18+）。apiToken（アプリ別コールバック可）/ password 認証・guestSpaceId・timeout 対応
- ExecutionContext は**逐次専用**（並行 executeStatement・dispose 後利用は明示エラー）
- 既存 `/engine`（read-only）は不変です

## 3. 設計書の前提訂正（重要 — 実装調査で判明した事実）

### 3.1 `SELECT ... INTO #t` は存在しない（§3.7 の対応表）

エンジンの既存正は **`CREATE TEMP TABLE #x AS SELECT ...`** です。dialect 1 の `CREATE TEMP TABLE x AS`（裸名）はこれへの正規化で、書き味には影響ありません。設計書 §3.7 の対応表の**右列（正規化先）を `CREATE TEMP TABLE #x AS ...` に訂正**してください。

### 3.2 `bulkRequest` はエンジン未実装（§5.1-4・§11）

書込チャンクは **100 件/リクエストのみ**です。したがって:

- 原子性の単位は 1 リクエスト（100 件）であり、「1 bulkRequest = 2,000 件」の記述は現状成立しません
- チェックポイント（`last_written_key`）の粒度も 100 件単位になります
- EXPLAIN の推定 API 消費も `ceil(N/100)` の HTTP リクエスト数で数えます（bulkRequest 導入時に推定式ごと更新予定。エンジン側課題台帳では M5 として保留中）

### 3.3 サブテーブル DML はエンジンでは可能（§3.4）

「kintone API の仕様上サブテーブル行を単独で INSERT / UPDATE できない」は、エンジンが**親レコード経由で既に解決済み**です（`INSERT INTO APPn$tbl` 等は dialect 0 の正式機能）。dialect 1 での禁止は**方針としてのゲート**（validate エラー `KSQL1304`）であり、将来「親レコード経由のテーブル一括更新構文」を検討する際は既存実装を流用できます。

### 3.4 UPSERT は kintone updateKey API を使っていない（§3.4）

実装は **read-then-write**（`GET records.json` で照合 → POST / PUT・キー多重ヒット時は最大 `$id` を選択）です。したがって updateKey 検証（重複禁止・文字列(1行)/数値）は API の技術的必然ではなく、**非 unique キーでの upsert 先の曖昧さを塞ぐ方針上のチェック**として実装しています。dialect 1 では validate（`KSQL1301`〜`KSQL1303`）に加え、**実行時にも書込 API の前に fail-closed** で検査します（実行前は重複禁止設定を確認できない場合もエラー）。

### 3.5 「dialect 0 で ASSERT → エラー」の読み替え（受入 5(d)）

`ASSERT <式> <比較> <式>` は dialect 0 の既存機能のため、そのままでは後方互換と矛盾しました。**「dialect 0 で Flow 形式（`, 'msg'` / `WARN`）のみエラー・既存形式は不変」**へ読み替えて実装しています（エンジン側オーナー裁定 Q1）。

## 4. ランナー実装時の注意点

- **文数上限**: 1 スクリプト **20 文**（`MAX_BATCH_STATEMENTS`）。実ジョブで超える例が出たら引き上げを再裁定します（裁定 Q8）— 超過事例が出たらエンジン側へ連絡してください
- **`@` なし時刻関数**（`TODAY()` / `THIS_MONTH()` 等）は kintone サーバー評価のため **as-of の対象外**。dialect 1 の WHERE で使うと警告（`KSQL1306`）が出ます。設計書の見本 SQL は `@` 付きへ統一することを推奨します
- **MCP `ksql_validate` はネットワーク 0** の契約です。updateKey の schema 依存検証は載りません — ランナーの `validate` コマンドは `/flow` の `validateScript(source, { client })` を使えばフル検証になります
- **`strict`**（素の INSERT をエラー化・§5.2）は `validateScript` の opts と MCP `ksql_validate` の入力の両方にあります
- 診断コード一覧は言語リファレンス §27.6（`KSQL1001`〜`KSQL1306`）。コードは公開契約として維持します
- `depends_on` / `timeout` はエンジンでは**解析のみ**（値制約検証あり）。実行制御はランナー側の責務のままです

## 5. 残す論点（エンジン側の把握事項）

- bulkRequest（3.2）を導入する場合はエンジン側で別起票（工数追加）
- `--as-of` の CLI フラグはエンジン CLI には載せていません（`/flow` オプションのみ）。ランナー CLI が自前のフラグから `asOf` へ渡す想定です
