## 0. まず重要な訂正 2 件（ランナー側の対応が必要）

依頼書を実測レビューした結果、**ランナーの現行実装の前提に誤りが 2 つ**見つかりました。

1. **E-5: 「metrics の前回値との差分」は v3.69.0 では機能していません**。`StatementResult.metrics` は
   ミュータブルな共有参照だったため、**保持した過去の metrics も後続実行で進み、差分は常にゼロ**でした。
   v3.70.0 で**累積値のスナップショット返却**へ安全化したので、**v3.70.0 以降は**「前回スナップショット
   との差分＝文単位の消費」が意図どおり計算できます。ランナーの集計ロジックが v3.69.0 で
   期待値になっていたかの確認を推奨します（api_calls の値がバッチ末尾の累積 × 文数になっていた可能性）。
2. **E-1 併記質問への回答: 書込はキー昇順に整列されていません**。INSERT は VALUES / SELECT の入力順、
   UPSERT は入力順のまま **INSERT 全チャンク → UPDATE 全チャンク**の順で送信します。UPDATE / DELETE は
   対象取得が `$id` 昇順のため結果的にレコード ID 順ですが、**業務キー順ではありません**。
   コアでの整列は CLI / MCP / プラグインの書込順まで変えるため「追加的変更のみ」に収まらず、
   今回は実施しません。**設計書 5.1-2 の `last_written_key` 単調性の前提はランナー側で再裁定してください**
   （「チャンク単位の観測値」としては E-1 のコールバックで足ります。単調性だけが成立しません）。

## 1. E-6: `explainScript` の as-of（対応済み・v3.70.0）

- `ExplainScriptOptions` に `asOf?: Date` / `timezone?: string` を追加しました。規則は
  `createExecutionContext` と同一（呼出開始時に 1 回固定・省略時は現在時刻・ホスト TZ）
- 実装は planner（`buildBatchExplainPlans`）冒頭への一括注入のため、**CLI batch dry-run・
  MCP 複文 `ksql_explain`・プラグイン batch EXPLAIN も同時に解消**しています（既定値で動作）
- 受入基準（`monthly_sales_sync.sql` を `explainScript(source, { client, apps, asOf, timezone })` で
  推定取得）はテストで固定済み。**`dryrun.ts` のテキスト置換回避策は撤去できます**
- 補足: 未注入時の内部エラーに U+0000 付き内部変数名が露出していたのも利用者向け文言へ正規化しました
  （依頼書のエラー例は制御文字が脱落した表記でした）

## 2. E-3: DML 結果型の公開（対応済み・v3.70.0 — ただし形は依頼書と異なる）

依頼書の `{ type, insertedCount, updatedCount, deletedCount }` という共通形は**実装と一致しません**。
実際の形を正確に写した **discriminated union** を公開しました:

```ts
import { isDmlResult, type FlowDmlResult } from "@rex0220/kintone-sql-tools/flow";

type FlowDmlResult =
  | { type: "INSERT"; createdIds: string[]; insertedCount: number }
  | { type: "UPDATE"; updatedCount: number }
  | { type: "DELETE"; deletedCount: number }
  | { type: "UPSERT"; insertedCount: number; updatedCount: number };

if (isDmlResult(result.result)) {
  // result.result.type で分岐して written_count を集計する
}
```

- **`written_count` の集計は `type` ごとの分岐が必要**です（UPDATE に `insertedCount` はありません）
- APPLY / IMPORT 実行時に載る追加フィールドは**安定契約外**です（型コメントに明記）
- `StatementResult.result` の宣言は `unknown` のままです（型を狭めると利用側の構築コードに
  破壊が及ぶため）。`isDmlResult` ガード経由で利用してください

## 3. E-5: metrics のスナップショット化（対応済み・v3.70.0）

§0-1 のとおり、「共有参照＋利用側で差分」ではなく**エンジン側でスナップショット返却**に変更しました。

- `StatementResult.metrics` と dispose 時の最終 metrics は**その時点の累積値のコピー**です
- 文単位の消費＝「今回のスナップショット − 前回のスナップショット」で計算できます
- context 内部の累積・`/engine` の挙動は不変です

## 4. E-4: `KsqlFlowError.code` の値域（回答）

**現状、値域全体は公開・安定契約ではありません**。`code` は Error の `name`・メッセージ先頭の
`XxxError:` 接頭辞・kintone 応答の `code`・fallback の `FLOW_ERROR` から動的に決まる `string` です。

- **安定に依存してよいもの**: エンジンの既存エラー接頭辞（`ParseError` / `ArgumentError` /
  `AssertError` 等＝dialect 0 から続く公開実績のある値）と、`/flow` が明示生成する
  `ExecutionContextDisposedError`。これらは変えない運用です（既存の code 契約と同じ扱い）
- **依存すべきでないもの**: kintone 由来の code（kintone 側の仕様に従属）・上記以外の動的値
- ランナーのエラー分類が HTTP status ベースで完結しているなら現状のままで十分です。
  表示・ログの安定化のために **literal union 化（エンジン所有 code の列挙）が必要になったら
  再依頼してください**（小〜中の作業・lifecycle エラーの正規化統一を含めて設計します）

## 5. E-1: 書込チャンクの観測（対応済み・v3.70.0＝コールバック方式）

```ts
createExecutionContext({
  client, script, apps,
  onChunkWritten: async (info) => {
    // info: { statementIndex, appId, operation: "INSERT"|"UPDATE"|"DELETE",
    //         records, chunkIndex, lastKeyValue? }
    await saveCheckpoint(info);   // await されます（永続化完了まで次チャンクへ進まない）
  },
});
```

仕様（重要な境界）:

- **発火＝書込 API（POST / PUT / DELETE）1 リクエストの成功直後**。`Promise` を返せば await します
- **コールバックの throw はその文の実行エラー**になります。ただし**通知対象チャンクは書込済み**です
  （チェックポイント保存失敗時のリカバリはランナーの責務＝冪等リランで回復する設計のままにしてください）
- `chunkIndex` は 0 始まり・**文内の全書込リクエスト通算**（操作種別ごとにリセットしません）
- `lastKeyValue` は**単一キー UPSERT のみ**設定（そのチャンク最後のレコードのキー値）。INSERT VALUES /
  UPDATE / DELETE では `undefined` です
- `appId` は LAPP 解決後の**物理アプリ ID** です
- metrics 方式でなくコールバック方式にした理由: チャンクごとの履歴が必要（最終値だけでは 3 チャンクを
  復元できない）・E-5 の共有参照問題と絡めない・逐次専用 context と発火順序が素直に整合するため
- 受入基準（250 件 UPSERT で 3 チャンクの観測）はテストで固定済み。**Q3 縮退の解除条件は満たしています**
  （ただし §0-2 のとおり `last_written_key` の**単調性は成立しない**ので、ログ項目の意味を
  「最後に書いたチャンクの末尾キー（順序保証なし）」へ改める再裁定とセットで解除してください）
