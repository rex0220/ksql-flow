## 0. 原則

1. **読むだけのレビューは不可。必ず動かす**: テストを実行し、受け入れ基準のシナリオを可能な範囲で再現する。動かせない場合はその旨を明記し、机上確認である旨を指摘に付す。
2. **仕様の正は設計書 v2.5**。実装が設計書と食い違う場合、正しいのはどちらかを自分で決めない — 指摘として挙げ、裁定は Takashi。裁定結果は `docs/reviews/` の裁定ログに残す（kSQL エンジン側の裁定 Q1〜Q11 方式を踏襲）。
3. **実装コードを直接修正しない**。修正は実装担当（Codex）に差し戻す。ただし指摘には再現手順・期待値・該当する設計書の節番号を必ず付け、修正が一意に決まる粒度まで具体化する。
4. スタイルの好みは指摘しない。lint / 既存規約に反する場合のみ MINOR で挙げる。

## 1. レビュー観点（この順で・毎回全観点）

### A. 仕様適合

* `flow_runner_task.md` §6 の受け入れ基準 1〜9 が**テストで実証**されているか（実装済みマイルストーン分のみ）。基準を満たすテストが存在しない場合は、それ自体を MAJOR とする。
* §3 の結果種別 → ステータス / Exit Code 変換表との完全一致。特に `NO_DATA` = Exit 0・通知なし、`ASSERT_WARNING` = 続行 + log_detail 記録。
* v2.5 の前提訂正が実装に正しく効いているか: 100 件チャンク粒度のチェックポイント、20 文上限の表面化、`@` なし時刻関数の警告の取り回し。

### B. 安全性（このプロジェクトで最も重い観点）

* **fail-closed の実証**: ログアプリ到達不能・ロック INSERT 失敗・env 未解決・config 不備の各ケースで、**書き込み系 API が 1 回も呼ばれずに**停止することをテストか再現で確認する。
* **秘密情報の漏えい**: トークン・パスワード・証明書パスワードが、正常ログ・エラー・例外スタック・デバッグ出力・JSONL のどこにも現れないこと。例外オブジェクトに client 設定が同梱されて漏れるパターンに特に注意。
* **外部通信の限定**: 通信先が (1) 設定された kintone、(2) 設定された Webhook のみであること（設計書 12 章）。依存パッケージ経由の想定外通信も含めて確認。
* **排他の実質**: ロック取得と RUNNING INSERT の間の競合窓、stale 回収の誤回収（生きているプロセスのロックを回収しないか）、`--force-unlock` 後の整合。

### C. エラーパスとリカバリ

* リトライ対象（429 / 5xx / タイムアウト）と非対象（認証・4xx）の分類が `KsqlFlowError` の実物と整合しているか。
* 部分適用後の `FAILED` で、`last_written_key` / `written_count` がログに正しく残り、`--resume` が設計どおり動くか。
* JSONL フォールバックの再送: 再送自体が失敗した場合・再送と新規実行が重なった場合の挙動。

### D. テストの実効性

* テストが実装の写経になっていないか（モックが実装と同じ仮定を共有していて、実 API との齟齬を検出できない構造は MAJOR）。
* 結合テストがエンジン実体（`file:../kintone-sql-tools`）を使っているか。エンジンの pin バージョンと互換表の整合。
* 境界値: 0 件・1 件・100 件・101 件・20 文・21 文。

### E. 依存とスコープ

* エンジンの公式 API `/flow` 以外（内部パス）を import していないこと（BLOCKER）。
* `flow_runner_task.md` §1.2 のスコープ外機能（bulkRequest 前提の実装など）が紛れ込んでいないこと。
* 新規依存パッケージの妥当性（MIT 互換ライセンス・メンテ状況・本当に必要か）。

## 2. 出力形式

`docs/reviews/code_review_claudecode-M<n>-YYYYMMDD.md` として:

```
## 指摘 N: <一行要約>
- 重大度: BLOCKER（安全性・仕様違反）/ MAJOR（欠陥・テスト不備）/ MINOR（軽微）
- 観点: A〜E
- 該当: <ファイル:行> ／ 根拠: 設計書 §x.y または flow_runner_task.md §z
- 再現/確認手順: <実行したコマンドと結果。机上のみの場合はその旨>
- 期待値: <どうなるべきか>
```

末尾に「実行したテスト・再現シナリオの一覧」「裁定が必要な項目」「総合判定（マイルストーン通過可否）」を付ける。**BLOCKER が 1 件でもあれば通過不可**。

## 3. 往復の運用

指摘 → Codex 修正 → 再レビュー（修正差分と該当テストのみで良い）。3 往復して収束しない論点は裁定に上げる。裁定結果は `docs/reviews/decisions.md` に Q 番号で追記し、以後のレビューで再指摘しない。
