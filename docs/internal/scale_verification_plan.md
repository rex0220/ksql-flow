# レコード増加 3 段階検証 企画（S: 200 / M: 2,000 / L: 20,000）

- 起案日: 2026-08-23（起案: Claude Code、裁定: Takashi）
- 状態: **企画（未実施）**
- 対象: kSQL Flow v0.1.0 + kintone-sql-tools v3.72.0
- 実施場所: dev 環境（SFA パック 4245〜4249。実ドメインは記載しない）

## 1. 背景と目的

- 記事 #2（AI 連携編）の実走で、レコード追加・更新まわりの課題を複数摘出した（VALUES の as-of 制約 → F-2 で解決、ルックアップの参照先データ・トークン併送、ASSERT 比較バグ → F-1 で解決）。**少数件の実行だけでこれだけ出た**以上、実データの追加・更新・削除の実行回数がまだ少ないことが現在の最大リスク
- 公開仕様書 11 章の性能・API 目標（読取 1 万 → 書込 1 千: 1 分以内・約 35 回 / 読取 10 万 → 書込 1 万: 10 分以内・約 305 回）は「**未保証の設計目標値（実測値ではない）**」のまま公開されている
- スケジュール実行（記事 #3 = 毎朝の無人運用）に載せる前に、**対象レコード数の増大に対する挙動を実機で検証**し、目標値を実測で裏付ける（または修正する）

## 2. 規約（Phase 0 検証記録 §1 を継承）

- 書き込みは **`KSQL-FLOW-TEST-` プレフィックスのレコードのみ**。cleanup で漏れなく削除できる設計にする
- 実ドメイン・トークンをリポジトリ内のあらゆるファイルに書かない
- 書込を伴う実行はすべて人間（書込可トークンはセッション限定環境変数）。Claude Code は観測・突合・記録を担当

## 3. データ設計

| 段階 | 案件件数 | 会社数 | 会社あたり案件 | 主な狙い |
| --- | --- | --- | --- | --- |
| S | 200 | 20 | 10 | 基準線。少数件で全観点の計測手順を確立 |
| M | 2,000 | 200 | 10 | 読取カーソル（500 件/回）・書込チャンク（100 件/回）が複数回転する最小規模 |
| L | 20,000 | 2,000 | 10 | 仕様 11 章の目標値スケール・チェックポイント/中断リランの実証 |

- **期待値は式で決める**: 会社 `KSQL-FLOW-TEST-C<i>`（i = 1..N）の案件 j（j = 1..10）の売上を `i * 1000 + j` とすると、会社 i の期待合計 = `10 * i * 1000 + 55`、期待件数 = 10。全社の突合が SELECT 1 本で機械判定できる
- 受注予定日はすべて `@TODAY()`（as-of 基準で当月に入る）
- ルックアップ制約により**先に顧客管理へ会社を UPSERT**（記事 #2 で確立した順序）

### 投入（シード）方式 — 実装時に選定

| 案 | 方法 | 見込み | 懸念 |
| --- | --- | --- | --- |
| a | 倍加 INSERT ... SELECT（自己複製を繰り返す） | ジョブだけで完結・API 効率良 | 売上の式が単純倍加では作れない（要工夫） |
| b | CLI の `IMPORT INTO ... FROM CSV`（エンジン公式機能） | 式どおりの値を CSV 生成で正確に投入・100 件/POST | flow ジョブ外のツール併用になる |
| c | 生成スクリプトで INSERT ... SELECT 文を組み立て | 柔軟 | 文数上限 20 文/スクリプトに注意 |

推奨は **b（CSV IMPORT）**: 期待値式をそのまま CSV に落とせて突合が単純になる。CSV 生成スクリプトは `dev/` に同梱し、cleanup は既存方式（プレフィックス削除。L では 200 リクエスト規模になるため DELETE も計測対象に含める）。

## 4. 検証観点

### 全段階共通（S/M/L）

| # | 観点 | 合否基準 |
| --- | --- | --- |
| 1 | **結果の正しさ** | 全社の件数・合計が期待式と完全一致（突合クエリの不一致 0 行） |
| 2 | **API 消費** | 実測 = EXPLAIN の分解形見積と一致（読取 ceil(N/500)・書込 ceil(社数/100) + UPSERT 事前 GET + ログ・ロック）。乖離があれば原因を特定 |
| 3 | **実行時間** | S/M は数十秒以内、L は仕様 11 章スケール比（読取 2 万 + 書込 2 千 ≒ 目標 2〜3 分圏）。`timeout: 600` 内 |
| 4 | **dry-run の正確性** | 差分件数（UPDATE/INSERT 社数）が本実行結果と一致・書込 0 件・previewStatement の所要時間記録 |
| 5 | **ログアプリ記録** | read_count / written_count / api_calls が実測と一致。L ではチェックポイント（100 件/チャンク・25 チャンクまたは 60 秒間隔）の進捗更新を観測 |
| 6 | **削除（cleanup）のスケール** | プレフィックス削除が全件消えること・DELETE の API 消費とガード（件数 ASSERT は段階に合わせ引き上げ）動作 |

### L 限定（+必要なら M でも）

| # | 観点 | 内容 |
| --- | --- | --- |
| 7 | **インメモリ上限の挙動** | 単純 GROUP BY はストリーミング逐次集約で「行数上限の対象外」（仕様 11 章）のはず — 2 万件で実証。あわせて `limits.maxTempRows` を意図的に小さく設定した変形ジョブで**明示エラーの安全停止**（fail-closed）を確認 |
| 8 | **中断 → 冪等リラン** | 書込チャンク途中で強制中断（Ctrl+C）→ ログアプリの RUNNING/チェックポイント記録を確認 → 同一 as-of でリラン → 最終状態が一発成功時と完全一致（重複・欠落なし）することを突合で証明 |
| 9 | **maxApiCalls の強制** | 見積の 7 割程度に `maxApiCalls` を設定して実行 → 上限到達で安全停止・ログ記録・その後のリラン収束を確認 |
| 10 | **429/5xx の観測** | 発生すればリトライ（指数バックオフ + Retry-After）の実動作を記録（発生しなければ「発生せず」を記録） |

## 6. 手順（段階ごとの定型）

1. `seed`（人間）→ 件数確認（Claude Code: MCP で COUNT 突合）
2. `EXPLAIN` で分解形見積を記録（推定 API・押し下げ確認）
3. `npm run dry-run` — 時間・API・差分件数を記録
4. `npm run job` 本実行（人間）— 時間・API・exit code を記録
5. 突合クエリで全社一致を機械判定
6. （L のみ）観点 7〜9 の追加試験
7. `cleanup`（人間）→ 残存 0 件確認
8. 実測を `verification/scale-notes.md` に追記（コマンド・数値・ログアプリのレコード ID）

**進行ゲート**: S 合格 → M 着手、M 合格 → L 着手。不合格・想定外挙動は原因特定し、エンジン起因は F 系で起票（F-1/F-2 と同じ流儀）、ランナー起因は修正してから次段階へ。

## 8. リスクと対策

- **dev アプリの肥大・レコード番号消費**: cleanup 徹底。L のサイクル数を絞る
- **日次 API 枠の圧迫**: §5 の予算内で計画実行。他検証と同日に重ねない
- **長時間実行中の環境要因**（PC スリープ・ネットワーク断）: L 本実行時は電源設定を確認。中断はむしろ観点 8 の素材として記録
- **実データへの影響**: 書込はテストプレフィックスのみ。既存 276 件の実データには読取しか行わない
