## 1. 背景と目的

- 記事 #2 の実走で、レコード追加・更新まわりの課題を複数摘出（F-1/F-2 で解決、ルックアップの罠 2 件）。**少数件でこれだけ出た**以上、実データ DML の実行回数不足が最大リスク
- 公開仕様書 11 章の性能・API 目標は「未保証の設計目標値」のまま。さらに Codex レビューで**ストリーミング集約の記述が実装と乖離**していることが判明（F-3 起票済み）
- スケジュール実行（#4 = 毎朝の無人運用）に載せる前に、規模増大時の挙動を実測し、目標値を「特定環境での参考実測」として裏付ける（または修正する）
- **実測記録はそのまま連載 #3 の Qiita 記事として公開する**（§10）。後から撮り直せない素材（初見の失敗ログ・中断の瞬間・429）ほど価値が高い

## 2. 規約と検証専用ジョブ

- 書き込みは **`KSQL-FLOW-TEST-` プレフィックスのレコードのみ**。実ドメイン・トークン非記載。書込実行は人間（書込可トークンはセッション限定環境変数）
- **検証専用の profile を用意する**（`unlock` は同一 profile の全 RUNNING を解除するため、通常利用と分離）

### 2.1 検証専用ジョブ（B1 対応）

既存の `jobs/monthly_deal_summary.sql` は当月の**全**案件を集計するため、当月に実案件があると実顧客を更新してしまう。検証では使わず、**全文をテストスコープに限定した専用ジョブ**を作る:

- `dev/scale_deal_summary.sql` — ASSERT・集計・UPSERT のすべてに `会社名 LIKE 'KSQL-FLOW-TEST-C%'` 相当のスコープを付けた集計ジョブ
- `dev/scale_touch_update.sql` — テスト案件 20,000 件への UPDATE（§3.3 の書込大ジョブ）
- **dry-run の合否基準に「プレフィックス外の INSERT/UPDATE/DELETE が 0 件」を全段階で追加**

## 3. データ設計

### 3.1 段階と期待値

| 段階 | 案件件数 | 会社数 | 会社あたり | 主な狙い |
| --- | --- | --- | --- | --- |
| S | 200 | 20 | 10 | 基準線・手順確立（+境界値補助ケース） |
| M | 2,000 | 200 | 10 | 読取カーソル・書込チャンクの複数回転 |
| L | 20,000 | 2,000 | 10 | 上限系・中断リラン・maxApiCalls |
| XL | **100,000** | 10,000 | 10 | **仕様 11 章の公表目標「読取 10 万 → 書込 1 万・10 分以内」と同スケールの実測**。F-3 回答 §5 でエンジンから依頼された「10 万段階の実測共有」への回答。サポート目安 100,000 の実証（2026-08-23 追加・Takashi 指示） |

- **検証全体で固定 as-of を最初に 1 つ決める**（例: 実施日の `T00:00:00+09:00`）。seed の日付・全実行・突合・リランのすべてで同一 as-of を明示指定し記録する（M5 対応）
- 会社 `KSQL-FLOW-TEST-C<i>`（i=1..N）の案件 j（j=1..10）の売上 = `i*1000 + j` → 会社 i の期待合計 = `10*i*1000 + 55`・期待件数 = 10
- 全体検算値も記録: 総売上 = `10000*N(N+1)/2 + 55N`（L: **20,010,110,000**）

### 3.2 シード方式（確定: エンジン CLI の CSV IMPORT）

- 使うのは kSQL Flow ではなく**エンジン側 CLI `ksql`** の `IMPORT INTO ... FROM CSV`（`--import-csv <name>=<path>`）
- 前提整備（S の前に **10 件スモーク**で全て確認）:
  - IMPORT capability gate の有効化・`--allow-dml`・非対話実行
  - L 用に `--max-records 20000` / `--dml-max-rows 20000`
  - CSV は固定 as-of から導出した**実日付** `YYYY-MM-DD` を生成（`@TODAY()` は CSV に書けない）。生成スクリプトと CSV の件数・サイズ（10 MiB 制限検査）・ハッシュを記録
  - エンジン CLI 用の接続設定（認証・アプリ対応・ルックアップ先トークン併送）をテンプレートの config と別に用意し、互換を実測確認
- 顧客（会社）は先行 UPSERT（ルックアップ制約）。シードは再実行安全に設計

### 3.3 書込大ジョブ（M8 対応・L の中断/チェックポイント試験用）

集計ジョブの書込は 2,000 社 = 20 チャンクしかなく、チェックポイント（25 チャンクまたは 60 秒）が発火しない。そこで書込側のスケールは専用ジョブで検証する:

- `dev/scale_touch_update.sql`: テスト案件 20,000 件の `詳細` 等を UPDATE（= **200 チャンク**・冪等）
- チェックポイント発火（ログアプリの進捗更新・`last_written_key`）、中断リラン、maxApiCalls 試験はこのジョブで実施

## 4. 検証観点

### 4.1 全段階共通（S/M/L）

| # | 観点 | 合否基準（R2） |
| --- | --- | --- |
| 1 | 結果の正しさ | 突合 SQL（CTE/UNION で ①会社別の件数・合計不一致 ②期待会社総数との差の sentinel 行 ③案件側のみ/顧客側のみの欠落 ④プレフィックス内の余剰会社、を同時検出）が**全 0 行**。突合 SQL は S 実施前に確定し validate を通す |
| 2 | API 消費 | 実測が**文単位の EXPLAIN 見積範囲内 + ランナー固定費（ログ・ロック・再送）の別加算**で説明でき、差分の全リクエストに説明が付く。`--json` 出力・HTTP カウンタ・ログアプリ `api_calls` の 3 点を比較 |
| 3 | 実行時間・資源 | **ウォームアップ 1 回 + 計測 3 回**の中央値・最小・最大。INSERT 初回と UPDATE 再実行は別計測。Node 最大 RSS/heap・版数（flow/engine/Node/OS）・commit・回線・実行時刻を記録。仕様書へは「特定環境での参考実測」として掲載 |
| 4 | dry-run | 差分件数が本実行結果と一致・書込 0 件・**プレフィックス外の書込 0 件**・所要時間記録 |
| 5 | ログアプリ記録 | read_count / written_count / api_calls が実測と一致 |
| 6 | cleanup | **案件 → 顧客の順**で削除。削除前 ASSERT は「段階の期待値と完全一致」（上限以下では不足・余剰を検出できない）。削除後は**両アプリ別々に 0 件確認**。DELETE の API 消費（ID 取得読取含む）も計測対象 |
| 7 | 成功 → 成功の再実行 | 同一 as-of で本実行をもう 1 回 → 最終状態不変を突合で確認（written_count は初回と同じになり得ることを合否に明記） |
| 8 | 境界値（S の補助 1 ケース） | 読取 501 件または書込 101 件を 1 回だけ実施し、API が 2 回に割れることを確認 |

### 4.2 L 限定

| # | 観点 | 内容 |
| --- | --- | --- |
| L-9 | 読取上限 | 2 ケース: ①未指定（既定 10,000）で 20,000 読取が `FetchAllLimitError` の明示エラーで安全停止 ②`maxReadRows: 25000` + `maxTempRows: 25000` で完走（エンジン回答 §2 のモック実証の実機版。片方だけの設定で失敗点が移動することも 1 回観測して記録） |
| L-10 | maxTempRows | 2 ケースに分離: ①集計ジョブ（出力 2,000 行）が TEMP 出力上限に影響されないこと ②明細 SELECT 等で `maxTempRows+1` 行を実体化させ**明示エラーの安全停止**を確認。RSS 採取（「メモリ一定」の主張は F-3 案 B 対応まではしない） |
| L-11 | 中断 → リラン（**2 本立て**・書込大ジョブで実施） | ①**単発 run**: 明示 `--as-of` → 書込途中 Ctrl+C → ログアプリ RUNNING + `last_written_key` 確認 → `unlock`（または stale 待ち） → **同一 --as-of で再実行** → 突合一致。②**run-all**: 中断 → BATCH/JOB の RUNNING 確認 → `unlock` → `run-all --resume` → **元 as-of の自動継承**を確認 → 突合一致 |
| L-12 | maxApiCalls | 停止位置を式で設定: `固定費 + 読取 + 事前GET + 書込 k チャンク + 1`（k は事前計算・書込途中で止める）。合否に「直後はローカル JSONL/pending 退避・ログアプリは RUNNING のまま」「次回実行時に再送されて解消」の**状態遷移**を含める |
| L-13 | 429/5xx | 実機では**観測のみ**（発生の有無と挙動を記録。「発生せず」も記録）。リトライ機能自体の合否は既存の HTTP モック試験の証跡を記事に併記する形にする |

### 4.3 無人運用ゲート（#4 タスクスケジューラ編へ進む前提・最小 3 点）

1. **二重起動**: 同一 profile・同一ジョブの並行実行が Exit 5 で即終了する（実機）
2. **通知**: 失敗時 Webhook と成功 heartbeat が実際に届く（1 回ずつ）
3. **実行環境**: スケジューラ実行を想定したアカウント/別シェルで、環境変数・作業ディレクトリ・`.ksql` 書込権限込みで同一コマンドが成功する

（stale ロック回収・タイムゾーン・ディスク等の残りは #4 の記事内で扱う）

## 5. API 予算（R2 再見積り・kintone 目安: 1 アプリ 1 日 10,000 回）

UPSERT の事前 GET は 50 キー/回、cleanup の ID 取得読取・metadata・ログ/ロックを含めて再計算:

| 段階 | seed | dry-run | 本実行 | 突合 | cleanup | 1 サイクル概算 |
| --- | --- | --- | --- | --- | --- | --- |
| S | 〜12 | 〜10 | 〜14 | 〜6 | 〜14 | **〜60** |
| M | 〜35 | 〜18 | 〜35 | 〜10 | 〜40 | **〜140** |
| L（集計系） | 〜260 | 〜85 | 〜110 | 〜45 | 〜270 | **〜800** |
| L（書込大ジョブ 1 回） | — | 〜45 | 〜250 | — | — | **〜300** |
| XL（集計系・実測補正済み係数で換算） | 〜1,310 | 〜430 | 〜530 | 〜740 | 〜1,330 | **〜4,300** |
| XL（書込大 1 回） | — | 〜230 | 〜1,230 | — | — | **〜1,460** |

- **XL は 1 日 1 サイクル厳守**（案件管理 1 アプリで日次目安 1 万回の約半分を消費）。計測 3 回は集計のみ・touch/cleanup は各 1 回。limits: `maxReadRows/maxTempRows 120,000・batchTimeoutSec 7200`

- 記録は**アプリ別 × 操作別**の内訳表にする（1 アプリ上限との比較に総和だけを使わない）
- L はリラン・中断試験込みで 1 日 **約 1,500〜2,000 回**を上限予算とし、1 日 1 サイクル

## 6. 手順

0. **準備**: 固定 as-of 決定 → `verification/scale-notes.md` の**記録スキーマを先に作る**（batch_id とスクショ・一次ログの対応付け） → 突合 SQL 確定 + validate → シード 10 件スモーク（§3.2 の前提全確認）
0'. **precheck（各段階の seed 直前に必須）**: `out/<tier>/precheck.sql` で `KSQL-FLOW-TEST-` 名前空間の残存 0 件を確認（非 0 なら停止して片付け）。検証期間中はこの名前空間を本検証が専有する — SMOKE 1 回目で他世代残存による突合誤検出が実際に発生（scale-notes 参照）
1. 各段階の定型: seed → 件数確認 → EXPLAIN 記録 → dry-run（プレフィックス外 0 件確認込み） → 本実行（計測 3 回・§4-3） → 突合 → 同一 as-of 再実行（観点 7） → cleanup → 記録
2. S では境界値補助ケース（観点 8）を追加
3. L では集計系（L-9/L-10）→ 書込大ジョブ（チェックポイント観測 → L-11 ①② → L-12）の順
4. 最後に無人運用ゲート 3 点（§4.3）
5. **進行ゲート**: S 合格 → M、M 合格 → L。不合格はエンジン起因なら F 系起票・ランナー起因なら修正後に再開

3. S → M → L 実測 — EXPLAIN 見積 vs 実測（API・時間の中央値）の対比表（アプリ別内訳）
4. ハイライト①: 仕様書の目標値 vs 実測（読取上限に当たった話 = **F-3 起票 → エンジン対応**の物語も含む）
5. ハイライト②: **強制切断 → 冪等リラン**（単発 run と run-all --resume の 2 本。RUNNING/last_written_key/unlock/元 as-of 継承の実画面）
6. fail-closed の実演 — maxApiCalls 停止と pending 再送の状態遷移・maxTempRows 超過
7. 見つかった課題と起票（F-1/F-2/F-3 に続く「実測 → 起票 → 修正」の物語）
8. 無人運用ゲート 3 点（二重起動 Exit 5・通知・実行アカウント）→ 次回 #4 へ
9. まとめ — 「この環境での参考実測であり一般保証ではない」の明記
