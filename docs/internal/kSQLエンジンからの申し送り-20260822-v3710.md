- 対象: [E-2 dry-run 依頼](../../../kintone-sql-tools/docs/flow_engine_requests_20260821.md) — [設計提案 R2 確定](kSQLエンジンからの設計提案-E2-dryrun-20260821.md) に基づく実装
- 対応バージョン: **v3.71.0**（`/flow` への純加法のみ。既存 `executeStatement` ほか全 API 不変）

## 1. 提供内容

R2 確定契約（6 件）どおり `previewStatement` を `/flow` へ追加しました。

```ts
import { previewStatement, type PreviewResult, type PreviewSample } from "@rex0220/kintone-sql-tools/flow";

const preview = await previewStatement(stmt, ctx, { maxSamples: 5 });
// PreviewResult:
// { kind: "PREVIEW", operation: "INSERT"|"UPDATE"|"DELETE"|"UPSERT", appId,
//   counts: { insert, update, delete },       // 常に 3 キー（update = キー一致件数）
//   samples: PreviewSample[],                 // 書込順の先頭 maxSamples 件
//   reads: number,                            // preview が実消費した読取 API 数（cursor 含む）
//   estimatedWrites: number }                 // 本実行時の 100 件単位の推定書込 API 数
// PreviewSample: { kind: "insert"|"update"|"delete", key?, before?, after? }
//   before/after は代入対象列のみ・DELETE は key（$id）のみ
```

R2 契約との対応:

| R2 | 実装 |
|---|---|
| 1. DML 専用 | INSERT / INSERT...SELECT / UPDATE / UPDATE...FROM / DELETE / UPSERT / UPSERT...SELECT（MERGE 正規化後含む）のみ受理。非 DML・`VALIDATE ONLY`・`ON ERROR SKIP`・CHECK・APPLY・IMPORT・サブテーブルは**読取前に**対処付き `ArgumentError` |
| 2. counts 3 キー固定 | 実装どおり。unchanged 判定なし |
| 3. samples 既定 5・上限 50 | 整数 1〜50 以外は**読取開始前**に `ArgumentError`（client 呼出 0 回で失敗） |
| 4. reads / estimatedWrites | reads は records GET に加え cursor create/page も計上。metadata API は含めない。注入 client を全読取が通るためランナー単一カウンタでも並行計上可能 |
| 5. context 共有 | TEMP TABLE・変数・as-of / timezone・busy/順序検査を `executeStatement` と共有。preview 後も同じ context で続行可能 |
| 6. 書込 0 回 | preview 経路に書込呼出なし＋`postRecords`/`putRecords`/`deleteRecords` が必ず throw する遮断ラッパーの二重化 |

## 2. R2 に無かった仕様確定 1 件（要認識）

**`EXIT SUCCESS IF` 成立後の context に DML の preview を渡した場合**、`executeStatement` の
skipped と整合させるため、**全ゼロの `PreviewResult`**（counts すべて 0・samples 空・reads 0・
estimatedWrites 0）を返します。型に status を増やさず契約を最小に保つ判断です。
ランナーの dry-run 表示では「EXIT 成立（メッセージ）を表示し、以降の DML は 0 件」という
見え方になります — EXIT の `exited` は直前の `executeStatement` の結果で判定してください。

## 3. dialect 1 の prepare 検証は preview でも有効

updateKey 3 条件（重複禁止・型・キー数）とサブテーブル禁止は preview でも本実行と同じく
fail-closed で検査されます。「dry-run は通ったのに本実行で止まる」を作らないためです。
