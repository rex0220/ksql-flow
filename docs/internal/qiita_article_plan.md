# kSQL Flow Qiita 記事シリーズ構成案

**作成**: 2026-08-22（Claude Code 起草・チェックリスト 4-3 の文面ドラフト材料）
**前提**: v0.1.0 公開後（Phase 2/3 完了後）に順次公開。既存の kintone-sql-tools 記事群（`cli-ksql を作ったので紹介します` / `AIエージェントに kintone を操作させるには SQL が最適解である` 等）と同一トーン・相互リンクで**シリーズ化**する。

**全体設計の考え方**:

* 読者は「自分の実行環境」で記事を選ぶ → **環境別記事は各々自己完結**（その記事だけ読めば動く Quickstart 形式）にし、共通の思想・詳細はハブ記事（第 1 弾）へリンクで寄せる
* 実機検証（Phase 0）で踏んだ罠は**一次情報**として独自価値が高い → 該当環境の記事に体験談として織り込む
* as-is / no support 方針は全記事の冒頭テンプレとして統一（誤解による問い合わせ予防）

## 第 2 弾（実行環境別・自己完結 Quickstart）

### ② GitHub Actions で kintone の定期集計を無料運用する — kSQL Flow

* **対象読者**: サーバーを持ちたくない・Git 管理と PR レビューで回したい層（最も Qiita 読者と相性が良い）
* **骨子**: リポジトリ構成（jobs/ + config）→ Secrets 登録 → schedule workflow（examples/A-1 実物）→ PR ごとの `validate-all` → main マージ前の `run-all --dry-run --json` を PR コメントに貼る CI レシピ → 失敗時の `workflow_dispatch` + `--resume` 手動リラン
* **schedule の制約を正直に書く**: ベストエフォートで実行時刻は保証されない（毎時 0 分は混雑で数十分遅延・高負荷時はドロップもあり得る・public リポジトリは 60 日更新なしで schedule 自動無効化）。対策 = cron の分を 0 以外にずらす / 遅延前提でジョブは as-of 基準に（kSQL Flow は開始時刻でなく as-of で集計するので遅延に強い、という接続）/ 時刻厳守の要件は ③cron・タスクスケジューラへ誘導
* **独自ネタ**: dry-run --json を PR コメント化する actions スニペット（設計書 14 章の実装例）
* **分量**: 4,000〜5,000 字

### ③ Windows サーバー + タスクスケジューラで kintone バッチ — kSQL Flow

* **公開済み（2026-08-24）**: https://qiita.com/rex0220/items/d0a66c133edd42ff91c4 （【kSQL Flow #4】タスクスケジューラで毎朝動かす — PowerShell が 0.1 秒で無言死する罠つき。ドラフト: `qiita_draft_04_scheduler.md`。ChatGPT 9.1 / Gemini 公開可の両レビュー消化済み。素の Windows 11(Parallels VM)で通し再現検証済み。付随成果: 通知レシピ実機検証・テンプレート zip のタイトル設定・dev/notify_test 同梱・run_batch.bat/register_task.ps1 整備）
* **位置づけ**: **シリーズ第 4 話・運用編**（⑨スケール検証を経たジョブを毎朝の実運用に載せる回。単体でも自己完結で読める）
* **対象読者**: **すでに社内 Windows サーバーが動いている**情シス向けの現実解（ノークリサーチ 2024: 中堅・中小の約 44% は IaaS/ホスティング非導入。一方でクラウド併用が過半のため「本命」とは呼ばない）。新規に環境を用意する読者には冒頭で ②GitHub Actions（無料枠）/ ④VPS + cron（月 1,000 円前後）を先に案内する
* **骨子**: 冒頭で位置づけを正直に宣言 — **タスクスケジューラ単体は本番バッチ基盤の水準にない**（無言死・通知なし・単一マシン SPOF）。通知・実行記録・排他・リランはランナー側が持ち、スケジューラは「決まった時刻に 1 コマンド叩く起動装置」に徹する分担表を示す。それでも残る限界（**「そもそも起動しなかった」事故は heartbeat の不在を外部で検知するしかない**・SPOF）も明示 → ⑥で作ったジョブ（または付属サンプル）を前提に → Node 導入 → config と env（環境変数の置き場所）→ タスク登録の実手順（動作確認済みの登録スクリプト）→ `LastTaskResult` と ログアプリの突合 → 「再起動リトライは使わず `--resume`」の理由（多重起動ロックとの関係）
* **独自ネタ（実機で踏んだ罠 2 連発 — この記事の目玉）**:
  1. タスクスケジューラの既定は Windows PowerShell 5.1 → **BOM なし UTF-8 の日本語入り .ps1 はパースエラー**（0.1 秒無言死・LastTaskResult だけ 0 になるケースの調査記録）
  2. `LastTaskResult = 4294770688 (0xFFFD0000)` = -File のパス解決失敗（カレントディレクトリ依存の罠）
* **分量**: 5,000〜6,000 字。「kintone の文字列とソートの仕様まとめ」系の実機検証トーンで
* タイトル代案: 「タスクスケジューラで PowerShell が 0.1 秒で無言死する話 — kintone バッチ運用の実機の罠」（罠を主役にしたバズ寄せ案）

### ④'-a AWS 編 / ④'-c Azure 編 — **見送り（2026-08-24 決定）**

* 環境別のクラウド編は **GCP（④'-b）とレンタルサーバー（④''）に絞る**。理由: AWS はアカウントが利用不能で実機検証ができない（記事 = 実機検証済みの規約を優先）。Azure も絞り込みにより当面温存（反応を見て再検討）
* 旧 AWS 編に置いていた**全環境共通の設計論**は ④'-b GCP 編へ移管して残す: (1) 二重発火はスケジューラの仕様 → ログアプリの `job_key` 分散ロック（Exit 5）が設計で吸収、(2) スケジューラ側リトライは 0・リランは `--resume`、(3) 読み取り専用 FS / 使い捨て環境では `cwd/.ksql`（ローカルロック・JSONL 退避）が書けない → `/tmp` 等へ逃がす。排他と resume はログアプリが正なので成立し続ける
* 旧構想の詳細は git 履歴参照（このコミット以前の本ファイル）

### ④'-b Google Cloud で kintone バッチ — Cloud Run Jobs + Cloud Scheduler

* **対象読者**: GCP 利用企業の開発者・情シス + サーバーレス運用の設計論を知りたい層（AWS 編の見送りに伴い、共通設計論もこの記事が持つ）
* **骨子**:
  1. 適合サービスの結論 — **Cloud Run Jobs**（run-to-completion 型。Cloud Functions を選ばない理由も冒頭で 1 段落: 時間制限・読み取り専用 FS）
  2. **サーバーレスと BYOC バッチの相性論**（旧 AWS 編から移管） — 「実行環境が使い捨てでも壊れない」設計条件 = ログアプリが分散ロック・実行履歴・resume の正であること。**二重発火はスケジューラの仕様**で、`job_key` 分散ロック（Exit 5）が設計で吸収する話（この記事の目玉）
  3. examples/A-4 の Dockerfile を Artifact Registry へ push → Cloud Run Jobs 作成（タスクタイムアウトは最大 24h で余裕）。読み取り専用 FS 対策（`cwd`/`logging.localDir` を書込可能領域へ）もここで
  4. **Cloud Scheduler は cron にタイムゾーン指定可** — `Asia/Tokyo` で朝 6 時をそのまま書ける（UTC 換算不要が GCP の美点）
  5. Secret Manager → 環境変数注入（`env:` 参照と直結）
  6. **ジョブの maxRetries は 0**・リランは `--resume`（#4 タスクスケジューラと同じ原則の適用）
  7. ログアプリでの実行確認とコスト目安
* **前提作業**: examples/ に Cloud Run Jobs 設定例を追加（記事 = examples 一致の規約）。ローカルロックディレクトリの設定可能化は製品改善候補として起票検討
* **分量**: 5,000 字

### ④'' レンタルサーバーの cron で kintone バッチ — 月数百円の既存資産に載せる

* **対象読者**: ホームページ・メール用に**すでにレンタルサーバーを契約している**中小企業・個人。#4 の「既存 Windows サーバー」と同じ**「既存資産に載せる・追加のサーバー費用なし」訴求の第 2 弾**
* **骨子**:
  1. 位置づけ — SSH + cron が使えるプランが前提（さくら スタンダード以上・エックスサーバー等）。新規契約を勧める記事ではなく「すでにあるなら載せられる」の検証
  2. **最大の関門: Node.js 20.6+ をユーザー領域に用意する**（root 不可・ホスティング公式サポート外が普通）— Linux 系は公式バイナリ tarball 展開で可。**さくらは FreeBSD なので Node 公式バイナリが無い**点に注意（検証に使う 1 社に絞って確実な手順だけ書く）
  3. cron 登録（コントロールパネル or crontab）と罠 — **cron の環境は PATH 最小・cwd はホーム** → #4 の `%~dp0` と同じ思想の「自分の場所へ cd する絶対パス起動 sh」を用意（examples に同梱）
  4. 実行時間・プロセス制限 — 共有サーバーは長時間プロセスが kill されるプランがある → `limits.maxApiCalls` / `batchTimeoutSec` で 1 回を短く保つ・ジョブ分割・`--resume` で継続
  5. 通知・記録・排他・復旧は #4 と同一（kintone 条件通知 + ログアプリ + Exit Code + `--resume`）— スケジューラが変わっても運用設計が変わらないことが連載の主張
* **前提作業**: **契約中のレンタルサーバーで実機検証してから**（記事 = 実機検証済みの規約）。examples/ に sh 起動スクリプト + crontab 例を追加
* **分量**: 4,000〜5,000 字

## 第 3 弾（深掘り・読み物）

### ⑤ kintone バッチの事故は設計で潰す — 排他ロック・冪等リラン・fail-closed の作り方

* **対象読者**: バッチ基盤を自作している・しようとしている中級者（kintone に限らず刺さる汎用テーマ）
* **骨子**: kintone にトランザクションが無い前提から始める → 部分適用と冪等 UPSERT リラン → `job_key` 重複禁止フィールドを使った分散ロック（kintone アプリをロックサーバーにするアイデアが目玉）→ stale 回収と fail-closed → NO_DATA と ABORTED を分けた通知設計（誤アラートで監視が形骸化する話）→ Exit Code 体系
* **独自ネタ**: 「ログアプリ = 実行履歴 + 分散ロック + resume の Source of Truth」という一石三鳥の設計解説
* **引用素材（許諾取得済み 2026-08-25）**: エンジン B175 の実測表（kintone 全文検索索引の書込ラグ — `like` は書込直後 8 回中 6 回空振り・旧値ヒットあり / `=`・`IN`・`$id` は即時。一致規則: ハイフンは語分割・アンダースコアは非分割）。**引用条件 4 点を厳守**: ①測定条件を併記（開発 1 ドメイン・軽量アプリ・1〜2 件書込直後・1 日 8 試行）②秒数を保証値として書かない（「数秒のラグが観測された」まで）③kintone 公式に記載のない「観測された挙動」であり仕様ではないと明記 ④環境識別子は伏せる。整形済みの引用用表は `docs/kSQLエンジンからの回答-20260825-B175実測データ引用許諾.md` §3
* **追加ネタ候補**: F-5 A/B 実測（bulkRequest B/A = 96% — 「束ねても速くならない」の実証。書込時間はサーバ側処理支配）も本記事の射程
* **分量**: 6,000 字。設計書 5・7・8 章のダイジェスト
