# kSQL Flow Qiita 記事シリーズ構成案

**作成**: 2026-08-22（Claude Code 起草・チェックリスト 4-3 の文面ドラフト材料）
**前提**: v0.1.0 公開後（Phase 2/3 完了後）に順次公開。既存の kintone-sql-tools 記事群（`cli-ksql を作ったので紹介します` / `AIエージェントに kintone を操作させるには SQL が最適解である` 等）と同一トーン・相互リンクで**シリーズ化**する。

**全体設計の考え方**:

* 読者は「自分の実行環境」で記事を選ぶ → **環境別記事は各々自己完結**（その記事だけ読めば動く Quickstart 形式）にし、共通の思想・詳細はハブ記事（第 1 弾）へリンクで寄せる
* 実機検証（Phase 0）で踏んだ罠は**一次情報**として独自価値が高い → 該当環境の記事に体験談として織り込む
* as-is / no support 方針は全記事の冒頭テンプレとして統一（誤解による問い合わせ予防）

## 第 2 弾（実行環境別・自己完結 Quickstart）

### ② GitHub Actions で kintone の定期集計を無料運用する — kSQL Flow

* **対象読者**: サーバーを持ちたくない・Git 管理と PR レビューで回したい層（最も Qiita 読者と相性が良い）
* **骨子**: リポジトリ構成（jobs/ + config）→ Secrets 登録 → schedule workflow（examples/A-1 実物）→ PR ごとの `validate-all` → main マージ前の `run-all --dry-run --json` を PR コメントに貼る CI レシピ → 失敗時の `workflow_dispatch` + `--resume` 手動リラン
* **schedule の制約を正直に書く**: ベストエフォートで実行時刻は保証されない（毎時 0 分は混雑で数十分遅延・高負荷時はドロップもあり得る・public リポジトリは 60 日更新なしで schedule 自動無効化）。対策 = cron の分を 0 以外にずらす / 遅延前提でジョブは as-of 基準に（kSQL Flow は開始時刻でなく as-of で集計するので遅延に強い、という接続）/ 時刻厳守の要件は ③cron・タスクスケジューラへ誘導
* **独自ネタ**: dry-run --json を PR コメント化する actions スニペット（設計書 14 章の実装例）
* **分量**: 4,000〜5,000 字

### ③ Windows サーバー + タスクスケジューラで kintone バッチ — kSQL Flow

* **位置づけ**: **シリーズ第 4 話・運用編**（⑨スケール検証を経たジョブを毎朝の実運用に載せる回。単体でも自己完結で読める）
* **対象読者**: **すでに社内 Windows サーバーが動いている**情シス向けの現実解（ノークリサーチ 2024: 中堅・中小の約 44% は IaaS/ホスティング非導入。一方でクラウド併用が過半のため「本命」とは呼ばない）。新規に環境を用意する読者には冒頭で ②GitHub Actions（無料枠）/ ④VPS + cron（月 1,000 円前後）を先に案内する
* **骨子**: 冒頭で位置づけを正直に宣言 — **タスクスケジューラ単体は本番バッチ基盤の水準にない**（無言死・通知なし・単一マシン SPOF）。通知・実行記録・排他・リランはランナー側が持ち、スケジューラは「決まった時刻に 1 コマンド叩く起動装置」に徹する分担表を示す。それでも残る限界（**「そもそも起動しなかった」事故は heartbeat の不在を外部で検知するしかない**・SPOF）も明示 → ⑥で作ったジョブ（または付属サンプル）を前提に → Node 導入 → config と env（環境変数の置き場所）→ タスク登録の実手順（動作確認済みの登録スクリプト）→ `LastTaskResult` と ログアプリの突合 → 「再起動リトライは使わず `--resume`」の理由（多重起動ロックとの関係）
* **独自ネタ（実機で踏んだ罠 2 連発 — この記事の目玉）**:
  1. タスクスケジューラの既定は Windows PowerShell 5.1 → **BOM なし UTF-8 の日本語入り .ps1 はパースエラー**（0.1 秒無言死・LastTaskResult だけ 0 になるケースの調査記録）
  2. `LastTaskResult = 4294770688 (0xFFFD0000)` = -File のパス解決失敗（カレントディレクトリ依存の罠）
* **分量**: 5,000〜6,000 字。「kintone の文字列とソートの仕様まとめ」系の実機検証トーンで
* タイトル代案: 「タスクスケジューラで PowerShell が 0.1 秒で無言死する話 — kintone バッチ運用の実機の罠」（罠を主役にしたバズ寄せ案）

* **対象読者**: Linux サーバー・コンテナ運用層（cron と Docker は読者が重なるため 1 本に統合）

* **分量**: 4,000 字

### ④'-a サーバーレスで kintone バッチ (AWS 編) — Lambda の罠と「リトライ 0 + resume」の原則

* **対象読者**: AWS でサーバーレス運用したい層 + 全クラウド共通の設計論を知りたい層（②〜④の続き・クラウド読者の取り込み枠。末尾の比較表が ④'-b/④'-c への振り分けハブ）
* **骨子**:
  1. サーバーレスと BYOC バッチの相性論 — 「実行環境が使い捨てでも壊れない」ための設計条件
  2. **二重発火はスケジューラの仕様** — EventBridge 等のまれな重複実行を、ログアプリの `job_key` 分散ロック（Exit 5）が設計で吸収する話（この記事の目玉）
  3. Lambda 実装 — コンテナイメージ化・EventBridge Scheduler(タイムゾーン指定 cron)・Secrets Manager → env
  4. **Lambda の罠（実機検証ネタ）**: 読み取り専用 FS で `cwd/.ksql`（ローカルロック・JSONL）が書けず起動失敗 → `cwd` と `logging.localDir` を `/tmp` へ逃がす回避策。15 分上限と `batchTimeoutSec` の関係
  5. AWS での本命は **ECS Fargate Scheduled Task**（run-to-completion 型・examples/A-4 の Docker イメージがそのまま使える）
  6. **「スケジューラ側リトライは 0・リランは `--resume`」の原則** — EventBridge の retry を切り、部分適用からの復旧は冪等リランに一本化（A-2 タスクスケジューラと同じ思想。3 クラウド共通の横串として ④'-b へ接続）
  7. 制約の明示 — JSONL フォールバック（到達不能時の退避 + 再送）は環境が消えると失われる。排他と resume はログアプリが正なので成立し続ける、という整理
* **独自ネタ**: 「ログアプリ = 分散ロック + 実行履歴 + resume の正」という設計が、そのままステートレス実行の成立条件になっている構図。⑤（設計深掘り）への導線
* **末尾に 3 クラウド比較表**（適合サービス / cron の TZ 対応 / 時間上限 / シークレット注入 / リトライ設定）を置き、④'-b（GCP）/ ④'-c（Azure）への振り分けハブを兼ねる
* **前提作業**: examples/ にサーバーレス例を追加してから公開（記事 = examples 一致の規約）。ローカルロックディレクトリの設定可能化は製品改善候補として起票検討
* **分量**: 5,000〜6,000 字

### ④'-b Google Cloud で kintone バッチ — Cloud Run Jobs + Cloud Scheduler

* **対象読者**: GCP 利用企業の開発者・情シス（自己完結 Quickstart。GCP 読者に GCP のことだけを書く）
* **骨子**:
  1. 適合サービスの結論 — **Cloud Run Jobs**（run-to-completion 型。Cloud Functions を選ばない理由も冒頭で 1 段落: 時間制限・読み取り専用 FS → 詳細は ④'-a へリンク）
  2. examples/A-4 の Dockerfile を Artifact Registry へ push → Cloud Run Jobs 作成（タスクタイムアウトは最大 24h で余裕）
  3. **Cloud Scheduler は cron にタイムゾーン指定可** — `Asia/Tokyo` で朝 6 時をそのまま書ける（UTC 換算不要が GCP の美点）
  4. Secret Manager → 環境変数注入（`env:` 参照と直結）
  5. **ジョブの maxRetries は 0**・リランは `--resume`（④'-a の原則の適用。二重発火は分散ロックが吸収、の要約付き）
  6. ログアプリでの実行確認とコスト目安
* **前提作業**: examples/ に Cloud Run Jobs 設定例を追加
* **分量**: 4,000 字

### ④'-c Azure で kintone バッチ — Container Apps Jobs（Functions を選ばない理由つき）

* **対象読者**: Azure 利用企業の情シス・開発者。**kintone ユーザー企業は Microsoft ショップが多く、シリーズ中でも読者相性が良い見込みの本命枠**
* **骨子**:
  1. 適合サービスの結論 — **Container Apps Jobs**（スケジュール起動の run-to-completion コンテナ）。**最初に Azure Functions を選ばない理由**を明示（Timer + Consumption の時間制限・読み取り専用パッケージ → 詳細は ④'-a へリンク）。WebJobs（App Service）現役組への言及も 1 段落
  2. examples/A-4 の Dockerfile を ACR へ push → Container Apps Jobs 作成（cron トリガー）
  3. **Azure 固有の罠: cron は UTC のみ** — JST 6:00 は `0 21 * * *`（GitHub Actions と同じ換算表を再掲）
  4. シークレット（Container Apps シークレット / Key Vault 参照）→ 環境変数注入
  5. **リトライポリシーは 0**・リランは `--resume`（④'-a の原則の適用。二重発火は分散ロックが吸収、の要約付き）
  6. ログアプリでの実行確認とコスト目安
* **前提作業**: examples/ に Container Apps Jobs 設定例を追加
* **分量**: 4,500 字

## 第 3 弾（深掘り・読み物）

### ⑤ kintone バッチの事故は設計で潰す — 排他ロック・冪等リラン・fail-closed の作り方

* **対象読者**: バッチ基盤を自作している・しようとしている中級者（kintone に限らず刺さる汎用テーマ）
* **骨子**: kintone にトランザクションが無い前提から始める → 部分適用と冪等 UPSERT リラン → `job_key` 重複禁止フィールドを使った分散ロック（kintone アプリをロックサーバーにするアイデアが目玉）→ stale 回収と fail-closed → NO_DATA と ABORTED を分けた通知設計（誤アラートで監視が形骸化する話）→ Exit Code 体系
* **独自ネタ**: 「ログアプリ = 実行履歴 + 分散ロック + resume の Source of Truth」という一石三鳥の設計解説
* **分量**: 6,000 字。設計書 5・7・8 章のダイジェスト

* **対象読者**: AI 活用層 + kintone 開発者。エンジン側の既存記事「AIエージェントに kintone を操作させるには SQL が最適解である」の**続編**ポジション
* **骨子**: 既存記事の要約（SQL が AI との共通言語）→ **VSCode + Claude Code + kSQL MCP 構成**（`--scope project` で `.mcp.json` ごと Git 管理・ジョブ/config/MCP 設定が 1 リポジトリに揃う）→ MCP でスキーマ取得 → AI にジョブ SQL を生成させる実例プロンプト（月次集計を要件文から）→ `ksql_validate`（一次チェック）とランナー `validate`（フル検証）の二段構え（二次も AI がターミナルで自走）→ **dry-run の差分プレビューを人間の最終レビューにする**運用 → Git/PR に載せて完成。「次回: このジョブをタスクスケジューラで毎朝動かす」で③へ引き継ぐ

* **テンプレートリポジトリ**: https://github.com/rex0220/ksql-flow-template （public・template フラグ有効）に CLAUDE.md（AI 向け作業規約）・.mcp.json・config 2 種・検証済みサンプルジョブを同梱。「LLM は kSQL Flow を知らない」前提を CLAUDE.md + ksql_docs で塞ぐのが記事の核。記事とテンプレートの内容は一致させる（乖離したらテンプレート側を正とする）
* **分量**: 5,000 字。既存記事と相互リンクでシリーズの入口を増やす
