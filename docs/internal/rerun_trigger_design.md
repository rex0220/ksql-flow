# リラン起動手段の設計検討 — VPS / クラウドでの「押せない」問題

* 起票: 2026-08-27（記事 #9 公開後の宿題）
* 状態: **検討案（未裁定）** — 裁定は Takashi、結果は `reviews/decisions.md` へ
* 関連: [#7 リラン設計](qiita_draft_07_error_rerun.md) / [#8 失敗の 4 クラス](qiita_draft_08_failure_classes.md) / [#9 VPS + cron](qiita_draft_09_vps_cron.md) / 仕様 §6

## 1. 問題

記事 #9 で「VPS 構成の弱点」として明示したとおり。

| 環境 | リランの操作 | 出先で押せるか |
| --- | --- | --- |
| #4 Windows サーバー | サーバーに入って 1 コマンド | 社内網に入れれば |
| #6 GitHub Actions | ブラウザで Run workflow + resume チェック | **押せる**（スマホ可） |
| #9 VPS + cron | SSH で入って 1 コマンド | **SSH 鍵を持つ端末が要る** |

失敗の通知は kintone の条件通知でスマホまで届く（#4 で構築）。**気づけるのに直せない**、という非対称がある。休日・外出先で顕在化する。

これは VPS 固有ではなく、**自前でスケジューラを持つ環境すべて**（VPS・オンプレ・クラウド VM・Cloud Run Jobs のスケジュール実行）に共通する。

## 2. 前提として動かせない条件

* 復旧の正は冪等リラン（`--resume`）。スケジューラ側の自動リトライは採らない（連載を通じた方針）
* resume に必要なのは ①ジョブリポジトリの clone ②書込可トークン ③kintone への到達 の 3 つだけ（仕様 §6.2）
* 書込可トークンの露出面は増やしたくない（#9 で「GitHub に置くのは閲覧のみトークン、書込は VPS の `.env` だけ」を利点として書いた）
* VPS にインバウンドポートを開けたくない（#9 の構成は cron から node を叩くだけ・ufw と fail2ban はイメージ既定のまま）

## 3. 案の比較

| 案 | 実装コスト | 出先操作 | 書込トークンの露出面 | インバウンド | 判定 |
| --- | --- | --- | --- | --- | --- |
| A. GitHub Actions を復旧専用に併用 | ゼロ（#6 の資産） | ブラウザ | **増える**（GitHub Secrets にも置く） | 不要 | 併用可・妥協案 |
| B. kintone を指示キューにする（ポーリング） | 小（VPS 側スクリプト） | **kintone アプリ** | 増えない | **不要** | **本命** |
| C. Webhook 受信サーバーを VPS に立てる | 中 | kintone アプリ | 増えない | **要る** | 却下 |
| D. スマホに SSH 秘密鍵を入れる | ゼロ | ターミナルアプリ | 鍵の露出面が増える | 不要 | 補助のみ |
| E. リランが要らない設計に寄せる | ゼロ〜中 | 不要 | 増えない | 不要 | **前提として先に効かせる** |
| F. 限定的な自動 resume（cron 1 行） | ほぼゼロ | 不要 | 増えない | 不要 | **併用推奨・要裁定** |

### C を却下する理由

kintone Webhook を VPS の HTTPS エンドポイントで受ける構成は、B と得られるものがほぼ同じで、コストとリスクだけ増える。

* インバウンドを開ける = 攻撃面が増える。#9 の「cron から node を叩くだけ」という構成の単純さが壊れる
* TLS 証明書・リバースプロキシ・その更新という保守項目が増える（#9 の主題である「保守工数」に直撃する）
* kintone Webhook は送信元の署名を持たないため、**URL の秘匿頼み**の認証になる

B はポーリングの遅延（最大 5 分）を受け入れるだけで、これらを全部回避できる。

## 4. 本命案 B — kintone をリラン指示キューにする

### 4.1 構成

```
[担当者のスマホ] --レコード追加--> [kintone 実行指示アプリ]
                                          ^   |
                          5 分ごとに GET  |   | 状態・終了コードを書き戻す
                                          |   v
                                  [VPS: poll_control.sh (cron)]
                                          |
                                          v
                                  run_batch.sh --resume
```

VPS からの outbound HTTPS のみ。**ポートは 1 つも開けない。**

### 4.2 実行指示アプリのフィールド

| フィールド | 型 | 用途 |
| --- | --- | --- |
| 操作 | ドロップダウン | `リラン` / `バックフィル` / `通常実行` — **自由入力させない** |
| 対象プロファイル | ドロップダウン | `prod` / `stg` — allowlist |
| 対象ホスト | ドロップダウン | 複数台あるとき、どのホストが拾うか |
| 基準時刻 | 日時 | バックフィル時のみ |
| 状態 | ドロップダウン | `受付待ち` / `実行中` / `完了` / `失敗` |
| 受付ホスト・受付日時 | 文字列・日時 | どのホストがいつ拾ったか |
| 終了コード・メッセージ・BATCH ID | 数値・文字列 | 実行結果の書き戻し（証跡） |

レコードの作成者は kintone が自動で持つので、**誰がリランを押したかの証跡が標準で残る**。

### 4.3 ポーラーの処理

1. `状態 = 受付待ち` かつ `対象ホスト = 自ホスト` を 1 件取得（無ければ即終了 = API 1 回）
2. **revision を条件に `実行中` へ更新**して自分のものとして確保する（楽観ロック。二重取得の防止）
3. `操作` の列挙値を**固定のコマンド文字列にマップ**して `run_batch.sh` を起動
4. 終了コード・メッセージ・BATCH ID を書き戻す

### 4.4 セキュリティ上の必須要件

**この 1 点を外すと、kintone のレコード追加権限が VPS 上の任意コマンド実行になる。**

* **レコードの値をシェルに渡さない。** `操作` はドロップダウンの列挙値で受け、スクリプト内の固定文字列（`--resume` 等）へマップする。文字列フィールドをそのままコマンドラインに展開しない
* `--as-of` だけは値が要るが、**日時フィールドから ISO-8601 を再構築**して渡す（入力文字列をそのまま通さない）
* 「押せる人」は kintone のアプリ権限で決まる。**#4 で作ったジョブ管理グループ（通知先）にレコード追加権限を与えれば、通知の受け手と実行権限が一致する** — これは設計上きれいな性質
* VPS の `.env` トークンに要るのは、この指示アプリの**閲覧 + 編集**権限のみ（レコード追加は不要）

### 4.5 API 消費

日次 API リクエスト数は**アプリ単位**でカウントされる（#5 で確認した仕様）。指示アプリは専用なので、**業務アプリの枠を一切食わない**。

* 5 分間隔 × 24 時間 = 288 回/日
* 営業時間帯のみ（平日 7–20 時）= 156 回/日
* 専用アプリの上限 10,000/日 に対して **1.5〜3%**

### 4.6 弱点

* **ポーラー自体が動いていなければ何も起きない** — #4 以来の「起動しなかった事故」と同型。対策は kintone 側だけで組める: 指示レコードが N 分以上 `受付待ち` のままなら条件通知で再度知らせる
* VPS ごと落ちている場合は当然動かない（ただしその状況では SSH も入れない）
* 最大 5 分の遅延（SSH で駆けつける時間より短い）

## 5. 併用案 F — 限定的な自動 resume（cron 1 行）

```cron
7  6 * * * /opt/ksql/my-ksql-jobs/run_batch.sh          >> /var/log/ksql/batch.log 2>&1
35 6 * * * /opt/ksql/my-ksql-jobs/run_batch.sh --resume >> /var/log/ksql/batch.log 2>&1
```

* 6:07 の本番が全て成功していれば、resume の選抜対象はゼロ。**数 API で即終了**するので常時仕掛けても実質無コスト
* 救えるのは #8 の**クラス A（時間が解決する一時障害）だけ**。クラス B（データ起因・Exit 2）は同じ ASSERT で再び止まるが、**書く前に止まるので無害**で、通知が続くことが「まだ直っていない」の表示になる（#7 で既述）

### 方針との整合（要裁定）

連載で一貫して「スケジューラ側の自動リトライは使わない」と書いてきた。ここは**書き分けが要る**。

* 却下してきたのは「**スケジューラが失敗を検知して同一プロセスを再起動する**」機能（回数が状況依存で、暴走しうる）
* F は「**独立した時刻スロットで冪等 resume を 1 回だけ走らせる**」もので、実行回数が時刻で固定されている

別物だが方針としては近接しているので、**採るなら記事と仕様で明示的に線を引く必要がある**。ここは裁定案件。

## 6. 前提として先に効かせる案 E

最良の解決は「駆けつけなくてよいこと」であり、これは既に #7 / #8 の主張。

* 累積・全量型のジョブなら翌日の実行が欠落を吸収する → そもそもリランが要らない
* 期間窓型は残るので、E だけでは解決しない。**E で母数を減らし、残りを B / F で拾う**という重ね方になる

## 7. 推奨

1. **E** を設計方針として先に効かせる（母数を減らす）
2. **F** を入れる（cron 1 行でクラス A を自動回収）— 要裁定
3. **B** を本命として実装（VPS・オンプレ・クラウド VM に共通で効く汎用解）

B の価値は、#9 の利点（書込可トークンを GitHub に置かない）を保ったまま、#6 のブラウザボタンと同等の操作性が得られること。しかも**失敗通知が届いた kintone のアプリの中でリランまで完結する**ため、担当者の導線が 1 つで済む。

## 8. 実装上の論点（未決）

* ポーラーをどこに置くか — ①ジョブリポジトリ内のスクリプト（ランナー変更なし・テンプレート同梱）②ランナーの新コマンド `ksql-flow serve` 相当。**まず ① で実証し、有用なら ② を検討**するのが妥当
* 指示アプリをログアプリと分けるか統合するか — 分ける前提で書いた（ランナーの書込と競合させないため・API 枠を分けるため）
* 複数ホストが同じ指示アプリを見る場合の割り当て規則（`対象ホスト` フィールドで足りるか）
