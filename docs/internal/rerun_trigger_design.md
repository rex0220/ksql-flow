# リラン起動手段の設計検討 — VPS / オンプレでの「押せない」問題

* 起票: 2026-08-27（記事 #9 公開後の宿題）／v2（Codex・Gemini レビュー反映）／v3（Q8・Q9 裁定反映）／**v4: 2026-08-27**（設計原則の確立により大幅に単純化）
* 状態: **案 B を実装方針として承認。未裁定の論点なし**（記録は `reviews/decisions.md` Q8・Q9・Q10）
* 関連: [#7 リラン設計](qiita_draft_07_error_rerun.md) / [#8 失敗の 4 クラス](qiita_draft_08_failure_classes.md) / [#9 VPS + cron](qiita_draft_09_vps_cron.md) / 仕様 §5.5・§6・§8.4・§10.3

## 1. 問題

記事 #9 で「VPS 構成の弱点」として明示したとおり。

| 環境 | リランの操作 | 出先で押せるか |
| --- | --- | --- |
| #4 Windows サーバー | サーバーに入って 1 コマンド | 社内網に入れれば |
| #6 GitHub Actions | ブラウザで Run workflow + resume チェック | **押せる**（スマホ可） |
| #9 VPS + cron | SSH で入って 1 コマンド | **SSH 鍵を持つ端末が要る** |

失敗の通知は kintone の条件通知でスマホまで届く（#4 で構築）。**気づけるのに直せない**、という非対称がある。休日・外出先で顕在化する。

### 1.1 対象範囲

**クラウドには管理プレーンからの実行手段がある**（Cloud Run Jobs は Google Cloud Console から、EC2 は Systems Manager Run Command で SSH なしにコマンドを送れる）。したがって本メモの対象は **VPS・オンプレ・クラウド管理プレーンを採用しない VM** に限る。管理プレーンが使えるならそれが実装ゼロの解（案 G）。

## 2. 設計原則 — 起動手段だけを変え、リランの動作は変えない

**この設計で変えるのは「誰が引き金を引くか」だけであり、リランの意味論は一切変えない。**

```
SSH で入って ./run_batch.sh --resume        ┐
                                            ├→ まったく同じ動作
kintone に指示レコードを追加 → ポーラーが実行 ┘
```

連載の主張は一貫して「**スケジューラを変えても運用設計は変わらない**」（#9）だった。その延長として「**起動手段を変えてもリランの動作は変わらない**」を置く。

この原則から、次が自動的に決まる。

* **リランの選抜規則・as-of の引き継ぎ・対象バッチの決まり方はランナーのまま。** ポーラーが独自の判断を足さない
* **ランナーの変更は不要。** 公開済み v0.4.0 のまま実装できる
* ポーラーが持つのは「**指示を受け取り、決められた 1 コマンドを起動し、結果を書き戻す**」だけ

### 2.1 対象バッチの「ずれ」を設計で扱わない理由（v4 で撤回）

v2〜v3 では Codex の指摘を受けて「指示に対象バッチ ID を持たせ、実行時の直近バッチと違えば実行しない」を必須要件にしていた。**これは撤回する。**

理由は、**同じ「ずれ」が手動リランにも等しく存在する**こと。土曜に失敗した通知を見た担当者が日曜に SSH で入って `--resume` を叩けば、拾われるのは日曜のバッチである。これは #7 で「**resume で救えるのは次のスケジュールが来る前だけ**。それを過ぎた復旧はバックフィル（`--as-of`）に変わる」として**既に文書化した仕様**であって、指示キューが新たに持ち込む欠陥ではない。

そして**キューは手動より窓が狭い**。

| 起動手段 | 失敗から実行までの遅延 |
| --- | --- |
| 人間が通知を見て SSH で入る | 数十分〜数時間（休日なら翌営業日） |
| **ポーラー（5 分間隔）** | **最大 5 分** |

したがって、キュー側にだけ対象バッチ固定を課すのは、**手動より安全な経路に手動より厳しい制約を付ける**ことになり、原則（§2）にも反する。「指示が長く滞留したまま実行される」という残る懸念は、**指示の有効期限**（§4.5）という軽い仕組みで足りる。

> この撤回により、v3 の「論点 3（ランナーに `--expect-batch` を足すか）」は**解消**する。ランナーの仕様変更は要らない。

### C を却下する理由

* kintone Webhook の**公開仕様に、受信側が検証できる送信元署名や shared secret の記載がない**。ただし「URL 秘匿頼み」と言い切るのは強すぎる — Webhook を wake-up 信号としてのみ使い、**受信後に API トークンで指示レコードを取り直して検証**すれば、偽リクエストから直接コマンドが走ることは防げる
* それでも残るのが、**インバウンド開放・TLS 証明書の保守・DoS 対策**。#9 の主題である保守工数に直撃し、「cron から node を叩くだけ」という構成の単純さが壊れる
* B はポーリング遅延（最大 5 分）を受け入れるだけでこれらを全部回避できるため、**B を優先**する

## 4. 本命案 B — kintone をリラン指示キューにする

### 4.1 構成

```
[担当者のスマホ] --レコード追加--> [kintone 実行指示アプリ]
                                          ^   |
                          5 分ごとに GET  |   | 状態・結果を書き戻す
                                          |   v
                                  [VPS: poll_control.sh (cron + flock)]
                                          |
                                          v
                              ./run_batch.sh --resume
                              （SSH で叩くのと同一のコマンド）
```

VPS からの outbound HTTPS のみ。**ポートは 1 つも開けない。**

### 4.2 実行意味論 — at-least-once

**exactly-once は保証しない。保証しないでよい**というのが、この設計が成立する理由である。

* リランは冪等（仕様 §5.2）。同じ指示が 2 回実行されても最終状態は変わらない
* 同時実行はログアプリの分散ロック（仕様 §5.5）が Exit 5 で止める
* したがってキューに必要なのは「**いつか必ず 1 回以上実行される**」ことだけで、重い状態機械は要らない

**この前提が崩れる操作（`通常実行`・`バックフィル`）は MVP から外す**（§7）。

### 4.3 実行指示アプリのフィールド

| フィールド | 型 | 用途 |
| --- | --- | --- |
| 操作 | ドロップダウン | MVP は `リラン` のみ。**自由入力させない** |
| 対象プロファイル | ドロップダウン | `prod` / `stg` — allowlist |
| 対象ホスト | ドロップダウン | どのホストが拾うか |
| 状態 | ドロップダウン | `受付待ち` / `実行中` / `完了` / `失敗` / `結果不明` / `期限切れ` / `取消` |
| 確保ホスト・確保期限 | 文字列・日時 | claim と stale 回収（§4.4） |
| 実行バッチ ID | 文字列 | 実行されたバッチ。ログアプリへの導線 |
| 終了コード・要約 | 数値・文字列 | 結果の書き戻し（§4.6 のマスキング規則に従う） |
| 実行時 git_ref | 文字列 | **記録のみ**（実行を止める条件にはしない — §4.7） |

レコードの `作成者` は kintone が自動で持つので、**誰がリランを指示したかの証跡が標準で残る**。

### 4.4 ポーラーの処理

1. **`flock` でホスト単位に一重化**（cron は前回の終了を待たないため必須）
2. `状態 = 受付待ち` かつ `対象ホスト = 自ホスト` を**作成日時 asc で 1 件**取得（無ければ即終了 = API 1 回）
3. **有効期限を過ぎていれば `期限切れ`** にして終了（§4.5）
4. **revision を条件に `実行中` へ更新**して確保する。同時に `確保ホスト` と `確保期限`（= 現在 + `batchTimeoutSec` + 余裕）を書く
5. 固定の絶対パスを **argv 配列で起動**（`sh -c` や文字列連結を使わない）
6. 終了コードを状態にマップして書き戻す

**終了コードのマッピング**（仕様 §10.3。**ロック競合は Exit 5**）:

| Exit | 指示レコードの状態 | 意味 |
| --- | --- | --- |
| 0 | `完了` | 復旧した（resume 対象が無かった場合も含む） |
| 2 | `失敗` | データが直っていない（#8 クラス B）。**書く前に止まっているので無害** |
| 3 | `失敗` | 基盤側がまだ復旧していない |
| **5** | **`受付待ち` へ戻す**（試行回数を加算） | 通常バッチが実行中。**失敗ではなく「待つべき」状態** |

**stale 回収**: `実行中` のまま `確保期限` を過ぎた指示は `結果不明` にする。ログアプリ側に対応する実行バッチがあるかを人間が照合して判断する。単純な再取得による自動リトライはしない。

### 4.5 指示の有効期限

**指示が長く滞留したまま実行されること**への対策は、対象バッチ固定ではなくこれで足りる（§2.1）。

* 作成から N 時間（既定案: 6 時間）を過ぎた `受付待ち` は、実行せず `期限切れ` にする
* 人間には「この指示は古い。現在の状態を見て、必要なら出し直すか、バックフィル（`--as-of`）に切り替えてほしい」という意味になる
* これは**リランの動作を変えるものではなく、古い依頼を受け付けないという受付側の規則**である

### 4.6 セキュリティ要件

**この節を外すと、kintone のレコード追加権限が VPS 上の任意コマンド実行になる。**

* **レコードの値をシェルに渡さない。** `操作`・`プロファイル`・`ホスト` はドロップダウンの列挙値で受け、**ローカル allowlist のキーとしてのみ**使う。レコード値からパス・環境変数名・作業ディレクトリを組み立てない
* **`sh -c` と文字列連結を使わない。** 固定の絶対パスを argv 配列で起動する
* **ランナーの stdout / stderr をそのまま指示レコードへ転記しない。** 仕様 §8.4 のマスキングを迂回して認証情報・SQL リテラル・レコード値が漏れる経路になる。**固定の要約とログアプリへのリンクだけ**を返す
* **指示の連投による DoS を防ぐ** — プロファイルごとの `受付待ち` 上限、および §4.5 の有効期限
* **権限は kintone 標準のアクセス権で実現する**（Q9 裁定済み）。ランナー側に権限機構を持たせない:

| 主体 | 指示アプリ | ログアプリ | 実現手段 |
| --- | --- | --- | --- |
| リラン依頼者 | **レコード追加**（結果フィールドは編集不可） | 閲覧のみ | アプリのアクセス権 + **フィールド単位のアクセス権** |
| 通知の受け手 | 閲覧のみ | 閲覧のみ | アプリのアクセス権 |
| VPS のトークン | 閲覧 + 編集（**追加不要**） | 追加・編集 | API トークンの権限設定 |

> **指示アプリのレコード追加権限 = リランを起こせる人**、という 1 対 1 対応になる。どのグループを充てるかは**運用判断**であり、設計上の制約にしない。
>
> 「誰が指示したか」は、人間が kintone UI からレコードを追加する以上 `作成者` に自動で残る。ポーラーは編集しかしないので `更新者` はトークン側になる点に注意。

**指示アプリとログアプリを分ける理由**: ①権限の非対称性 — 指示アプリは「人間が追加・VPS が編集」、ログアプリは「VPS が追加・編集・人間は閲覧のみ」 ②状態機械の分離 ③通知ルールの分離 ④待機ポーリングの API 枠の分離。

### 4.7 リビジョンの扱い — 記録するが止めない

#7 で書いたとおり **as-of が固定するのは入力の時刻基準であって処理ロジックではない**。失敗後に `git pull` されていれば、resume は新しいコードで走る。

これは**手動リランでも同じ**なので、§2 の原則により**キュー側で実行を止める条件にはしない**。実行時の `git_ref` を指示レコードに記録し、**後から突き合わせられるようにする**のみとする（ログアプリ側にも `git_ref` は残る）。

厳密な再現が要る場合の手順（失敗時の commit を checkout してから resume する）は #7 のとおりで、これは人間が SSH で行う作業として残る。

### 4.8 API 消費

日次 API リクエスト数は**アプリ単位**でカウントされる（#5 で確認した仕様。スタンダードコース 10,000 回／ワイドコースはより大きい）。

* **待機ポーリングの消費は指示アプリだけ**に載る。5 分間隔 × 24 時間 = 288 回/日、営業時間帯のみ（平日 7–20 時）なら 156 回/日
* **複数ホストなら `288 回 × ホスト数`**
* ただし**実際に resume すれば業務アプリとログアプリの API は当然消費する**。「業務アプリの枠を一切食わない」のは待機中のみ

### 4.9 残る弱点

* **ポーラー自体が動いていなければ何も起きない** — #4 以来の「起動しなかった事故」と同型。対策は kintone 側だけで組める: 指示レコードが N 分以上 `受付待ち` のままなら条件通知で再度知らせる
* VPS ごと落ちている場合は動かない（ただしその状況では SSH も入れない）
* 最大 5 分の遅延（手動リランより短い — §2.1）
* `対象ホスト` の固定は障害時の failover を失う。将来は「実行プール + profile 一致」での割り当てを検討

## 5. 案 F — 限定的な自動 resume（**却下 / Q8 裁定済み**）

**2026-08-27 裁定: 却下**（`reviews/decisions.md` Q8）。連載および仕様の方針「スケジューラ側の自動リトライは使わない。復旧は冪等リランに一本化する」は**文言変更せず維持**する。**再提案しない。**

却下理由（記録として残す）:

* 当日の定期実行が**そもそも起動しなかった**日、自動 resume は直近バッチ = **前日のバッチ**を拾い、前日の as-of で再実行する。**人間の判断が挟まらないため、この「ずれ」を誰も検知できない**（案 B では指示を出す人間が現在の失敗を見て判断している）
* 「救えるのは #8 のクラス A だけ」という当初の記述も不正確だった。データが偶然直っていればクラス B も走り、原因未解消なら Exit 2 を再発させる
* 「失敗検知連動の再起動」と「独立スロットでの 1 回限りの resume」は技術的には区別できるが、運用上はいずれも**人間の判断を挟まずに外側から `--resume` する**仕組みであり、方針の実質的な変更にあたる

復旧の起動手段は**案 B に一本化**する。

## 6. 案 E — リランが要らない設計に寄せる

最良の解決は「駆けつけなくてよいこと」であり、これは既に #7 / #8 の主張。

* 累積・全量型のジョブなら翌日の実行が欠落を吸収する → そもそもリランが要らない
* 期間窓型は残るので E だけでは解決しない。**E で母数を減らし、残りを B で拾う**という重ね方になる

## 7. 推奨と MVP スコープ

1. **E** を設計方針として先に効かせる（母数を減らす）
2. **G** — クラウドで管理プレーンが使えるならそれが最適。B は要らない
3. **B** を VPS・オンプレ向けの本命として実装。**MVP は以下に限定**:
   * 操作は **`リラン` のみ**（`通常実行`・`バックフィル` は冪等前提が崩れるため後段へ）
   * **単一ホスト**
   * `flock`（§4.4）・有効期限（§4.5）・セキュリティ要件と権限分離（§4.6）は MVP に含む
   * 意味論は **at-least-once** と明記
   * **ランナーの変更は行わない**（§2）
4. **F** は却下済み（Q8）

B の価値は、#9 の利点（書込可トークンを GitHub に置かない）を保ったまま、#6 のブラウザボタンと同等の操作性が得られること。しかも**失敗通知が届いた kintone のアプリの中でリランまで完結する**ため、担当者の導線が 1 本で済む。
