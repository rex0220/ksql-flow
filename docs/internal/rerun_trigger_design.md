## 1. 問題

記事 #9 で「VPS 構成の弱点」として明示したとおり。

| 環境 | リランの操作 | 出先で押せるか |
| --- | --- | --- |
| #4 Windows サーバー | サーバーに入って 1 コマンド | 社内網に入れれば |
| #6 GitHub Actions | ブラウザで Run workflow + resume チェック | **押せる**（スマホ可） |
| #9 VPS + cron | SSH で入って 1 コマンド | **SSH 鍵を持つ端末が要る** |

失敗の通知は kintone の条件通知でスマホまで届く（#4 で構築）。**気づけるのに直せない**、という非対称がある。休日・外出先で顕在化する。

### 1.1 対象範囲

**クラウドには管理プレーンからの実行手段がある**（Cloud Run Jobs は Google Cloud Console から、EC2 は Systems Manager Run Command で SSH なしにコマンドを送れる）。したがって本メモの対象は **VPS・オンプレ・クラウド管理プレーンを採用しない VM** に限る。管理プレーンが使えるならそれが実装ゼロの解（案 G）。

## 2. 設計原則 — 起動手段だけを変え、リランの動作は変えない

**この設計で変えるのは「誰が引き金を引くか」だけであり、リランの意味論は一切変えない。**

```
SSH で入って ./run_batch.sh --resume        ┐
                                            ├→ まったく同じ動作
kintone に指示レコードを追加 → ポーラーが実行 ┘
```

連載の主張は一貫して「**スケジューラを変えても運用設計は変わらない**」（#9）だった。その延長として「**起動手段を変えてもリランの動作は変わらない**」を置く。

この原則から、次が自動的に決まる。

* **リランの選抜規則・as-of の引き継ぎ・対象バッチの決まり方はランナーのまま。** ポーラーが独自の判断を足さない
* **ランナーの変更は不要。** 公開済み v0.4.0 のまま実装できる
* ポーラーが持つのは「**指示を受け取り、決められた 1 コマンドを起動し、結果を書き戻す**」だけ

### 2.1 対象バッチの「ずれ」を設計で扱わない理由（v4 で撤回）

v2〜v3 では Codex の指摘を受けて「指示に対象バッチ ID を持たせ、実行時の直近バッチと違えば実行しない」を必須要件にしていた。**これは撤回する。**

理由は、**同じ「ずれ」が手動リランにも等しく存在する**こと。土曜に失敗した通知を見た担当者が日曜に SSH で入って `--resume` を叩けば、拾われるのは日曜のバッチである。これは #7 で「**resume で救えるのは次のスケジュールが来る前だけ**。それを過ぎた復旧はバックフィル（`--as-of`）に変わる」として**既に文書化した仕様**であって、指示キューが新たに持ち込む欠陥ではない。

そして**キューは手動より窓が狭い**。

| 起動手段 | 失敗から実行までの遅延 |
| --- | --- |
| 人間が通知を見て SSH で入る | 数十分〜数時間（休日なら翌営業日） |
| **ポーラー（5 分間隔）** | **最大 5 分** |

したがって、キュー側にだけ対象バッチ固定を課すのは、**手動より安全な経路に手動より厳しい制約を付ける**ことになり、原則（§2）にも反する。「指示が長く滞留したまま実行される」という残る懸念は、**指示の有効期限**（§4.5）という軽い仕組みで足りる。

> この撤回により、v3 の「論点 3（ランナーに `--expect-batch` を足すか）」は**解消**する。ランナーの仕様変更は要らない。

### C を却下する理由

* kintone Webhook の**公開仕様に、受信側が検証できる送信元署名や shared secret の記載がない**。ただし「URL 秘匿頼み」と言い切るのは強すぎる — Webhook を wake-up 信号としてのみ使い、**受信後に API トークンで指示レコードを取り直して検証**すれば、偽リクエストから直接コマンドが走ることは防げる
* それでも残るのが、**インバウンド開放・TLS 証明書の保守・DoS 対策**。#9 の主題である保守工数に直撃し、「cron から node を叩くだけ」という構成の単純さが壊れる
* B はポーリング遅延（最大 5 分）を受け入れるだけでこれらを全部回避できるため、**B を優先**する

## 4. 本命案 B — kintone をリラン指示キューにする

### 4.1 構成

```
[担当者のスマホ] --失敗した BATCH レコードの「リラン要求」にチェック--+
                                                                     |
                          [kintone 実行ログアプリ（既存・#4 で構築済み）]
                                          ^   |
                          5 分ごとに GET  |   | 状態・結果を同レコードへ書き戻す
                                          |   v
                                  [VPS: poll_control.sh (cron + flock)]
                                          |
                                          v
                              ./run_batch.sh --resume
                              （SSH で叩くのと同一のコマンド）
```

VPS からの outbound HTTPS のみ。**ポートは 1 つも開けない。**

**専用の実行指示アプリは作らない**（Q11）。失敗の通知が届いたそのレコードの上で要求し、結果も同じレコードに返る。理由は §4.10。

### 4.2 実行意味論 — at-least-once

**exactly-once は保証しない。保証しないでよい**というのが、この設計が成立する理由である。

* リランは冪等（仕様 §5.2）。同じ指示が 2 回実行されても最終状態は変わらない
* 同時実行はログアプリの分散ロック（仕様 §5.5）が Exit 5 で止める
* したがってキューに必要なのは「**いつか必ず 1 回以上実行される**」ことだけで、重い状態機械は要らない

**この前提が崩れる操作（通常実行・バックフィル）は MVP から外す**（§7）。

### 4.3 ログアプリに追加するフィールド

既存の **23 フィールド**（仕様 §8.2・`src/logapp.ts` の `LOG_APP_FIELDS`）に、`rerun_` 接頭辞で次の 10 個を足す。**BATCH レコードでのみ使う**（JOB レコードでは未選択・空のまま。詳細画面では折りたたみグループへ隔離するとよい）。追加後は 33 で、kintone のアプリあたり上限に対して十分小さい。

| フィールドコード | ラベル | 型 | 用途 |
| --- | --- | --- | --- |
| `rerun_request` | リラン要求 | チェックボックス（選択肢 `REQUEST` 1 つ） | **人間が編集する唯一のフィールド。** チェックを入れることがリラン要求になる。既定はチェックなし |
| `rerun_state` | リラン状態 | ドロップダウン（必須にしない） | 選択肢は §4.3.1。**既定は未選択**（「空」という選択肢は作らない）。クエリ上の未選択は `rerun_state in ("")`。**ポーラーだけが書く**（依頼者は閲覧のみ） |
| `rerun_requested_at` | リラン要求日時 | 日時 | **有効期限の基準**（§4.5）。初回確保時にポーラーが人間の要求時刻（`更新日時`）を退避し、以後は変えない |
| `rerun_requested_by` | リラン要求者 | 文字列 | **要求者の証跡**。初回確保時に `更新者` を退避する。ポーラーが書き戻すと `更新者` は Administrator に変わるため、**このフィールドが唯一の恒久的な証跡**になる（§4.6） |
| `rerun_claimed_host` | リラン確保ホスト | 文字列 | claim したホスト（§4.4） |
| `rerun_claim_expires_at` | リラン確保期限 | 日時 | stale 回収の判定（§4.4） |
| `rerun_attempt` | リラン試行回数 | 数値 | claim 回数。Exit 5 での再受付を数える |
| `rerun_exit_code` | リラン終了コード | 数値 | ランナーの Exit Code |
| `rerun_result` | リラン結果 | 複数行文字列 | **固定要約のみ**（§4.6 のマスキング規則） |
| `rerun_batch_id` | リラン実行バッチID | 文字列 | resume が新たに発行したバッチの `batch_id`（確定規則は §4.4.1） |

既存フィールドと同じく、**フィールドコードは小文字スネークケース・ラベルは日本語**とする（`status` / ステータス、`batch_id` / バッチ実行ID と同じ体系）。

#### 4.3.0 なぜ人間の入力をチェックボックスに分けるか

当初は「人間が `rerun_state` を `REQUESTED` にする」設計だったが、**撤回する。**

**フィールド単位のアクセス権は「そのフィールドを編集できるか」しか制御できず、どの選択肢を選べるかは制御できない。** `rerun_state` を依頼者に編集させると、ドロップダウンの 7 値すべてを書けてしまう。実行していないのに `SUCCESS` を選べば**リランが成功したように見える記録が残り**、`CLAIMED` を選べばポーラーが stale とみなして `UNKNOWN` へ倒す。

そこで**人間の入力と機械の状態を分離する**。

| | フィールド | 編集できるのは |
| --- | --- | --- |
| 入力 | `rerun_request`（チェックボックス） | **依頼者**（と運用管理者） |
| 状態 | `rerun_state`（ドロップダウン） | **ポーラーのみ**（人間は閲覧） |

チェックボックスは値が「入っているか / いないか」の 2 通りしかないため、**誤った値を書くという事故が構造的に起きない**。操作もチェック 1 つで済み、スマホからでも押しやすい。

#### 4.3.1 `rerun_state` の選択肢

**既存の `status` / `record_type` に合わせ、選択肢は大文字 ASCII の識別子とする。** 日本語の選択肢は使わない — 同じアプリの中で `status` が `SUCCESS` / `FAILED`、`record_type` が `BATCH` / `JOB` である以上、`rerun_state` だけ日本語では体系が割れる。クエリ・ログ・スクリプトでの扱いも識別子のほうが安全である（表示上の分かりやすさはラベルと一覧の設定で担保する）。

**すべてポーラーが書く。人間は書かない。**

| 値 | 意味 | 誰が設定するか |
| --- | --- | --- |
| （未選択） | 未処理。新規要求はこの状態でチェックが入る | 既定 |
| `REQUESTED` | Exit 5 で差し戻した継続要求（§4.4） | ポーラー |
| `CLAIMED` | ポーラーが確保し、実行している | ポーラー |
| `SUCCESS` | リランが正常終了した（Exit 0） | ポーラー |
| `FAILED` | リランが失敗した（Exit 1 / 2 / 3 / 4） | ポーラー |
| `UNKNOWN` | 確保期限を超過し、結果を確認できない | ポーラー |
| `EXPIRED` | 有効期限を過ぎたため実行しなかった | ポーラー |
| `CANCELED` | 受付条件を満たさず取り消した | ポーラー / 運用管理者 |

`SUCCESS` / `FAILED` は `status` と同じ語を意図的に再利用する（意味も「成功した / 失敗した」で一致する）。実行中を表す語は `status` の `RUNNING` と紛れるため **`CLAIMED`** とした — `rerun_claimed_host` / `rerun_claim_expires_at` とも語が揃う。

**専用アプリの 14 フィールドが 10 に減る理由**は、`profile` / `host` / `started_at` が **BATCH レコードに既に存在する**からである。専用アプリのフィールドの多くは、ログアプリが持っている文脈の再現だった。

人間が profile や host を選び直さないため、**取り違えが構造的に起きない**。

> ログアプリへの独自フィールド追加は安全である。`checkLogAppCommand`（`src/commands/initLogapp.ts`）は**期待フィールドの存在と型だけを検査し、余分なフィールドを拒否しない**。ランナーの書込もフィールド指定であり、レコード全体を上書きしない。
>
> **ただし裏返しの穴がある**（Codex 指摘）: `init-logapp` は `LOG_APP_FIELDS` からしかフィールドを作らず、`--check-logapp` は `rerun_*` が 1 個も無くても OK を返す。**ランナーは変更しない**方針を保つため、**ポーラー側が自前の `check` を持ち**、起動時に 10 フィールドの存在・型・選択肢を検証して、欠けていれば API を呼ぶ前に停止する。配布物（テンプレート・ZIP）への反映は第 2 段階で検討する。

### 4.4 ポーラーの処理

**チェックが入っている = まだ終端に至っていない要求**、という不変条件を置く。ポーラーは終端状態にするとき**必ずチェックを外す**。これにより候補クエリは 1 条件で済む。

1. **`flock` でホスト単位に一重化**（cron は前回の終了を待たないため必須）
2. 1 回の GET で候補を取る（無ければ即終了 = API 1 回）。条件は `record_type = BATCH` かつ `profile` / `host` が**ローカル設定値と一致**し、**`rerun_request` にチェックがある**こと。`started_at` asc で FIFO
3. 取得した各レコードを `rerun_state` で振り分ける:

| `rerun_state` | 意味 | 処理 |
| --- | --- | --- |
| （未選択） | **新規要求** | 要求時刻・要求者を退避して claim |
| `REQUESTED` | **Exit 5 からの継続** | 要求時刻・要求者は**据え置き**で claim |
| `CLAIMED` かつ期限内 | 実行中 | 何もしない |
| `CLAIMED` かつ期限超過 | **stale** | `UNKNOWN` + チェックを外す。**再実行しない** |
| 終端値（`SUCCESS` 等） | **再要求**（終端でチェックを外した後に人間が入れ直した） | 前回結果をクリアし、要求時刻・要求者を取り直して claim |

4. `status` が**失敗系（`FAILED` / `ABORTED` / `TIMEOUT`）でなければ `CANCELED` + チェックを外す**（誤操作へのフィードバック。§4.4.2）
5. **有効期限を過ぎていれば `EXPIRED`** + チェックを外して終了（§4.5）
6. **revision を条件に `CLAIMED` へ更新**して確保する。**チェックは付けたまま**にする。同時に `rerun_claimed_host`・`rerun_claim_expires_at`（= 現在 + `batchTimeoutSec` + 余裕）・`rerun_attempt + 1` を書く。新規要求・再要求のときだけ、kintone の `更新日時` と `更新者` を `rerun_requested_at` / `rerun_requested_by` へ退避する — **ポーラーがまだ触っていないこの時点でのみ、人間の要求時刻と要求者が読める**（§4.6）
7. 固定の絶対パスを **argv 配列で起動**（`sh -c` や文字列連結を使わない）
8. 終了コードを状態にマップして書き戻す。**Exit 5 だけは `REQUESTED` + チェックを付けたまま**（次回また拾わせる）。**それ以外の終端はチェックを外す**

チェックの扱いを 1 行にまとめると: **終端に達したら外す。継続なら残す。** 人間が再要求したいときは、もう一度チェックを入れるだけでよい。

`profile` / `host` は**レコードから読んで実行に使うのではなく、ローカル設定値でクエリを絞る**。レコード値をコマンド組み立てに使わない原則（§4.6）はそのまま保たれる。

#### 4.4.2 失敗系でないレコードへの要求は取り消して返す

`status` の判定は**クエリではなくコードで行う**。成功したバッチにチェックが入っていた場合、クエリで落とすと**ポーラーが永久に取得せず、チェックが入ったまま滞留する**。滞留は §4.9 のポーラー停止検知の条件でもあるため、**ポーラーは正常なのに停止通知が飛び続ける**。

取得したうえで `CANCELED` + チェック解除 + 理由の固定文言を返せば、人間に理由が届き、滞留通知は本当の停止だけを指す。API 消費は増えない。

**revision 競合時の扱い**（Codex 指摘）: ランナーのログアプリ更新は revision 条件を持たない（`logapp.ts` の `update()`）。さらに前回失敗した書込は `resendPending()` で**次回実行時に同じレコードへ再送**される。したがって claim 後の結果書込が revision 競合で失敗しうる。ただし**ランナーは `rerun_*` を一切書かない**ため、リラン状態が壊れることはない。競合したら**再 GET して 1 回だけ再適用**する（`rerun_*` は他の書き手がいないので安全）。それでも失敗したら stale 回収に委ねる。

### 4.4.1 `rerun_batch_id` の確定規則

resume は新しい `batch_id` で BATCH レコードを作るが、**確定できない場合がある**。同一アプリになっても、この規則は必要である。

* 照合は `record_type = BATCH` かつ `profile` / `host` がローカル設定値と一致し、`started_at` が claim 時刻より後のもの
* **要求レコード自身を除外する**
* **0 件** — resume の対象が無ければ BATCH レコードは作られずに Exit 0 で終わる（`runAll.ts` は resume 選抜の直後に return し、BATCH 作成はその後段）。`SUCCESS` としてよく、`rerun_batch_id` は**空欄が正しい**
* **2 件以上** — claim から結果書込までの間に定期 cron が割り込むと候補が並ぶ。`profile` / `host` では区別できないため、**帰属を断定せず空欄にする**

**終了コードのマッピング**（仕様 §10.3。**ロック競合は Exit 5**）:

| Exit | `rerun_state` | 意味 |
| --- | --- | --- |
| 0 | `SUCCESS` | 復旧した（resume 対象が無かった場合も含む） |
| 1 / 4 | `FAILED` | 設定・検証エラー、または再開できる直近バッチ無し（1）／部分成功（4）。**原因は断定せず、ログアプリを見るよう促す** |
| 2 | `FAILED` | データが直っていない（#8 クラス B）。**書く前に止まっているので無害** |
| 3 | `FAILED` | 基盤側がまだ復旧していない |
| **5** | **`REQUESTED` へ戻す**（`rerun_attempt` を加算） | 通常バッチが実行中。**失敗ではなく「待つべき」状態** |
| signal / その他 | `UNKNOWN` | 成功・失敗を断定しない |

**stale 回収**: `CLAIMED` のまま `rerun_claim_expires_at` を過ぎたレコードは `UNKNOWN` にする。実際に resume が走ったかは、**同じアプリの中で**そのレコードより後の BATCH レコードを見れば判断できる（別アプリ間の突合が要らない）。単純な再取得による自動リトライはしない。

### 4.5 指示の有効期限

**指示が長く滞留したまま実行されること**への対策は、対象バッチ固定ではなくこれで足りる（§2.1）。

* **要求時刻から** N 時間（既定案: 6 時間）を過ぎた要求は、実行せず `EXPIRED` + チェック解除にする
* 基準は `rerun_requested_at` フィールドとする。新規要求・再要求の claim 時に kintone の `更新日時`（人間がチェックを入れた時刻）を退避し、**その要求が終端に至るまで書き換えない**
* **`更新日時` をそのまま基準にしてはならない**（Codex 指摘）。Exit 5 で差し戻すたびにポーラー自身の編集で `更新日時` が進み、**期限が無限に延びる**。通常バッチが長引くほど古い要求が生き残ってしまう
* BATCH レコードの `作成日時` も使えない。**バッチが走った時刻**であって要求時刻ではない
* 人間には「この要求は古い。現在の状態を見て、必要なら出し直すか、バックフィル（`--as-of`）に切り替えてほしい」という意味になる
* これは**リランの動作を変えるものではなく、古い依頼を受け付けないという受付側の規則**である

### 4.6 セキュリティ要件

**この節を外すと、kintone のレコード追加権限が VPS 上の任意コマンド実行になる。**

* **レコードの値をシェルに渡さない。** `操作`・`プロファイル`・`ホスト` はドロップダウンの列挙値で受け、**ローカル allowlist のキーとしてのみ**使う。レコード値からパス・環境変数名・作業ディレクトリを組み立てない
* **`sh -c` と文字列連結を使わない。** 固定の絶対パスを argv 配列で起動する
* **ランナーの stdout / stderr をそのまま指示レコードへ転記しない。** 仕様 §8.4 のマスキングを迂回して認証情報・SQL リテラル・レコード値が漏れる経路になる。**固定の要約とログアプリへのリンクだけ**を返す
* **要求の連投による DoS を防ぐ** — profile ごとのチェック済みレコードの同時件数上限、および §4.5 の有効期限。なお BATCH レコードは人間が追加できない（`rerun_request` の編集権限しか与えない）ため、**レコードそのものを量産される経路は存在しない**。要求できる母数は「過去に失敗したバッチの件数」に限られる
* **権限は kintone 標準のアクセス権で実現する**（Q9 裁定済み）。ランナー側に権限機構を持たせない:

| 主体 | ログアプリでの権限 | 実現手段 |
| --- | --- | --- |
| リラン依頼者（ジョブ管理・実ユーザー） | **`rerun_request` だけ編集可** | **フィールド単位のアクセス権**（ジョブ管理 = 編集可の行） |
| その他の実ユーザー | 全フィールド閲覧のみ | 全編集可能フィールドに Everyone = 閲覧のみの行 |
| VPS のトークン | **全フィールド編集可** | API トークンの権限設定（閲覧 + 編集）。**フィールド単位に絞ることはできない**（下記） |

**アプリのレコード編集権は「制限なし」でよい**（実機構成 2026-08-27）。編集画面には誰でも入れるが、全フィールドが閲覧のみのため実際には何も変更できず、唯一の例外 `rerun_request` の編集可否がそのまま「誰がリランを起こせるか」になる。制御点がフィールド ACL に一本化され、アプリ権限との二重管理が要らない。

> **運用ルール**: ログアプリへ今後フィールドを追加する場合は、**Everyone = 閲覧のみの ACL 行を必ずセットで追加**する。レコード編集権が開いているため、ACL の無い新フィールドは誰でも編集できてしまう（ACL 設定スクリプトは対象をフォーム定義から動的に取るため、再実行すれば自動で埋まる）。

**API トークンは Administrator 相当の権限で動作し、フィールド単位のアクセス権の対象外である。** したがってポーラーのトークンを `rerun_*` だけに制限することはできない。これは受容する — §4.10 のとおり、VPS の `.env` にはランナー用のログアプリ書込トークンが既にあり、**同じ能力がすでに存在する**ためである。専用アプリに分離しても、そちらのトークンが同様に Administrator 相当になるだけで、フィールド単位の保護は得られない。

**重要な帰結: 実行者の証跡が `更新者` には残らない。** トークンによる操作の `更新者` は Administrator になるため、ポーラーが結果を書き戻した時点で、人間が要求したという `更新者` の記録は**上書きされる**。変更履歴を辿れば追えるが、それに依存しない。

> **`rerun_state` を編集できる人 = リランを起こせる人**、という 1 対 1 対応になる。どのグループを充てるかは**運用判断**であり、設計上の制約にしない。
>
> **`rerun_request` にチェックを入れられる実ユーザー = リランを起こせる人**、という 1 対 1 対応になる。フィールド単位のアクセス権は実ユーザーには効くため、**「誰が要求できるか」の制御は無傷**である。効かないのはトークン側だけで、そこは元から書込可能だった。
>
> 依頼者に編集させるのが**チェックボックス 1 つだけ**なので、書ける値は「入れる / 外す」の 2 通りしかない。`rerun_state` の 7 値を書けてしまう問題（§4.3.0）はここで構造的に消える。

### 4.10 なぜ専用の実行指示アプリを作らないか（Q11）

検討途中では専用アプリ案を採っていたが、分離の根拠 4 点がいずれも成立しないことを確認して撤回した。

| 分離の根拠 | 検証結果 |
| --- | --- |
| 権限の非対称性 | **崩れる** — Q9 のフィールド単位アクセス権で `rerun_state` だけを編集可にできる。同じ機構で解決する |
| 状態機械の分離 | **崩れる（ただし条件付き）** — ランナーは `rerun_*` を一切書かないので、**リラン状態が壊れる経路は無い**。ただし「失敗 BATCH レコードは以後触られない」は無条件には成り立たず、`resendPending()` による再送や `recoverStale()` で revision が上がりうる（Codex 指摘）。影響は結果書込の revision 競合という**可用性の問題**に限られ、§4.4 の再 GET + 1 回再適用で扱える |
| 通知ルールの分離 | 弱い — #4 の 2 条件に足すだけ |
| API 枠の分離 | **崩れる** — 固定費 288 回/日（約 3%）+ リラン 1 回あたり 3〜4 回。ログアプリの枠が逼迫するとすれば実行回数自体が多いということで、それは指示アプリの有無ではなく仕組み側の問題である |
| （Codex が追加提起）トークン漏えい時の影響範囲 | **分離の根拠にならない** — ポーラーは VPS 上で動き、その `.env` には**ランナー用のログアプリ書込トークンが既にある**。同一マシンでログアプリを書き換える能力はすでに存在する。むしろ分離案では `.env` にトークンが 2 本になるため、統合のほうが露出面は小さい。**加えて API トークンは Administrator 相当**なので、専用アプリに分けてもそちらのトークンが全フィールドを編集でき、フィールド単位の保護は得られない |

得られる利点は次のとおり。

* **新規アプリの構築が不要**（フィールド定義・アクセス権・通知設定が丸ごと消える）。#9 の主題である保守工数に直接効く
* **追加フィールドが 14 → 7 に減る**（§4.3）
* **失敗レコードを見ている人がそのレコードで要求する**ため、profile / host の取り違えが構造的に起きない
* **失敗・要求・結果が同一レコードに並ぶ**ので、`batch_id` での突合が不要になる

API 枠を実際に分けたい規模になった場合に限り、第 2 段階で分離を再検討する。

### 4.7 リビジョンの扱い — 記録するが止めない

#7 で書いたとおり **as-of が固定するのは入力の時刻基準であって処理ロジックではない**。失敗後に `git pull` されていれば、resume は新しいコードで走る。

これは**手動リランでも同じ**なので、§2 の原則により**キュー側で実行を止める条件にはしない**。実行時の `git_ref` を指示レコードに記録し、**後から突き合わせられるようにする**のみとする（ログアプリ側にも `git_ref` は残る）。

厳密な再現が要る場合の手順（失敗時の commit を checkout してから resume する）は #7 のとおりで、これは人間が SSH で行う作業として残る。

### 4.8 API 消費

日次 API リクエスト数は**アプリ単位**でカウントされる（#5 で確認した仕様。スタンダードコース 10,000 回／ワイドコースはより大きい）。

* **固定費（待機ポーリング）**: 5 分間隔 × 24 時間 = **288 回/日**、日次上限（スタンダードコース 10,000 回）の約 **3%**。リラン回数によらず一定
* **変動費（リラン 1 回あたり）**: claim PUT + 結果 PUT + BATCH 照合 GET で **3〜4 回**。期限切れ・stale 回収・Exit 5 での差し戻し・revision 競合の再試行で数回増える
* 当初「リラン回数と無関係」と書いたのは**固定費のみを指した不正確な表現**だった（Codex 指摘）。ただし 1 回 4 回程度なので、結論（枠は問題にならない）は変わらない
* **複数ホストなら `288 回 × ホスト数`**
* **業務アプリの枠は待機中まったく消費しない。** ポーリングはログアプリだけを見る。実際に resume すれば業務アプリの API は当然消費する
* ログアプリの枠が実際に逼迫するとすれば、それは**実行回数そのものが多い**ということであり、ポーリングの有無ではなく仕組み側の問題である（Q11）

### 4.9 残る弱点

* **ポーラー自体が動いていなければ何も起きない** — #4 以来の「起動しなかった事故」と同型。対策は kintone 側だけで組める。ただし**通常の条件通知では作れない** — 条件成立の瞬間に発報するため、チェックを入れるたびに「停止の可能性」が飛ぶ誤報になる（#7 の誤アラート問題）。**リマインダーの条件通知**（日時基準・**発報時点で条件を再評価**・最小単位 1 時間）を使う:
  * タイミング: **`更新日時` の 1 時間後**
  * 条件: `rerun_request` に REQUEST を含む **かつ** `rerun_state` が**未選択**
  * ポーラー正常時は 5 分以内に `CLAIMED` になるため、1 時間後の再評価で条件を満たさず**発報しない**。死んでいれば未選択のままなので発報する
  * 条件に `REQUESTED` を**含めない** — Exit 5 の差し戻し中に通常バッチが 1 時間を超えて走っているだけで誤報するため。差し戻しループ中のポーラー死は検知範囲外とし、誤報ゼロを優先する（実機設定済み 2026-08-27・実発報確認済み）
  * **公式仕様**（kintone ヘルプ「通知の種類」）: リマインダーは **10 分間隔の巡回**で条件合致レコードを評価して送信する。したがって着信は指定時刻から**最大 +10 分**遅れる。送信者は常に Administrator。基準の `更新日時` が変わらない限り**発報は 1 回きり** — ポーラー停止時の通知はちょうど 1 通で鳴り続けない（見逃すと再通知は無い点は運用注意）
  * 任意で、通常の条件通知「`rerun_request` に REQUEST を含む」を**受付確認**（毎回飛ぶことが正しい ACK）として併設できる
* VPS ごと落ちている場合は動かない（ただしその状況では SSH も入れない）
* 最大 5 分の遅延（手動リランより短い — §2.1）
* `host` によるルーティングは障害時の failover を失う。将来は「実行プール + profile 一致」での割り当てを検討

## 5. 案 F — 限定的な自動 resume（**却下 / Q8 裁定済み**）

**2026-08-27 裁定: 却下**（`reviews/decisions.md` Q8）。連載および仕様の方針「スケジューラ側の自動リトライは使わない。復旧は冪等リランに一本化する」は**文言変更せず維持**する。**再提案しない。**

却下理由（記録として残す）:

* 当日の定期実行が**そもそも起動しなかった**日、自動 resume は直近バッチ = **前日のバッチ**を拾い、前日の as-of で再実行する。**人間の判断が挟まらないため、この「ずれ」を誰も検知できない**（案 B では指示を出す人間が現在の失敗を見て判断している）
* 「救えるのは #8 のクラス A だけ」という当初の記述も不正確だった。データが偶然直っていればクラス B も走り、原因未解消なら Exit 2 を再発させる
* 「失敗検知連動の再起動」と「独立スロットでの 1 回限りの resume」は技術的には区別できるが、運用上はいずれも**人間の判断を挟まずに外側から `--resume` する**仕組みであり、方針の実質的な変更にあたる

復旧の起動手段は**案 B に一本化**する。

## 6. 案 E — リランが要らない設計に寄せる

最良の解決は「駆けつけなくてよいこと」であり、これは既に #7 / #8 の主張。

* 累積・全量型のジョブなら翌日の実行が欠落を吸収する → そもそもリランが要らない
* 期間窓型は残るので E だけでは解決しない。**E で母数を減らし、残りを B で拾う**という重ね方になる

## 7. 推奨と MVP スコープ

1. **E** を設計方針として先に効かせる（母数を減らす）
2. **G** — クラウドで管理プレーンが使えるならそれが最適。B は要らない
3. **B** を VPS・オンプレ向けの本命として実装。**MVP は以下に限定**:
   * 操作は **リランのみ**（通常実行・バックフィルは冪等前提が崩れるため後段へ）。MVP では `rerun_state` が操作の種類も兼ねるため、操作フィールドは設けない
   * **単一ホスト**
   * `flock`（§4.4）・有効期限（§4.5）・セキュリティ要件と権限分離（§4.6）は MVP に含む
   * 意味論は **at-least-once** と明記
   * **ランナーの変更は行わない**（§2）
4. **F** は却下済み（Q8）

B の価値は、#9 の利点（書込可トークンを GitHub に置かない）を保ったまま、#6 のブラウザボタンと同等の操作性が得られること。しかも**失敗通知が届いた kintone のアプリの中でリランまで完結する**ため、担当者の導線が 1 本で済む。
