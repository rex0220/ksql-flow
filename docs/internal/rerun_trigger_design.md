## 1. 問題

記事 #9 で「VPS 構成の弱点」として明示したとおり。

| 環境 | リランの操作 | 出先で押せるか |
| --- | --- | --- |
| #4 Windows サーバー | サーバーに入って 1 コマンド | 社内網に入れれば |
| #6 GitHub Actions | ブラウザで Run workflow + resume チェック | **押せる**（スマホ可） |
| #9 VPS + cron | SSH で入って 1 コマンド | **SSH 鍵を持つ端末が要る** |

失敗の通知は kintone の条件通知でスマホまで届く（#4 で構築）。**気づけるのに直せない**、という非対称がある。休日・外出先で顕在化する。

### 1.1 対象範囲（v2 で限定）

当初「自前でスケジューラを持つ環境すべて」と書いたが、これは誤り。**クラウドには管理プレーンからの実行手段がある**（Codex 指摘）。

* Cloud Run Jobs — Google Cloud Console から実行を起こせる
* AWS EC2 — Systems Manager Run Command で SSH ログインなしにコマンドを送れる

したがって本メモの対象は **VPS・オンプレ・クラウド管理プレーンを採用しない VM** に限る。クラウドで管理プレーンが使えるなら、そちらが実装ゼロの解（案 G）。

## 2. 前提として動かせない条件

* 復旧の正は冪等リラン（`--resume`）。スケジューラ側の自動リトライは採らない（連載を通じた方針）
* resume に必要なのは ①ジョブリポジトリの clone ②書込可トークン ③kintone への到達 の 3 つだけ（仕様 §6.2）
* 書込可トークンの露出面は増やしたくない（#9 で「GitHub に置くのは閲覧のみトークン、書込は VPS の `.env` だけ」を利点として書いた）
* VPS にインバウンドポートを開けたくない（#9 の構成は cron から node を叩くだけ・ufw と fail2ban はイメージ既定のまま）

### C を却下する理由（v2 で理由を修正）

* kintone Webhook の**公開仕様に、受信側が検証できる送信元署名や shared secret の記載がない**。ただし Codex の指摘どおり「URL 秘匿頼み」と言い切るのは強すぎる — Webhook を wake-up 信号としてのみ使い、**受信後に API トークンで指示レコードを取り直して検証**すれば、偽リクエストから直接コマンドが走ることは防げる
* それでも残るのが、**インバウンド開放・TLS 証明書の保守・DoS 対策**。#9 の主題である保守工数に直撃し、「cron から node を叩くだけ」という構成の単純さが壊れる
* B はポーリング遅延（最大 5 分）を受け入れるだけでこれらを全部回避できるため、**B を優先**する。C の却下自体は妥当

## 4. 本命案 B — kintone をリラン指示キューにする

### 4.1 構成

```
[担当者のスマホ] --レコード追加--> [kintone 実行指示アプリ]
                                          ^   |
                          5 分ごとに GET  |   | 状態・終了コードを書き戻す
                                          |   v
                                  [VPS: poll_control.sh (cron + flock)]
                                          |
                                          v
                                  run_batch.sh --resume
```

VPS からの outbound HTTPS のみ。**ポートは 1 つも開けない。**

### 4.2 実行意味論 — at-least-once（v2 で明記）

**exactly-once は保証しない。保証しないでよい**というのが、この設計が成立する理由である。

* リランは冪等（仕様 §5.2）。同じ指示が 2 回実行されても最終状態は変わらない
* 同時実行はログアプリの分散ロック（仕様 §5.5）が Exit 5 で止める
* したがってキューに必要なのは「**いつか必ず 1 回以上実行される**」ことだけで、重い状態機械は要らない

**この前提が崩れる操作（`通常実行`・`バックフィル`）は MVP から外す**（後述 §7）。

### 4.3 実行指示アプリのフィールド

| フィールド | 型 | 用途 |
| --- | --- | --- |
| 操作 | ドロップダウン | MVP は `リラン` のみ。**自由入力させない** |
| 対象プロファイル | ドロップダウン | `prod` / `stg` — allowlist |
| 対象ホスト | ドロップダウン | どのホストが拾うか |
| **対象バッチ ID** | 文字列 | **指示作成時点の失敗バッチを固定する**（§4.4） |
| **対象 git_ref** | 文字列 | 失敗時のリビジョン。実行時に突合（§4.5） |
| 状態 | ドロップダウン | `受付待ち` / `実行中` / `完了` / `失敗` / `結果不明` / `対象ずれ` / `取消` |
| 確保ホスト・確保期限 | 文字列・日時 | claim と stale 回収（§4.6） |
| 実行バッチ ID | 文字列 | **新たに発行された実行バッチ**（対象バッチ ID とは別物） |
| 終了コード・要約 | 数値・文字列 | 結果の書き戻し（§4.7 のマスキング規則に従う） |

レコードの作成者は kintone が自動で持つので、**誰がリランを指示したかの証跡が標準で残る**。

### 4.4 対象バッチの固定 — 最重要（Codex BLOCKER 1・実装で確認済み）

`--resume` の対象バッチは**実行時点で**解決される。[logapp.ts:300](../../src/logapp.ts) の実装:

```
query: `record_type in ("BATCH") and profile = "..." order by started_at desc limit 1`
```

つまり「土曜に失敗 → 指示を作成 → ポーラーが拾う前に日曜の定期実行が走る」と、**指示は土曜分ではなく日曜分を対象にする**。#7 に書いた「resume で救えるのは次のスケジュールが来る前だけ」の裏返しで、キューを挟むと待ち時間のぶん踏みやすくなる。

**必須要件**: ポーラーは実行直前にログアプリの直近バッチを取得し、`対象バッチ ID` と一致しなければ**実行せず** `対象ずれ` として終了する。人間に「この指示はもう使えない。バックフィルに切り替えるか、新しい失敗に対して指示を出し直せ」と返すのが正しい。

> ランナー側に「指定バッチを正として resume する」契約（例: `--resume-batch <id>`）があれば、この照合を CLI に寄せられる。仕様追加の要否は裁定事項（§8）。

### 4.5 リビジョンの突合（Codex 指摘 9）

`対象ホスト` を指定しても、失敗時と同じ SQL・config・ランナー版で走る保証はない。#7 で書いたとおり **as-of が固定するのは入力の時刻基準であって処理ロジックではない**。

* 指示の `対象 git_ref` と、実行ホストの実際の `git_ref` を突合する
* dirty worktree（未コミットの変更あり）では実行しない
* 不一致なら自動実行せず、`対象ずれ` として人間の明示承認に回す

### 4.6 ポーラーの処理

1. **`flock` でホスト単位に一重化**（cron は前回の終了を待たないため必須 — Codex 指摘 3・Gemini も同旨）
2. `状態 = 受付待ち` かつ `対象ホスト = 自ホスト` を**作成日時 asc で 1 件**取得（無ければ即終了 = API 1 回）
3. **revision を条件に `実行中` へ更新**して確保する。同時に `確保ホスト` と `確保期限`（= 現在 + `batchTimeoutSec` + 余裕）を書く
4. §4.4 の対象バッチ照合・§4.5 のリビジョン突合。外れていれば `対象ずれ` で終了
5. 固定の絶対パスを **argv 配列で起動**（`sh -c` や文字列連結を使わない）
6. 終了コードを状態にマップして書き戻す

**終了コードのマッピング**（Gemini 指摘・ただし同氏の「ロック競合は Exit 3」は誤り。仕様 §10.3 のとおり**ロック競合は Exit 5**）:

| Exit | 指示レコードの状態 | 意味 |
| --- | --- | --- |
| 0 | `完了` | 復旧した |
| 2 | `失敗` | データが直っていない（#8 クラス B）。**書く前に止まっているので無害** |
| 3 | `失敗` | 基盤側がまだ復旧していない |
| **5** | **`受付待ち` へ戻す**（試行回数を加算） | 通常バッチが実行中。**失敗ではなく「待つべき」状態** |

**stale 回収**: `実行中` のまま `確保期限` を過ぎた指示は `結果不明` にし、ログアプリ側に対応する実行バッチがあるかを照合して人間が判断する。単純な再取得による自動リトライはしない。

### 4.7 セキュリティ要件

**この節を外すと、kintone のレコード追加権限が VPS 上の任意コマンド実行になる。**

* **レコードの値をシェルに渡さない。** `操作`・`プロファイル`・`ホスト` はドロップダウンの列挙値で受け、**ローカル allowlist のキーとしてのみ**使う。レコード値からパス・環境変数名・作業ディレクトリを組み立てない
* **`sh -c` と文字列連結を使わない。** 固定の絶対パスを argv 配列で起動する（Codex 指摘 5）
* **ランナーの stdout / stderr をそのまま指示レコードへ転記しない**（Codex 指摘 5）。仕様 §8.4 のマスキングを迂回して認証情報・SQL リテラル・レコード値が漏れる経路になる。**固定の要約とログアプリへのリンクだけ**を返す
* **指示の連投による DoS を防ぐ** — プロファイルごとの `受付待ち` 上限、指示の有効期限
* **権限は kintone 標準のアクセス権で実現する**（Q9 裁定済み）。ランナー側に権限機構を持たせない:

| 主体 | 指示アプリ | ログアプリ | 実現手段 |
| --- | --- | --- | --- |
| リラン依頼者 | **レコード追加**（結果フィールドは編集不可） | 閲覧のみ | アプリのアクセス権 + **フィールド単位のアクセス権** |
| 通知の受け手 | 閲覧のみ | 閲覧のみ | アプリのアクセス権 |
| VPS のトークン | 閲覧 + 編集（**追加不要**） | 追加・編集 | API トークンの権限設定 |

> **指示アプリのレコード追加権限 = リランを起こせる人**、という 1 対 1 対応になる。どのグループを充てるかは**運用判断**であり、設計上の制約にしない（当初「通知先グループと一致するのが設計上きれい」と書いたのは、運用判断を設計に固定してしまう書き過ぎだった — Codex 指摘 4）。
>
> 「誰が指示したか」は、人間が kintone UI からレコードを追加する以上 `作成者` に自動で残る。ポーラーは編集しかしないので `更新者` はトークン側になる点に注意。

**指示アプリとログアプリを分ける理由**（Gemini の整理が的確なので採用）: ①権限の非対称性 — 指示アプリは「人間が追加・VPS が編集」、ログアプリは「VPS が追加・編集・人間は閲覧のみ」 ②状態機械の分離 ③通知ルールの分離 ④待機ポーリングの API 枠の分離。

### 4.8 API 消費

日次 API リクエスト数は**アプリ単位**でカウントされる（#5 で確認した仕様。スタンダードコース 10,000 回／ワイドコースはより大きい）。

* **待機ポーリングの消費は指示アプリだけ**に載る。5 分間隔 × 24 時間 = 288 回/日、営業時間帯のみ（平日 7–20 時）なら 156 回/日
* **複数ホストなら `288 回 × ホスト数`**
* ただし**実際に resume すれば業務アプリとログアプリの API は当然消費する**（Codex 指摘 7）。「業務アプリの枠を一切食わない」のは待機中のみ

### 4.9 残る弱点

* **ポーラー自体が動いていなければ何も起きない** — #4 以来の「起動しなかった事故」と同型。対策は kintone 側だけで組める: 指示レコードが N 分以上 `受付待ち` のままなら条件通知で再度知らせる
* VPS ごと落ちている場合は動かない（ただしその状況では SSH も入れない）
* 最大 5 分の遅延（SSH で駆けつける時間より短い）
* `対象ホスト` の固定は障害時の failover を失う。将来は「実行プール + profile 一致」での割り当てを検討（Codex 指摘 9）

## 5. 案 F — 限定的な自動 resume（**却下 / Q8 裁定済み**）

**2026-08-27 裁定: 却下**（`reviews/decisions.md` Q8）。連載および仕様の方針「スケジューラ側の自動リトライは使わない。復旧は冪等リランに一本化する」は**文言変更せず維持**する。**再提案しない。**

却下理由（記録として残す）:

* 当日の定期実行が**そもそも起動しなかった**日、自動 resume は直近バッチ = **前日のバッチ**を拾い、前日の as-of で再実行する（§4.4 の実装）。安全にするには対象バッチ固定のガードが前提になり、**「cron 1 行」という唯一の利点が消える**
* 「救えるのは #8 のクラス A だけ」という当初の記述も不正確だった。データが偶然直っていればクラス B も走り、原因未解消なら Exit 2 を再発させる
* 「失敗検知連動の再起動」と「独立スロットでの 1 回限りの resume」は技術的には区別できるが、運用上はいずれも**人間の判断を挟まずに外側から `--resume` する**仕組みであり、方針の実質的な変更にあたる

復旧の起動手段は**案 B に一本化**する。

## 6. 案 E — リランが要らない設計に寄せる

最良の解決は「駆けつけなくてよいこと」であり、これは既に #7 / #8 の主張。

* 累積・全量型のジョブなら翌日の実行が欠落を吸収する → そもそもリランが要らない
* 期間窓型は残るので E だけでは解決しない。**E で母数を減らし、残りを B で拾う**という重ね方になる

## 7. 推奨と MVP スコープ

1. **E** を設計方針として先に効かせる（母数を減らす）
2. **G** — クラウドで管理プレーンが使えるならそれが最適。B は要らない
3. **B** を VPS・オンプレ向けの本命として実装。**MVP は以下に限定**:
   * 操作は **`リラン` のみ**（`通常実行`・`バックフィル` は冪等前提が崩れるため後段へ）
   * **単一ホスト**
   * 対象バッチ ID の固定（§4.4）・`flock`（§4.6）・権限分離と出力マスキング（§4.7）は MVP に含む
   * 意味論は **at-least-once** と明記
4. **F** は却下済み（Q8）。復旧の起動手段は B に一本化する

B の価値は、#9 の利点（書込可トークンを GitHub に置かない）を保ったまま、#6 のブラウザボタンと同等の操作性が得られること。しかも**失敗通知が届いた kintone のアプリの中でリランまで完結する**ため、担当者の導線が 1 本で済む。

### 8.1 論点 3 — 対象バッチ固定をどこで担保するか

#### 何が問題か

`--resume` は**実行時点で**対象バッチを解決する（§4.4）。指示の作成時刻 T0 と実行時刻 T1 の間に定期実行が走ると、指示が意図していないバッチを対象にする。指示キューは T1 - T0 が最大 5 分（ポーラーが止まっていればもっと長い）あるため、この隙間が構造的に存在する。

#### 選択肢

**① ポーラー側で照合する（ランナー変更なし）**

ポーラーが実行直前に直近バッチを取得し、`対象バッチ ID` と一致しなければ実行しない。

* 利点: **公開済み v0.4.0 のまま実装できる**。仕様変更なし。第 1 段階（§9）にそのまま乗る
* 欠点: **TOCTOU の隙間が残る**。照合してから `run_batch.sh` が `findLatestBatch` を呼ぶまでの数秒間に、定期実行が新バッチを開始しうる
* 補足: この隙間の実害は限定的である。新バッチが走り出していれば**分散ロック（§5.5）が Exit 5 を返す**ので、指示は `受付待ち` へ戻るだけ（§4.6 のマッピング）。危険なのは「新バッチが照合後に開始して完了まで終わった」場合だけで、その場合も resume 対象が無く no-op になる（結果表示だけが不正確になる）
* 欠点 2: 選抜規則の一部がランナーの外に複製される。仕様 §6.3 が変わるとポーラーが黙って古くなる

**② ランナーに `--resume-batch <id>` を足す（対象を ID で指定する）**

* 利点: 原子的。照合とバッチ解決が同一プロセス内で完結し、TOCTOU が消える
* 利点 2: 「特定のバッチをリランする」が CLI 単体でもできるようになる
* **欠点（重い）**: **「直近バッチのみ」という不変条件が壊れる**。任意の過去バッチを resume できると、2 週間前の as-of で現在の集計結果を上書きしうる。これは実質バックフィルであり、#7 で「resume で救えるのは次のスケジュールが来る前だけ。それを過ぎたらバックフィル（`--as-of`）」と書いた線引きと衝突する
* 採るなら「指定 ID が直近バッチでなければ拒否する」等のガードが要り、それは結局 ③ と同じ意味論になる

**③ ランナーに `--expect-batch <id>` を足す（選択子ではなく事前条件）**

対象の解決規則は**現行のまま「直近バッチ」** とし、解決した結果が指定 ID と異なれば**実行せずに専用の Exit で終了する**、という事前条件アサートだけを足す。

* 利点: **原子的**（ランナー内部の `findLatestBatch` 直後に判定する）
* 利点 2: **新しい能力を一切増やさない**。「直近バッチのみ resume する」という不変条件は保たれ、#7 の線引きとも衝突しない
* 利点 3: 意味論が ASSERT と同じ（「前提が違うなら何もせず止まる」）で、方言の思想と一貫する
* 欠点: 仕様追加（§6.3 / §10.1 / §10.3 に新 Exit または既存 Exit への割り当て）と、ランナーのリリースが要る

#### 推奨

**第 1 段階は ①、実証後に ③ を仕様提案**する。

理由は 3 つ。①は公開済み版のまま今日から検証でき（§9 の第 1 段階と整合）、①で残る隙間は分散ロックが実害の大半を吸収し、そして**③が要るという判断そのものを実測で裏づけてから仕様を触れる**からである。②は「任意バッチの resume」という別の能力を持ち込むため採らない。

③を起票する場合は、Codex（仕様レビュー担当）へ正式に依頼を出す。決めるべきは「不一致時の Exit をどれにするか」（新設するか、`1`（検証エラー）に寄せるか）である。

## 9. 実装ステップ

* **第 1 段階**: `scripts/poll_control.sh` をジョブリポジトリ側に置く。**ランナー本体の変更なし**で検証できる（Codex・Gemini とも同意見）
* **第 2 段階**: 実績が出たら `ksql-flow poll-control` 相当の公式サブコマンド化を検討

記事 #10 以降の題材になりうる（「kintone をコントロールプレーンにする」）。
