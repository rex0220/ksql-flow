[#3](https://qiita.com/rex0220/items/62e950ab1ccc5b54ff69) のスケール検証で、読取 10 万件 → UPSERT 1 万件の集計ジョブは **API 511 回**を消費しました。設計目標は約 305 回。この誤算の正体は **UPSERT のキー照合に使う事前 GET が 200 回**（1 万キー ÷ 50 キー/回）— つまり **UPSERT の API 消費の 2/3 は「書く前の確認」**でした。

そこから 1 つの疑問が出ます。

> kintone の REST API には upsert があるのだから、事前の重複判定は不要ではないのか？

本記事は、この疑問から始まった **API 削減の実測記** です。途中で「束ねれば速くなるはず」という見込みが実測に覆され、最終的にジョブ全体の API 消費が **511 → 312 回（約 4 割減）** になるまでを、数値ごとお見せします。

環境は ksql-flow v0.4.0 + kintone-sql-tools（kSQL エンジン）v3.74.0。数値はすべて特定環境（Windows 11 / Node.js / 家庭用回線 / kintone 開発環境・検証専有データ）での参考実測であり、保証値ではありません。

## 前提 — API 消費には指標が 2 つある

先に整理を 1 つ。kintone バッチの「API 消費」には別々に動く指標が 2 つあります。

| 指標 | 何を数えるか | 気にする理由 |
| --- | --- | --- |
| **HTTP 往復数** | 実際に飛ぶリクエストの本数 | 所要時間・同時接続数（上限 100）への影響 |
| **[1 日に実行できる API リクエスト数](https://cybozu.dev/ja/kintone/docs/rest-api/overview/kintone-rest-api-overview/)** | アプリごとの日次カウント（スタンダード 10,000/日） | 超えると日中の業務アプリを巻き添えにする |

普段は両者は一致します。ズレるのが [`bulkRequest`](https://cybozu.dev/ja/kintone/docs/rest-api/records/bulk-request/)（複数リクエストを 1 回の HTTP に束ねる API・最大 20 サブリクエスト）で、**bulkRequest 自体は日次カウントの対象外・内包するサブリクエストが個別に数えられます**（[制限値一覧](https://jp.cybozu.help/k/ja/admin/limitation/limit.html)に「実行した API それぞれがリクエスト数にカウント」と明記）。bulkRequest を使っている開発者にはよく知られた仕様ですが、「束ねれば API 消費が 1/20」と早合点すると、**どちらの指標も減っていなかった**ということが起きます。実際に起きたのが次の話です。

## 検証 1 — 「bulkRequest で束ねれば速くなる」は本当か

#3 の実測で、書込は 100 件/リクエストのチャンクで **UPDATE 2.67 秒/チャンク**。10 万件なら 1,000 チャンク = 44.6 分です。当初こう考えていました — *往復レイテンシが支配的なのだから、bulkRequest（最大 20 サブリクエスト）で束ねれば 1/20 に近づくはず*。

エンジン開発側から逆の仮説が返ってきます。**「同じ 100 件でも軽量アプリなら 617ms、あなたの測定は 2.67 秒。往復は同じ条件なのだから、差はペイロードのサーバ側処理では？」**（617ms は 3 フィールドの検証専用アプリでの値。当方はルックアップ込み 20 フィールド超の案件管理アプリ）。ダメ押しに、当方自身の実測にも「UPDATE は DELETE の 5.6 倍/チャンク」という、往復回数では説明できない差がありました。

決着は A/B 実測です。同一の 2,000 件（ルックアップ込みアプリの文字列フィールド UPDATE）を:

- **A**: 100 件 × 20 回の逐次 PUT
- **B**: 2,000 件を bulkRequest 1 回（20 サブリクエスト × 100 件）

ウォームアップ 1 回のあと交互に 3 セット測りました。

| セット | A（逐次 PUT ×20） | B（bulkRequest ×1） |
| --- | --- | --- |
| 1 | 56.7 秒 | 48.2 秒 |
| 2 | 49.8 秒 | 47.6 秒 |
| 3 | 40.5 秒 | 11.8 秒 |
| **中央値** | **49.8 秒** | **47.6 秒** |

**中央値で B/A = 96%。今回の条件では、bulkRequest による安定した短縮効果は確認できませんでした**（B の 3 回目だけ 11.8 秒と大きく振れましたが再現せず、仮にこちらが真値でも 1/20 には遠く届きません。n = 3 の測定なので断定は避けますが、期待した「1/20 に近づく」とは明確に別の水準です）。

この結果は、**少なくとも今回のアプリ構成では、ネットワーク往復よりも kintone 側の書込処理の寄与がずっと大きい**ことを示唆します。

もう 1 つ、仮説として付記します。bulkRequest は公式仕様で**エラー時に実行済みの処理がロールバックされます** — つまり 20 サブリクエスト = 最大 2,000 レコードについて、**途中で失敗した場合に全処理をロールバックする一括処理**です（逐次 PUT は 100 件単位の部分適用で、この保証はありません）。**この全体ロールバック保証を実現するための処理コストが、往復削減分を相殺している可能性があります。**内部実装は観測できないため仮説の域を出ませんが、そう捉えると bulkRequest は**「速度の機能」というより「全体ロールバックを提供する一括処理」と見る方が、今回の結果には合っています**。冪等リランを復旧の正とするバッチにとっては「不要な保証の対価だけ払う」形になり得る、という整理です。

いずれにせよ日次カウントは減らない。bulkRequest 対応はエンジン側で「作らずに済んだ」として保留になりました。実装前の 1 時間の実測が、リクエスト計画層の新設という大工事を止めた形です。

## 検証 2 — 効いたのは「リクエストそのものを減らす」

冒頭の疑問に戻ります。kintone の[レコード更新 API](https://cybozu.dev/ja/kintone/docs/rest-api/records/update-records/) には `upsert: true` + `updateKey` があり、**キーの存在判定を kintone 側に委ねて、1 リクエスト（100 件）で挿入と更新を書き分けられます**。従来のエンジンは read-then-write（GET でキー照合 → POST / PUT に振り分け）で、この事前 GET が例の 200 回でした。具体的にはレコード一括取得（`GET /k/v1/records.json`）に `キー in ("値1", …, "値50")` のクエリを付けて 50 キーずつ引くもので、キーの存在判定と、更新時のレコード番号指定 PUT に必要な `$id` の取得を兼ねています。native upsert は `updateKey` 指定で `$id` を知らずに書けるため、この照合ごと不要になります。

エンジン v3.74.0 で、素の UPSERT は既定でこの **native upsert** になりました。設計の要点は「**速くするだけで、意味を変えない**」ことです:

- 適用条件（単一の重複禁止キー・素の UPSERT・空文字キーなし・ソース全体でキーが一意）を 1 つでも欠く文は、**従来経路へ自動フォールバック** — 結果はどちらの経路でも等価
- 挿入 / 更新の内訳はレスポンスの `records[].operation`（`"INSERT"` / `"UPDATE"`）で厳密に取得
- 注意点は 1 つ: native は**更新だけで完結する UPSERT でも対象アプリの「レコード追加権限」を要求**します（kintone の仕様）

XL（読取 10 万 → UPSERT 1 万）で再実測しました。ウォームアップ + 3 回、**API は全 4 回で 312 回に一致**:

| | 従来（v3.72 実測） | native（v3.74 実測） |
| --- | --- | --- |
| ジョブ全体 API | 511 回 | **312 回** |
| 読取件数 | 110,000 | 100,000（キー照合の既存 1 万件読取が消滅） |
| 所要時間（中央値） | 200.7 秒 | 197.8 秒 |

ジョブ全体で **日次 API リクエスト数が 4 割減**です。ただし日次上限は**アプリ単位**でカウントされるので、アプリ別に見るのが正確です — このジョブで削減が集中するのは**書込先の顧客アプリ**で、**約 300 回（事前 GET 200 + 書込 100）→ 約 100 回**。読取側の案件アプリは約 200 回のまま変わりません。つまり「書込先アプリの日次 API 枠への負荷を 1/3 にする」改善であり、書込先が日中の業務でも使われるアプリであるほど効きます。

一方で**所要時間は 3 秒しか縮んでいません**。200 回の GET が消えたのに、です。

### 「200 回減って 3 秒」に納得がいかない方へ

「API 200 回 = 大きな時間」という直感は、**1 リクエストの重さが均一だという暗黙の仮定**に立っています。実際は 2 桁違います。

- **事前 GET 1 本** = 重複禁止フィールドの完全一致検索（`IN` 50 キー）。今回の環境では、この約 200 本が消えて所要時間差は約 2.9 秒 — 単純に差分を本数で割ると **約 15ms/本に相当**します（※個々の GET を直接計測した値ではなく、ジョブ全体の所要時間差からの概算。差には測定揺らぎも含まれます）
- **書込 1 本**（100 件 PUT）= レコード検証など、kintone 側の書込処理の塊で、**1 本 1.5〜2.7 秒**（検証 1 で見たとおり、これは往復ではなくサーバ処理の時間）

XL ジョブの内訳に直すとこうなります。

| フェーズ | 本数 | 時間 |
| --- | --- | --- |
| 読取（カーソルで 10 万件） | 約 200 本 | 約 3〜4 割 |
| **事前 GET（キー照合）** | **200 本 = 本数の 4 割** | **約 3 秒 = 時間の 1.5%** |
| 書込（UPSERT 100 チャンク） | 約 100 本 | **時間の大半** |

事前 GET は「**本数では 4 割、時間では 1.5%**」だったのです。本数の内訳と時間の内訳はまったく別の分布をしている — これが「200 本消えても 3 秒」の正体で、検証 1（束ねても縮まない）と同じ「時間はサーバ側の書込処理が支配」という一つの事実の、別の現れです。**2 つの検証は裏表の関係**にあります。

## 施策と効く指標の対応表

| 施策 | HTTP 往復数 | 日次 API カウント | 所要時間 |
| --- | --- | --- | --- |
| bulkRequest で束ねる | 減る | 減らない（サブリクエストが個別カウント） | **短縮を確認できず（実測 96%）** |
| native upsert（事前 GET 削減） | 減る | **減る（実測 511 → 312）** | ほぼ変わらない（実測 -3 秒） |

「API を減らす」と一言で言っても、**どの指標を減らしたいのかで打ち手が変わります**。所要時間を縮めたいなら、この 2 つはどちらも答えではありません（書込件数そのものを減らす = 差分だけ書く設計が本命です）。

## おまけ — 実測 312 回に潜んでいた「+1」の教訓

試算では 511 - 200 = 311 回のはずが、実測は 312 回。この +1 の帰属を 2 回間違えました。

1. 「native が実行時にフォーム定義を 1 回取る」と推測 → **エンジン実装の計測で否定**（native ON/OFF でメタデータ呼び出しは完全一致）
2. 「では EXPLAIN の修正分では」 → ランナーの本実行経路は EXPLAIN を通らず、**構造的に該当せず**

正体は、**比較の基準値（8/23 の 511 回）が古いランナーで測られていた**こと。その後のバージョンでランナー自身が加えたログアプリのフィールド検出（プロセスあたり GET 1 回）が +1 でした。HTTP リクエストのパスを全記録して 3 条件（native ON / OFF / 旧エンジン）を並べたら、ON/OFF の差はちょうど `ceil(キー数/50)` 本 — 残差ゼロで確定です。

教訓はシンプルです。**基準値と再測値は、関わる全コンポーネントの版数を固定して比べる。** 片側だけ最新にした比較は、無関係な差分を「効果」や「オーバーヘッド」に見せます。

## まとめ

- UPSERT の API 消費の 2/3 は事前 GET（キー照合）だった — native upsert（`updateKey` + `upsert: true`）化で **XL 実測 511 → 312 回（約 4 割減・全 4 回一致）**
- 「bulkRequest で束ねれば速い」は今回の条件では確認できず — **B/A = 96%（中央値）**。書込時間はサーバ側処理の寄与が大きいことを示唆。日次カウントも減らない
- **HTTP 往復数と日次 API リクエスト数は別指標**。施策がどちらに効くかを分けて考える
- native upsert は適用条件を欠くと従来経路へ自動フォールバックし結果不変。UPSERT のソースは GROUP BY 等で**キーが一意になる形**に寄せると確実に適用される。**レコード追加権限**が必要な点だけ注意
- 測定の基準値は**全コンポーネントの版数を固定**してから比べる
