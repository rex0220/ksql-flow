[#7](https://qiita.com/rex0220/items/39821af2a79b88de0ed2) では「失敗した朝に何を見て、どう復旧するか」を実機検証つきで書きました。その検証には裏話があります — **障害を注入し、ログを診断し、復旧させる一連の作業を、AI（Claude Code）が実施した**のです。

そこで次の問いが生まれます。**本番運用でも、エラー判断とリランを AI に任せられるのか？**

本記事はこの問いを入口に、バッチの失敗を 4 クラスに分類し、**「機械が拾う失敗・AI が診る失敗・人間が判断する失敗」の切り分け**を設計として整理します。結論を先に言うと — **自動リランに AI は不要で、AI の本当の出番は別の場所にあります**。

## 失敗は 4 クラスある

[#7](https://qiita.com/rex0220/items/39821af2a79b88de0ed2) の Exit Code 分類（2 = データ / 3 = 基盤 / 5 = ロック）は「通知が来た朝」の初動分類でした。運用全体を設計するには、もう一段引いた分類が要ります。なお、ここでいう「失敗」には **Exit 0 で正常終了しても、業務上の結果が期待とずれるケースを含めます** — 後半 2 クラスがまさにそれです。

| クラス | 現れ方 | ジョブは | 誰が・何が対応するか |
| --- | --- | --- | --- |
| **A. 時間が解決する可能性が高い失敗** | Exit 3 のうち**一時障害・retryable なもの**（API の 429/503 系・一時的なタイムアウト） | 無実 | **機械** — 時間を置いてリラン（1 回だけ） |
| **B. 状態を直す失敗** | Exit 2 / 3 | 無実 or 要改修 | **人間** — 何かを直してからリラン |
| **C. 成功して見える誤り** | **Exit 0** | **業務とずれている** | **設計** — 起きる前に B へ変換する |
| **D. 成功したが入力が不完全** | **Exit 0** | 無実 | **リランが日常操作** — 入力後にやり直す |

A と B は「失敗として現れる」ので通知が来ます。**危険なのは C と D — 正常終了して、数字だけが間違っている**。順に見ていきます。

### A. 時間が解決する可能性が高い失敗 — 自動リランを検討してよい唯一のクラス

kintone の一時的な API 障害（HTTP 429 / 503 系）は、ランナーが内部で指数バックオフ済みです。それでも上限を超えて Exit 3 になった障害は「もっと長く待てば直る」**可能性が高い** — 再実行そのものが原因を解決し**得る**、唯一のクラスです。ただし「待てば必ず直る」保証はありません（長時間のサービス障害・恒常的なネットワーク設定ミスが同じ顔で現れることもある）。TIMEOUT も同様で、一時的な遅さなら A ですが、**データ量増加による恒常的な時間超過は A ではなく、ジョブ設計かタイムアウト設定を直すクラス B** です。**だから回数上限を 1 回にします** — 1 回で直らなければ、それは A ではなかったということで、人間に渡します。

ここから先は**設計提案**です — 現在のランナーの既定運用は「**外部の自動リランなし**」（[#7](https://qiita.com/rex0220/items/39821af2a79b88de0ed2) のとおり）で、以下は利用者が実装する場合の指針です。自動化するなら 3 つの安全条件を付けます: **①回数上限 1 回**（無限ループ防止）**②遅延を置く**（例: 30 分後）**③自動リランした事実を記録・通知する**（「勝手に再実行されたかも」で人間の判断が壊れるのを防ぐ）。「[#7](https://qiita.com/rex0220/items/39821af2a79b88de0ed2) で自動リトライを禁止したのでは？」と思った方へ — 禁止したのは**原因を見ずにスケジューラが即時再起動すること**です。ここでの自動 resume は、**リトライで直る型と判定できた失敗だけ**を、遅延・回数上限 1 回・記録付きで再実行する別物で、原因を見ない再起動の 3 つの害（無意味な繰り返し・ロック競合・判断の攪乱）をいずれも避けています。

そして重要な点 — **ここに AI は不要です**。判断が機械的なら、ルールで書くべきです。現状でもステータスコード等から機械判定は可能ですが、**構造化された `retryable` 属性はまだ無く、完全な機械判定にはなっていません**。実装方針としての理想は**ランナー自身が「retryable かどうか」を構造化した属性としてログに出力する**ことで（error 欄の文字列判定への依存が消える）、これはランナーの改善候補として検討します。**この属性が入るまでは、自動リランの導入は慎重に**というのが現時点の立場です。

### B. 状態を直す失敗 — 「誰が・何を直すか」のトリアージが本体

再実行では直らない失敗です。直すものによって担当が分かれます:

| 原因 | 直すもの | 直す人 |
| --- | --- | --- |
| 入力データ不良（誤入力・欠損） | 取込元データ | 業務担当 |
| マスター不足（ルックアップ参照先に未登録 等） | マスターデータ | マスター管理者 |
| 想定外データ（設計が予期しない値・形式） | **ジョブ設計そのもの**（SQL 改修 → [#6](https://qiita.com/rex0220/items/a522f7880a5960f033b3) の PR フロー） | 開発者 |
| 認証・設定・基盤 | トークン・環境 | 情シス |

ここで落とし穴が 1 つ。**Exit Code は原因を完全には語りません**。たとえば「ルックアップ参照先に存在しない会社名」は書込時の API エラー = **Exit 3 として現れますが、原因は基盤ではなくマスターデータ**です（[#2](https://qiita.com/rex0220/items/3a1213a596a8c49b67aa) の検証で実際に踏みました）。つまり error 欄の**内容**を読んで表に振り分ける工程が必ず要る — **ここが AI の出番です**（後述）。

なお、データ取込・クレンジング系のジョブは、そもそも設計時に「**止めるか、弾いて続行するか**」を選んでおきます。集計の整合が要るなら ASSERT で全停止、独立レコードの取込なら想定外データを除外して「未処理」として残す**選別続行型**に — 後者なら、業務担当がデータを直せば次回の定期実行が自動で拾い、リラン問題自体が消えます。

### C. 成功して見える誤り — 最も危険なクラス

**業務の運用変更がバッチに反映されていない**ケースです。たとえば月の締め日が 25 日から月末に変わったのに、ジョブは 25 日締めのまま — バッチは Exit 0 で正常終了し、通知も飛ばず、**数字だけが静かに間違い続けます**。#7 の対応表のどの行にも引っかかりません。

対処は「起きてから」ではなく設計です:

1. **業務パラメータの外部化** — 締め日のような「業務側が変えうる値」を SQL にハードコードせず、**kintone の設定マスターアプリに置いてジョブが参照**する。業務変更 = マスターのレコード更新で完結し、SQL 改修が不要になります。変更を「コード」から「データ」へ移す、が原則です。ただし**統制とのトレードオフ**があります — 設定マスターを誰でも直接編集できると、[#6](https://qiita.com/rex0220/items/a522f7880a5960f033b3) の PR レビューを通さずに本番の計算前提が変わります。**変更履歴・編集権限・入力値の検証・承認プロセス**が用意できる場合に限って外部化してください（kintone なら変更履歴とアクセス権、プロセス管理がそのまま使えます）
2. **前提の ASSERT 化** — 「この実行は締め日を過ぎているか」「対象期間の件数が想定レンジ内か」をジョブ冒頭でゲートします（レンジもマスター参照で — ハードコードするとゲートごとドリフトします）。これで早すぎ実行は ABORTED で止まり、**静かな誤りが、音の出る失敗（クラス B）に変換されます**
3. **業務変更の手順に「バッチ影響確認」を 1 行入れる** — ここも AI が使えます（後述）

起きてしまった後の修復には新しい道具は要りません — 正しい設定で再実行すれば冪等上書きで直り、実行し損ねた期間は `--as-of` バックフィルで埋まります。**検知だけが新しい問題で、修復は [#7](https://qiita.com/rex0220/items/39821af2a79b88de0ed2) の仕組みがそのまま使える**わけです。

### D. 成功したが入力が不完全 — リランは「復旧」ではなく「日常操作」

運用ミスでデータの入力が漏れていた・後から訂正が入った、というケースです。ジョブも処理も正しく、**入力が実行時点で揃っていなかった**だけ。ここで視点が変わります — 正常終了したバッチを、業務上の理由でやり直す。それが安全にできるのは冪等 + as-of 固定の直接の帰結です:

- 入力漏れが判明 → 入力してもらう → `--as-of 対象日` で再実行 → 冪等上書きで収束。**エラー対応ではなく、ボタンを押すだけの日常操作**です
- さらに一歩進めた定石が「**再集計ウィンドウ**」— 締め後 n 日間は確定前期間を毎朝バックフィルし続ける設計。冪等だから何度実行しても安全で、**後着データや訂正が人手ゼロで自動反映**され、n 日後に確定扱いにします。実装に新しい構文は不要です — 対象期間が `@MONTH_START()` 〜 `@NEXT_MONTH_START()` のような **as-of 起点の式**で書かれていれば（[#1](https://qiita.com/rex0220/items/893ab4016a5aaf595642) の月次ジョブがこの形）、締め後 n 日間だけ `--as-of 前月基準` の実行をスケジュールに 1 本足すだけで、同じジョブが前月窓を再計算します。「気づいた人が再実行を依頼する」運用を「気づかなくても翌朝直っている」設計に置き換えられます
- 確定済み期間への遡及訂正だけは、承認つきのバックフィル手順に（数字が確定後に動くことの合意は技術でなく業務ルールの問題です）

**変形として、訂正が「上書き」ではなく「レコードの追加」になる業務があります** — 請求先を間違えたときに、誤請求の取消レコードと正しい請求レコードを両方残す、いわゆる赤黒処理です。監査の都合で**間違いを消してはいけない**ので、ここだけは冪等 UPSERT（最終状態を上書きする）の思想が使えません。ただし影響は限定的です:

- **集計する側は何も変わりません** — 元 + 取消 + 正 の 3 レコードを全量再集計すれば正しい数字になるので、上と同じ「次回実行が吸収する」構造がそのまま働きます
- **バッチが訂正レコードを作る場合だけ注意**が要ります。これは UPSERT ではなく INSERT（イベント追記）なので、二重実行が二重計上を生みます。冪等にするには「元レコード ID + 訂正理由」などの**訂正キーを重複禁止フィールドに持たせてキー指定 UPSERT にする**（= 同じ訂正は 1 回しか積まれない）+ 「取消対象が存在し、まだ取り消されていない」ことを ASSERT で確認してから書く、の 2 点セットです

つまり「最終状態を保つデータ」と「イベントを積むデータ」で書込モデルが変わる、というだけの話で、ジョブを書く段階で選べば運用は同じ形に収まります。

## では、AI に何を任せるか — 実演つき

ここまでで役割分担が見えました。**A はルール、C と D は設計**。残る B の「error 欄を読んで、誰が何を直すかを振り分ける」— ここが AI の出番です。

実際にやってみます。[#7](https://qiita.com/rex0220/items/39821af2a79b88de0ed2) の障害ドリルで残った失敗レコードを、**閲覧のみトークン**の Claude に読ませて、トリアージレポートを書かせました。依頼したプロンプトの骨子はこれだけです:

> ログアプリの直近の FAILED / ABORTED レコード（error 欄・ステータス・as-of）を読み、①失敗の分類 ②誰に回すべきか ③影響範囲 ④復旧コマンド ⑤緊急度、を**一次トリアージ**として報告して。判断根拠を添えること。閲覧のみで実行し、書込は行わないこと。

出力がこちらです。入力はログアプリのレコードだけです:

> **障害トリアージレポート（Claude 生成・閲覧のみトークン）**
>
> **対象**: BATCH レコード #191（dev/error_drill/jobs・ABORTED・as-of 2026-08-26T23:44Z）
>
> **分類**: クラス B（状態を直す失敗）> 入力データ不良 — **担当: 業務担当**
>
> **根拠**: error 欄の ASSERT メッセージ「KSQL-FLOW-TEST 案件にマイナス売上があります（actual: 1）」。マイナス売上の案件が 1 件存在し、業務ゲートが書込前に停止した（Exit 2 / ABORTED）。基盤・ジョブ設計の問題ではない。
>
> **影響範囲**: DML 実行前の停止のため**書込ゼロ**。後続の 02_summary.sql は SKIPPED（依存元失敗）。データ破損なし。
>
> **推奨対応**: ①該当案件を特定して売上を修正（入力ミスか実態かは業務判断）②修正後、`run-all dev/error_drill/jobs --profile prod --resume` — as-of は失敗時点（2026-08-26T23:44Z）を自動で引き継ぎます。
>
> **緊急度**: 中 — 直るまで毎朝同じ通知が続きますが、書込前に止まるため被害は拡大しません。

注意点を 1 つ — **AI の分類は最終判断ではなく、ログからの一次トリアージ**です。たとえば「会社コードが存在しない」は、マスター登録漏れ・入力ミス・新規取引先・SQL の参照先誤りのどれでもあり得て、ログだけでは確定できません。レポートは「まずどこに回すか」を速くするための下書きで、確定は受け取った担当者がします。

このレポートの生成に必要なのは**閲覧のみトークンだけ**です。書込権限は一切渡していません — つまり [#2](https://qiita.com/rex0220/items/3a1213a596a8c49b67aa) から積み上げてきたトークン分離（AI には閲覧のみ・書込は人間）を**一切壊さずに**、朝の初動の大半（分類・根拠・影響範囲・推奨コマンド）が自動化できます。ただし閲覧のみトークンが防ぐのは**書込事故**までで、機密性の担保は別問題です — **error 欄やレコードの内容は AI のコンテキストに入ります**。個人情報・機密情報を含み得るジョブでは、[#2](https://qiita.com/rex0220/items/3a1213a596a8c49b67aa) と同じく、利用する AI サービスの規約と社内ポリシーに従って判断してください。

もう 1 つの使い所が、クラス C の予防です。業務変更の連絡文（「来月から締め日を月末に変更します」）と、**ジョブ SQL・config・依存関係（depends_on）・ASSERT・実行スケジュール**を AI に読ませ、**影響のあるジョブとゲートを洗い出させる**（SQL 単体だけ見せると依存先やスケジュールの影響を漏らします） — ドリフトを事後検知するのは AI にも困難ですが、**変更時点の影響分析**は得意分野です。これも閲覧のみで完結します。

## 任せてはいけないもの — 実行の判断

逆に、**リランの実行そのものを AI に自動でやらせることは勧めません**。理由は 2 つ:

1. **トークン分離が壊れる** — resume には書込可トークンが要ります。AI に常時書込権限を渡すことは、この連載が [#2](https://qiita.com/rex0220/items/3a1213a596a8c49b67aa) から一貫して避けてきた構成です
2. **第 3 のリトライ層になる** — [#7](https://qiita.com/rex0220/items/39821af2a79b88de0ed2) の整理は「リトライすべきものはランナー内で済んでいて、外に残るのは人間が判断すべき失敗だけ」でした。AI 自動リランはこの外側にもう 1 つ判断層を足すことになり、「勝手に再実行されたかもしれない」状態は人間の判断を壊します

実行は人間がやります — ただし [#6](https://qiita.com/rex0220/items/a522f7880a5960f033b3) で作ったとおり、その操作は**ブラウザの resume ボタン 1 つ**まで軽くできています。実物がこれです:

![2026-08-27_09h37_33.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/100572/70fa2286-39b8-47e8-a01d-8de7336566dd.png)


AI の診断レポートを読んで、このチェックを入れてボタンを押すのは人間。この分担なら、判断の重さと操作の軽さが両立します。

## まとめ — 診る AI・押す人間・拾う機械

| 層 | 担当 | 対象 |
| --- | --- | --- |
| **拾う** | 機械（ルール） | クラス A のみ — 1 回・遅延・記録付きの自動 resume |
| **診る** | AI（閲覧のみ） | クラス B のトリアージ（誰が何を直すか）+ クラス C の変更影響分析 |
| **押す** | 人間 | 状態の修正・実行の最終判断（操作は resume ボタンまで軽量化済み） |
| **（設計）** | ジョブを書く段階 | 停止型/続行型の選択・パラメータ外部化・前提 ASSERT・再集計ウィンドウ — C と D はここで潰す |

- バッチの失敗は 4 クラス — **通知が来る失敗（A/B）より、正常終了する誤り（C/D）のほうが危険**
- 自動リランしてよいのは「再実行そのものが原因を解決し得る」クラス A だけ。そこに AI は不要（ルールで書ける）
- AI の出番は**診断** — error 欄の内容から「誰が・何を直すか」を振り分ける工程は機械的ルールで書き切れず、**書込権限を渡さずに**自動化できる（ただし error 欄の内容は AI のコンテキストに入るので、データの取扱いは [#2](https://qiita.com/rex0220/items/3a1213a596a8c49b67aa) と同じ基準で）
- 実行の判断と書込権限は人間に残す — 分担は「**診る AI・押す人間・拾う機械**」
