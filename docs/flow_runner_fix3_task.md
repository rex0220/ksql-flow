## タスク A（最優先・正確性の疑義）: v3.69.0 metrics 差分集計の検証

申し送りが指摘する「v3.69.0 での差分集計が機能していなかった可能性」を最初に決着させる。

1. 現行実装の `written_count` / `api_calls` 集計コードを確認し、v3.69.0 の**共有参照 metrics** の下で差分計算が正しく動いていたかを判定する（参照を保持して後から差分を取っていた場合、差分が常に 0 または累積値の二重計上になっていた可能性がある）。
2. 判定結果を必ず報告に明記する: (a) 正しかった（スナップショットを取ってから差分していた等）、(b) 壊れていた — その場合、**既存テスト 87 件がなぜこれを検出できなかったか**の分析と、検出できるテストの追加まで行う。
3. エンジン依存を v3.70.0 へ更新（開発中は `file:../kintone-sql-tools` のまま、互換表とエンジン pin バージョンを更新）。E-5 回答により metrics は**スナップショット**になったため、集計コードを新仕様に合わせ、文単位値のテスト（複数文スクリプトで文ごとの増分が正しい）を追加する。

## タスク B（裁定 Q7）: `last_written_key` の単調性前提の廃止

**エンジン回答**: DML の書込は**キー昇順を保証しない**（E-1 回答）。設計書 5.1-2 の「キー昇順に整列して書き込み、`last_written_key` の単調性を保証する」という前提は成立しない。

**裁定 Q7（Takashi 承認済み — 本書をもって決定）**:

* エンジンへ整列の追加依頼は**しない**（整列は大規模データでメモリ・処理コストを増やす一方、得られるのは「将来の途中再開拡張」の前提だけで、現在の復旧戦略は冪等リラン〈5.1-1〉で完結しているため）。
* `last_written_key` の意味を「復旧ウォーターマーク（単調）」から**「診断情報: 最後に書き込まれたチャンクの最終キー値（順序保証なし）」**へ再定義する。障害時の影響範囲の手がかりという 8.2 の役割は保たれる。
* 設計書 5.1-2 の「キー昇順書き込み」の規定と「途中からの再開に拡張する場合の前提」の記述を削除し、8.2 の `last_written_key` の説明を上記の再定義に書き換える（v2.7 として改訂、付録 C に Q7 を追記）。
* `docs/reviews/decisions.md` に Q7 として記録。

## タスク C（Q3 縮退解除）: チェックポイントをキー値ベースへ

E-1 の `onChunkWritten`（書込成功直後発火・`lastKeyValue` 付き・キー順保証なし）が v3.70.0 で利用可能になったため、裁定 Q3 の期限条件が成立した。

1. チェックポイント記録を `chunk:<n>` から **`lastKeyValue`**（+ チャンク数・処理件数の併記）へ差し替える。Q7 により**順序保証なしの診断情報**として記録する（ウォーターマークとして使うコードを書かないこと）。
2. ログアプリ反映の間引き（25 チャンク / 60 秒）は現行維持。ローカル JSONL は毎チャンク記録を維持。
3. `onChunkWritten` は await 対応なので、コールバック内のログ書込がジョブ実行をブロックしすぎない設計にする（JSONL は同期追記で良いが、ログアプリ反映は間引きタイミング以外では待たせない）。
4. decisions.md の Q3 に「縮退解除済み（v3.70.0 / fix3）」を追記し、設計書 v2.7 と受入基準の「キー値」記述を復活（ただし Q7 の再定義文言で）。
5. 受入テスト: 250 件 UPSERT で 3 チャンク発火・最終キー値が JSONL とログアプリに残ること。チャンク途中失敗時に最後に成功したチャンクのキー値が残ること。

## タスク D: E-2 設計提案 R1 への回答

R1（`previewStatement` 案・質問 5 件）を読み、**ランナーの要件を根拠にした回答文書**を作成してエンジン側へ返す（`../kintone-sql-tools/docs/` 宛て、申し送り形式）。回答で守るべきランナー側の要件:

* 出力は設計書 10.2 の表示に写像できること: 種別ごとの件数（INSERT / UPDATE / DELETE）+ 変更サンプル（キー値と before → after。サンプル上限は既定 5 件・オプションで変更可、を提案）。
* preview の読み取りは実 API を消費するため、**ランナーの単一カウンタ（7.2）で計上できる**こと（fetch ラッパー経由で観測可能なら追加要件なし、と回答して良い）。
* `previewStatement` が ExecutionContext の TEMP TABLE 状態を前提にできること（多段ジョブの途中の DML をプレビューするには、それ以前の文を実行済みのコンテキストが必要。read-only 文は実行し DML だけ preview に差し替える、というランナーの利用計画を回答に明記する)。
* DELETE のプレビュー（削除対象のキー一覧サンプル）も対象に含めること。
* 質問 5 件には全件回答し、判断が割れるものは裁定（Takashi）に上げる。
