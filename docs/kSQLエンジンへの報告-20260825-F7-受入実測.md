## 2. XL 規模（UPSERT 10,000）— **受入基準 1 成立**

ウォームアップ 1 回 + 計測 3 回。**API は全 4 回で 312 回に一致**（決定的）。

| | v3.72.0（8/23 実測） | v3.74.0（native・本実測） |

- 所要時間の短縮は約 3 秒に留まります。事前 GET 200 回の消滅が時間に効きにくいのは、F-5 の A/B 実測（サーバ側処理支配）と同じ構図で、**F-7 の価値は所要時間ではなく API リクエスト数（特に日次上限）**にある、という双方の整理を裏付けています
- SUCCESS・書込 10,000・cleanup 後の残存 0 を確認

## 3. 実測知見 — 適格性判定のフォーム定義取得が +1 回【撤回 — 切り分けの結果、+1 はランナー v0.3.0 の deleted_count フォーム検出でした。正は「返信-20260825-F7-プラス1切り分け」参照】

M の差分が -4 ではなく -3、XL が -200 ではなく -199 だったことから、**native 経路は実行時に対象アプリのフォーム定義を 1 回取得している**と読み取れます（EXPLAIN の `fieldCalls` 0 → 1 と同じ挙動が本実行にもある、という理解。M / XL の両規模で +1 が一致）。通知 §2「効果: 300 → 100」には現れていない消費なので、正確には **UPSERT フェーズ 300 → 101 回**（フォーム込み）です。効果の大勢に影響はありませんが、推定式を厳密に合わせる際の係数として共有します。

## 4. 日次 API リクエスト数の併記（scale-notes 併記ルール）

現行実装は bulkRequest 不使用のため、本報告の API 回数 = HTTP リクエスト数 = kintone の「1 日に実行できる API リクエスト数」の消費です。XL 級ジョブの日次消費が 511 → 約 312 に下がることで、スタンダードコース（1 アプリ 10,000/日）での実行余地が約 1.6 倍になります。
