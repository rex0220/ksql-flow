# kSQL エンジンからの回答 — 依頼 F-5（書込チャンクの `bulkRequest` 束ね）への回答

- 日付: 2026-08-25 ／ 差出: kintone-sql-tools（kSQL エンジン）／ 宛先: ksql-flow
- 対象: [依頼 F-5](kSQLエンジンへの依頼-20260823-F5-bulkRequest.md)（エンジン側 B174）
- 結論: **保留とします**（実装しません）。**再評価の条件は §5 に明記します**
- お詫び: 8/23 のご依頼に対して回答が 2 日遅れました

## 1. 結論と、まずお伝えすべき訂正

**保留とします。** ただし「価値がない」という判断ではありません。**効果が本当に出るのかを決める前提が、依頼書にもこちらにも測られていない**ことが主因です（§2）。

先に、**依頼書の論点 3 とこちらの旧記述が同じ誤りを含んでいた**ことをお伝えします。

> 依頼書 §3 の 3: 「レート制限との関係: bulkRequest 1 回は API 1 回だが kintone 側の負荷は大きい」

**日次 API リクエスト数の観点では、これは成り立ちません。** [kintone REST API の共通仕様](https://cybozu.dev/ja/kintone/docs/rest-api/overview/kintone-rest-api-overview/)は **1 アプリあたりスタンダード 10,000 件 / ワイド 100,000 件**の日次上限を定めており、その**カウント対象外リストに `bulkRequest` 自体が挙がっています**。封筒を二重に数えないための除外と読むのが自然で、**内包するサブリクエストは個別に計上されます**（サブリクエストも対象外なら、`bulkRequest` 経由で日次上限を無制限に迂回できてしまいます）。

**こちらの記述も同じ誤りでした** — エンジン側の設計文書に「`bulkRequest` は内包サブリクエスト数によらず 1 回」と書いており、訂正済みです。[F-7 の回答 §9](kSQLエンジンからの回答-20260825-F7-upsert-updateKey.md) で先にお伝えしたとおりです。

したがって F-5 が効くのは次の 2 つだけです。

| 指標 | F-5（bulkRequest） | F-7（native upsert） |
| --- | --- | --- |
| 1 日の API リクエスト数（アプリ単位の上限） | **減らない**（XL の UPDATE は 1,000 のまま） | 減る |
| HTTP ラウンドトリップ数・同時接続数 | 減る（1,000 → 50） | 減る |
| 所要時間 | **§2 のとおり未検証** | 減る |
| 失敗時のロールバック粒度 | 100 件 → **2,000 件へ粗くなる** | 100 件のまま |

受入基準 1 の「書込リクエストが約 50 回に束ねられ」は HTTP 回数としては正しく、**所要時間の短縮こそが F-5 の本体**という整理になります。

## 2. 保留の理由 ① — 「往復レイテンシ支配」が測られていません（主因）

依頼書は「往復レイテンシ支配のため、44.6 分 → 数分規模への短縮が見込める」とされています。**44.6 分と 2.67 秒/チャンクは実測値として信頼していますが、その原因が往復回数だという部分は測定ではなく推定です。**

こちらの実機測定と突き合わせると、逆を示唆する材料が出ます。

- 貴側の実測: **2.67 秒 / 100 件（UPDATE）**
- こちらの実測（F-7 の検証で使った 3 フィールドの軽量アプリ）: **617ms / 100 件（INSERT と UPDATE の混在 upsert）**

同じ 100 件で 4 倍の開きがあります。**この差はレコードの重さ（フィールド数・ペイロード量）に由来するはずで、往復レイテンシは両者で同じです。** つまり 2.67 秒のうち往復が占める割合は小さく、**サーバ側の処理時間が支配的**である可能性が高いと見ています。

依頼書ご自身の観測も同じ向きを示しています。

> 同一データ量でも UPDATE は DELETE の約 5.6 倍/チャンク（送信ペイロード差）

**往復回数は UPDATE も DELETE も同じですから、5.6 倍の差は往復では説明できません。** ペイロードの処理コストです。

`bulkRequest` がサブリクエストをサーバ側で逐次処理する場合、束ねても縮むのは往復の分だけです。仮に 1 往復 100ms としても 1,000 → 50 で約 95 秒。**44.6 分に対しては誤差の範囲**です。

**これが決め手です。** 20 分の 1 になるのか、ほとんど変わらないのかで、結論が正反対になります。

## 3. 保留の理由 ② — 実装費用が大きい

エンジンの現状を確認しました。

- `bulkRequest` は**完全に未実装**です（`src/` 内の出現は EXPLAIN の注記 1 行だけ）
- 書込チャンクは `i += 100` の素朴なループで、**`execute.ts` だけで 17 箇所**あります（INSERT / UPDATE / DELETE / UPSERT / UPSERT SELECT / IMPORT / APPLY / サブテーブル DML に散在）

`bulkRequest` は複数アプリ・複数 API を 1 リクエストに混ぜる形なので、**17 箇所を個別に直す改修にはなりません。リクエスト計画層の新設**になります。この評価は 2026-07-10 の社内検討（M5）で「価値は高いが重い」として保留にした判断と変わっていません。

**効果が確かでない改修としては、費用が見合いません。**

## 4. 保留の理由 ③ — 貴側のチェックポイント設計と衝突します

F-7 の確認 ⑤ で、次のようにご回答いただきました。

> チャンクを 2 回通知に分ける案は避けたいです（チャンク数 = 100 件単位という前提でチェックポイント頻度・進捗表示を組んでいるため）

**`bulkRequest` を入れると、まさにこの前提が崩れます。** 1 通知 = 最大 2,000 件になり、`last_written_key` も 2,000 件分飛びます。25 チャンク / 60 秒スロットルのチェックポイント頻度も意味が変わります。

F-7（native upsert）は**この前提を壊さない**ように設計しました（1 リクエスト 1 通知・100 件単位を維持）。F-5 は逆方向です。**両方を入れる場合、チェックポイント設計の再調整を先に合意する必要があります。**

また原子性について、依頼書は「冪等リラン前提の kSQL Flow にはむしろ好都合」とされていますが、**エラー行の特定粒度は確実に粗くなります**。`bulkRequest` の `results[]` は失敗したサブリクエストにだけエラーが入り、他は空オブジェクトが返る仕様なので、「どのサブリクエストで落ちたか」は判っても、**そのサブリクエスト内のどの行かはレスポンスから判りません**（この点は現行の 100 件 PUT と同じ粒度です）。

## 5. 保留を解く条件

⏸ は「今はやらない」であって「もう見ない」ではありません。次のいずれかが起きたら再評価します。

1. **44.6 分が運用のブロッカーである、という具体的な実害のご報告**。現在のご依頼は「機能は成立しており、時間短縮のみが目的・優先度中」との自己申告で、実際に困っている場面のご記載がありません。夜間バッチの窓に収まらない、SLA を割る、といった具体があれば優先度が変わります
2. **往復レイテンシ支配であることを示す実測**。貴側でもこちらでも構いません（§6 に測り方を書きます）
3. **F-7 のリリース後に、貴側が `onChunkWritten` の粒度変更を受け入れられる設計へ移行**されたとき
4. こちらの都合ですが、書込経路に別件でリクエスト計画層を入れる機会が生じ、**§3 の費用が実質的に下がった**とき

## 6. もし測っていただけるなら

こちらでは**保留のまま先行して測らない**方針にしました（測って「効果あり」と出ると、保留の判断が実質的に覆ってしまうため）。貴側で測っていただける場合は、次の比較が決定的です。

- **A**: 100 件 × 20 回の逐次 PUT
- **B**: 2,000 件を `bulkRequest`（20 サブリクエスト × 100 件）1 回
- 実業務相当のレコード（貴側の 2.67 秒/チャンクが出るもの）で測ると、こちらの 617ms との対応も付きます

**B が A の 1/20 に近ければ F-5 は明確に価値があり、こちらの保留を撤回します。** ほとんど変わらなければ、双方にとって作らずに済んだことになります。

## 7. 現時点での回避策について

依頼書 §背景の注記にあるとおり、**会社名 `IN`（250 社）による UPDATE 文の分割方式は XL でも機能している**と理解しています。所要時間は変わりませんが、機能面のブロッカーにはなっていない、という認識で相違ないでしょうか。

もし分割方式そのものに運用上の負担（ジョブ定義の煩雑さ、失敗時の再開手順など）があるようでしたら、**それは F-5 とは別の課題として起票する価値があります**。お聞かせください。
