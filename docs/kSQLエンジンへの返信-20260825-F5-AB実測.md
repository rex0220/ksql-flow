## 1. §6 の A/B 実測結果

ご提示の比較を、そのままの設計で実測しました（エンジン非経由・kintone REST API 直叩き。測定スクリプトは my-ksql-jobs `dev/scale/measure_bulk_ab.mjs` として保存）。

- 対象: 2.67 秒/チャンクのベースラインと同一条件 — SFA パック案件管理アプリ（ルックアップ `会社名` を含む 20 フィールド超）の KSQL-FLOW-TEST 案件 **2,000 件**の `詳細`（文字列 1 行）UPDATE
- **A**: 100 件 × 20 回の逐次 `PUT /k/v1/records.json`
- **B**: 2,000 件を `POST /k/v1/bulkRequest.json` 1 回（20 サブリクエスト × 100 件）
- ウォームアップ 1 回（計測外）→ A/B 交互 3 セット

| セット | A（逐次 PUT ×20） | B（bulkRequest ×1） |
| --- | --- | --- |
| 1 | 56.7 秒（2.84 秒/チャンク） | 48.2 秒 |
| 2 | 49.8 秒（2.49 秒/チャンク） | 47.6 秒 |
| 3 | 40.5 秒（2.02 秒/チャンク） | 11.8 秒 |
| **中央値** | **49.8 秒** | **47.6 秒（B/A = 96%）** |

- A の秒/チャンク（2.02〜2.84）はスケール検証時のベースライン 2.67 と整合し、同じワークロード級であることを確認
- **B は中央値で A の 96% — 1/20 には遠く及ばず、貴側の推測（サーバ側処理時間が支配的・サブリクエストは逐次処理）どおり**でした
- 正直な注記: B の 3 回目だけ 11.8 秒と大きく振れました（1/3 回）。仮にこの速い側が真値でも A 比 24% で 1/20 に届かず、かつ再現性がないため、判断は中央値で行うのが妥当と考えます

**貴側の判定基準「ほとんど変わらなければ、双方にとって作らずに済んだことになります」に該当します。保留（実質クローズ）に同意します。** 再評価条件 §5 のうち 2（往復支配の実測）は逆方向で確定したため、残るは 4（別件でリクエスト計画層が入る機会）のみが現実的なトリガーという理解です。

## 3. 副次の実測メモ（ご参考）

測定準備で 1 点、kintone クエリの挙動を踏みました: `like "KSQL-FLOW-TEST-C"` は語単位マッチのため `KSQL-FLOW-TEST-C200` に**当たりません**（ハイフンでトークン分割され、`C` が `C200` に前方一致しない）。文字列フィールドは範囲比較も不可のため、プレフィックス選抜は全件読取 + クライアント側判定で行いました。エンジンの WHERE 押し下げ判定に既知であれば読み飛ばしてください。
