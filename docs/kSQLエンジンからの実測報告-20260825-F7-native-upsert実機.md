確認 6 点のご回答ありがとうございました。すべて反映のうえ、[回答 §7](kSQLエンジンからの回答-20260825-F7-upsert-updateKey.md) で「こちらで測る」とお伝えした項目を実機で測りました。**2 件で設計が変わり、うち 1 件は貴側の公開仕様と受入基準にも関係します。**

## 測定環境

kintone の検証ドメインに専用アプリを作成しました（重複禁止の「文字列（1行）」キーと「数値」キー、および payload フィールドの 3 つ）。API 呼び出し約 50 回。

## 結果

### ① `record` に updateKey フィールドを含めることはできません

新規・更新・同値・別値の 4 ケースすべてで拒否されました。

```
HTTP 400  CB_VA01
errors["records[0].record[key_text]"]:
  「updateKey」に指定したフィールドの値は更新できません。
```

**ただし挿入時のキー値は `updateKey` から入ります。** `record` に payload だけを入れて upsert すると `operation: "INSERT"` が返り、読み戻したレコードにキー値が正しく入っていました。

→ **エンジン側の対応**: native 経路では組み立てた `record` からキーフィールドを除去し、その値を `updateKey.value` に載せます。**結果は現行と等価**で、貴側の SQL の書き方は変わりません（`UPSERT INTO ... (key, ...) ... ON DUPLICATE (key)` のようにキーを列に含める現行の書式のままで動きます）。

### ② ソース内にキーが重複するとリクエストごと拒否されます — **確認 ⑥ の回答に関わります**

```
HTTP 400  GAIA_IQ28
「updateKey」に指定した条件にあてはまるレコードが重複しています。
```

両方が新規でも、既存レコードがある場合でも、**リクエスト全体が失敗**します（部分適用ではありません）。

これで **適用条件⑥（ソース内重複なし）は「実測次第で外せる」どころか必須**と確定しました。貴側の「維持で構いません」というご判断が正しかったことになります。含意が 2 つあります。

**(a) 現行の挙動と違います。** 現行の素の UPSERT はソース内重複を検出しておらず、**「既存あり + ソース重複」は同じレコードに 2 回書いて後勝ちで成功しています**。native ではこれが失敗します。したがってエンジンは**重複を検出したら native に入らず現行経路へ落とす**方針で仕様を起こします（opt-in の趣旨は「速くなるなら速く」であって、意味を変えることではないため）。**opt-in しても結果は変わらず、重複を含む文だけ従来どおりの速度になる**、という形です。

**(b) kintone が見るのは 1 リクエスト内だけです。** 100 件ずつのチャンクに割ったあとで重複を見ても、チャンク境界をまたぐ重複を取りこぼします。エンジンは**ソース全体を通して**検出します（ローカル処理で API 呼び出しは増えません）。

> **ご参考までに**: 貴側の定石（GROUP BY キー集計）なら重複は生じません。非集約 SELECT を書いたジョブがある場合、native を opt-in しても**そのジョブだけ高速化の対象外**になります。速度が読めることを重視されるなら、ソース側でキーが一意になる形に寄せておくと確実です。

### ③ 空文字キーは拒否されます

```
HTTP 400  CB_VA01
errors["records[0].updateKey.value"]: 必須です。
```

適用条件⑤（空文字キーの行がない）の根拠が固まりました。現行経路へ落とします。

### ④ 照合の同値性は現行エンジンと完全に一致します

| ケース | kintone の挙動 | 現行エンジン |
|---|---|---|
| 数値キー `5` に `updateKey.value = "5.0"` | **UPDATE**（レコードは増えない） | 同じ（数値正規化して同一視） |
| 文字列（1行）キー `"001"` に `updateKey.value = "1"` | **INSERT**（別レコードになる） | 同じ（誤同一視しない） |

**受入基準 2「挿入 / 更新の結果件数が現行と同値」は、照合規則の面でも満たせます。**

### ⑤ 安全整数を超える数値キーも扱えます（条件つき）

`numberPrecision` が `digits:30 / decimalPlaces:0` のアプリで、`9007199254740993`（16 桁）と `12345678901234567890`（20 桁）のいずれも登録でき、`updateKey` で正しく UPDATE に照合されました。**キー値を文字列のまま送る限り、JavaScript の数値精度の影響を受けません。**

ただし **アプリの数値精度設定が上限を決めます**。既定の `digits:16 / decimalPlaces:4` は整数部が 12 桁で、それを超える値はそもそも登録できません（「有効桁数を超えています。」）。これは native 化とは無関係な既存の制約ですが、大きな連結キーを数値フィールドで運用される場合はご注意ください（**連結キーは「文字列（1行）」フィールドを推奨します** — 貴側の定石どおりです）。

### ⑥ 混在チャンクの内訳は行単位で取れます — **確認 ⑤ の設計が裏付けられました**

1 リクエストに更新 1 行 + 新規 2 行を混ぜたところ:

```json
{"records":[{"id":"6","revision":"2","operation":"UPDATE"},
            {"id":"7","revision":"1","operation":"INSERT"},
            {"id":"8","revision":"1","operation":"INSERT"}]}
```

**リクエストの並び順どおりに返ります**（公式仕様どおり）。したがって:

- `onChunkWritten` の `records` 内訳（insert / update 件数）は**正確に出せます**
- `lastKeyValue`（ソース順の最終キー）も**現行と同じ意味で維持できます**
- ご希望の案①（`operation` に混在値を足す・分割通知はしない）が**そのまま実現できます**

## 仕様への反映

上記を踏まえ、適用条件は次の 6 つで確定します。**すべて満たしたときだけ native、1 つでも欠ければ現行経路**です。

1. クライアントが新しい書込メソッドを実装している（同梱 `createKintoneClient` は対応します）
2. 実行オプションで opt-in されている（既定 OFF）
3. キーが単一・重複禁止・「文字列（1行）」または「数値」
4. `CHECK` / `APPLY` を伴わない素の UPSERT（IMPORT 由来を除く）
5. 空文字キーの行がない（③）
6. ソース全体を通してキーが一意（②）

**4 について 1 点補足します。** 貴側の①のご回答（「dialect 1 は CHECK を公開構文に含めていない」）は貴側の公開仕様の話で、**エンジン側は dialect 1 でも `CHECK` 付き UPSERT を受理します**（parser の dialect 1 拡張は純加法で、既存構文を制限していません）。利用者が `CHECK` を書いた場合はその文だけ現行経路に落ちるだけで、結果は正しいままです。この fallback はテストで固定します。
