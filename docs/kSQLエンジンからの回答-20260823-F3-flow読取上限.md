## 1. 結論: 案 A は実装済みでした

「`/flow` の公開オプションに読取上限を変更する手段が見当たらない」は、**こちらの伝達漏れ**です。次の 2 つが v3.69.0（`/flow` 公開時）から存在し、公開パッケージの `dist-flow/flow-library/publicTypes.d.ts` にも出ています:

- `createExecutionContext` の options: **`maxRecords`**（文単位の読取候補行数上限・`executeStatement` / `previewStatement` が同一コンテキストで共有）
- `explainScript` の options: **`maxRecords`**

作ったのに README にも言語リファレンスの「入口ごとの `maxRecords` 既定値」表にも載せず、公開面から渡すテストも書いていませんでした。見つからないのは当然で、貴側の調査に落ち度はありません。スケール検証 L 段階は**現行版のまま**進められます。

## 2. 実測（v3.72.0・公開面テスト 6 ケースで固定）

エンジン repo に `src/flow-library/__tests__/b172MaxRecordsPublicSurface.test.ts` を追加し、`$id` シーク＋`limit/offset` ページングを尊重するモックで確認しました（全 green）:

| ケース | 結果 |
|---|---|
| 未指定・10,001 件の単純 GROUP BY | `FetchAllLimitError` で明示停止＝**既定 10,000 は不変**（受入基準 2） |
| `maxRecords: 10`・25 件 | 明示停止＝下げ方向も効く（配線の証明） |
| `maxRecords: 25000`・10,001 件の単純 GROUP BY | **完走・集計値も正**（受入基準 1 のモック版） |
| `maxRecords: 25000` のみ・10,001 件を `#t` へ実体化 | **実体化で停止**（→ §3 参照） |
| `maxRecords: 25000` + `tempTableMaxRows: 25000` | temp 経由でも完走 |
| `explainScript` に `maxRecords: 25000` | 受理・計画生成（受入基準 3 の explain 面） |

受入基準 4（dialect 0 の CLI / MCP / プラグインの既定不変）: このオプションは呼び出し単位で、他面の既定解決には触れません。受入基準 1 の「実データ 20,000 件」はモックでの確認です — 実機は L 段階そのものが本検証になります。

## 3. 重要 — `tempTableMaxRows` も揃えてください（依頼書が見ていない穴）

一時テーブルの実体化には `maxRecords` と**独立の** `tempTableMaxRows`（既定 10,000・1 テーブルあたり・超過は truncate 指定でも常にエラー）が掛かります。**`maxRecords` だけ引き上げると、`#t` へ 10,000 行超を実体化する文（スナップショット等）で失敗点が移動するだけ**です（§2 の 4 行目が実測）。

- L 段階の推奨設定: **`{ maxRecords: 25000, tempTableMaxRows: 25000 }`**（`tempTableMaxRows` は貴ランナーが既に渡しているオプションです）
- `limits.maxReadRows` を config に追加する際は、`tempTableMaxRows` も同じ源から揃えることを推奨します
- エンジン側で両者を**自動連動はしません**。守る資源が違います（`maxRecords`＝1 文の読取候補行数・API 消費／`tempTableMaxRows`＝同時最大 16 テーブルに累積するメモリ）。連動させると `maxRecords` の指定が黙って最大 16 倍のメモリ保持を許す形になり、fail-closed の設計に反するためです

## 4. 提案仕様との差分（未実装のまま）

- **1〜200,000 のハード上限（範囲外の設定エラー）は未実装**です。現行はどの面も正の整数なら受理します（200,001 も通ります）。採否は検討中 — 採る場合は `tempTableMaxRows` にも同じ検証を対称に入れます（読取側だけ塞ぐ片手落ちにしない）。受理していた値を拒否に変える変更は純加法でないため、入れる場合も別途明示して出します。**ランナー側で `maxReadRows` に上限検証を掛ける分には何の差し支えもありません**（むしろ推奨）
  - **【追記 2026-08-23・採否確定】エンジン側は見送りとしました**。理由の要点: 200,000 という線は貴仕様書のインメモリ想定であってエンジンが測った境界ではなく、全利用面共通のハード上限として課す根拠がないこと、行数はメモリの代理変数として不正確なこと（レコード幅に依存）、既定 10,000＋明示エラーで fail-closed は既に成立していることの 3 点です。**過大指定のガードは貴側の `limits.maxReadRows` 検証を正とします**（本節の推奨どおり）。過大指定による OOM の実例が出た場合は、行数でなくメモリ見積りベースの警告として再検討します
- 超過時のエラーは現行のまま（`code: "FetchAllLimitError"`・上限件数と対処を含む文面）。「引き上げ方法のヒント」の文言改善は文書化と合わせて検討します
- **案 B（単純 GROUP BY のページ逐次集約）は保留のまま台帳（B172）に残します**。仕様書 11 章を「将来対応（現状は maxReadRows で明示引き上げ）」へ改める方針（依頼書 §補足）は妥当です

## 5. 受理範囲と保証範囲（20 万件の扱い）

- 読取経路は `$id` シーク方式で kintone の offset 上限 1 万の壁を回避しており、**件数に構造的な上限はありません**
- ただし fetch-all 方式のため候補行は全件メモリに載ります。**20 万件域のエンジン実測は存在しません**。「20 万行 / 1GB」「1.5KB/件」は貴仕様書の想定・概算値です
- 提案の 200,000 は「受付を拒否する線」であって動作保証ではない、という三段の整理（サポート目安 10 万／10 万超〜20 万は動くが保証外／20 万超は分割）はエンジン側の理解とも一致します。**L 段階 → 10 万段階の実測（所要時間・メモリ・API 消費）はぜひ共有してください** — エンジン側文書に「実測済み範囲」として反映します
