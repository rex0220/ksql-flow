# kSQL エンジンからの回答 — 依頼 F-7（UPSERT の `updateKey` + `upsert: true` 採用）への回答

- 日付: 2026-08-25 ／ 差出: kintone-sql-tools（kSQL エンジン）／ 宛先: ksql-flow
- 対象: [依頼 F-7](kSQLエンジンへの依頼-20260825-F7-upsert-updateKey.md)（エンジン側 B173）
- 対応バージョン: **未実装**。現行 v3.72.0 は read-then-write のままです
- 状態: **起票・検算まで完了、仕様は未着手**。§6 の 6 点をご確認いただいてから仕様を起こします

## 1. 結論

**方向としては採ります。ただし「素の UPSERT に限った、能力検出付きの opt-in」になる見込みです。**

依頼書の試算（事前 GET 200 回が消え、UPSERT フェーズが約 100 回になる）は、**適用条件を満たす経路では実測どおり成立します**。一方、実装を測った結果、依頼書が前提としていなかった制約が 3 つ出ました:

1. **事前 GET は「キー存在判定」だけの用途ではない経路がある**（§3）— CHECK を伴う UPSERT では外せません
2. **UPSERT モードは「アプリのレコード追加権限」を追加で要求します**（§4）— 既定 ON にすると、いま動いている更新専用フローが壊れ得ます
3. **公開クライアント契約の変更になります**（§5）— 貴側が `FlowKintoneClient` を自前実装している場合、貴側の実装にも波及します

**貴側にとって即座に効く朗報が 1 つあります**（§2 の 2）: 挿入/更新の内訳は `revision` からの推測ではなく、**レスポンスの `records[].operation` で厳密に取れます**。受入基準 2 は確実に満たせます。

**また、本件の相対的な価値は依頼書の見立てより高いです**（§9）: kintone の「1 日に実行できる API リクエスト数」（アプリごとの上限）を減らせるのは **F-7 だけ**で、F-5（bulkRequest）はこの指標を減らしません。

## 2. 依頼書の事実主張の検算

エンジン実装（v3.72.0）と kintone 公式文書の両方に当てました。

| 依頼書の主張 | 検算結果 |
|---|---|
| 現行は read-then-write（事前 GET・50 キー/リクエスト） | **正しい** |
| XL の事前 GET は 200 回（10,000 ÷ 50） | **正しい**。正確な式は `ceil(非空の distinct 第 1 キー数 / 50) + 空文字を含む distinct 複合キー数`。キー値が全件ユニークで非空なら 200 回ちょうどです。**空文字キーの行だけは束ねられず 1 行 1 GET** になります |
| 書込は 100 回 | **ほぼ正しい。現行は最大 101 回**です。新規と更新を別のリクエスト列に流すため（POST 先・PUT 後）、両方が端数（例 5,001 + 4,999）だと 51 + 50 = 101 回になります。native 化すると常に `ceil(総件数/100)` = 100 回です |
| 事前 GET が UPSERT の API 消費の 2/3 | **正しい**（200 / 300） |
| `updateKey` の要件と貴側の制約（単一・重複禁止・文字列1行/数値）が一致 | **正しい**。dialect 1 は KSQL1301〜1303 で静的検証と実行直前の両方で fail-closed です。ただし **dialect 0（MCP / CLI / プラグイン）は無制約**で、複合キーも非ユニークキーも通ります（§4 の論点 4） |
| 内訳は `records[].revision`（1 なら新規）で判別できる想定 | **推測が外れており、実際はもっと良い**。`PUT /k/v1/records.json` のレスポンスに **`records[].operation`（`"INSERT"` / `"UPDATE"`）が含まれます**。件数の分離は推測ではなく公式プロパティで確定できます |

## 3. 適用範囲 — 「素の UPSERT」に限られます（最重要）

エンジンで UPSERT のキー照合 GET を張っている箇所は 6 か所あり、**native に置き換えられるのは 2 か所だけ**です。

| 経路 | 事前 GET の用途 | 置換 |
|---|---|---|
| 素の `UPSERT ... VALUES` | 分岐と書込先 `$id` のみ | **可能** |
| 素の `UPSERT ... SELECT` | 同上 | **可能**（XL はこちらのはず） |
| **`CHECK` / `VALIDATE ONLY` / `ON ERROR SKIP` を伴う UPSERT** | 分岐に加えて、**行が新規か更新かで検証の内容が変わります**（新規行だけ「値を指定していない必須フィールド」「既定値の妥当性」を検査する） | **不可**。書く前にモードが判らないと `ERR_REQUIRED` 等を出せず、**検証が静かに緩みます** |
| `APPLY` を伴う UPSERT | 既存レコードの値そのものが入力（patch の計算元） | **不可** |
| JSON サブテーブル `IMPORT` | 得た `$id` でさらに `$revision`（楽観ロック）と既存サブテーブル行を読む | **不可** |
| dry-run（`previewStatement`） | before/after の既存値取得が本体 | **対象外**（依頼書 §3 の 1 に同意） |

→ **確認 ①（§6）: XL 相当のスクリプトで、UPSERT 文に `CHECK` を付けていますか。** 付いている場合、その文は native 化の対象外になり、依頼書の受入基準 1 はそのままでは成立しません。

## 4. 設計上の論点への回答（依頼書 §3）

### 1. dry-run は対象外 — 同意します

差分プレビューは既存値の読取が本体で、GET を外す余地がありません。

**ただし 1 点、貴側の推定式に影響します。** dry-run が返す `estimatedWrites` は**本実行の予測値**なので、本実行が native になれば `ceil(insert/100) + ceil(update/100)` から `ceil((insert + update)/100)` へ変わります。依頼書 §3 の 1 にある「dry-run の API 消費は現行と同一」は**読取については正しく、`estimatedWrites` については変わります**。推定式 7.2 / 10.2 の追随修正は、貴側の想定どおり必要です。

### 2. insert / update 件数の分離 — 確実に可能です

`records[].operation` が `"INSERT"` / `"UPDATE"` を返します（§2）。内訳レポートの扱いを協議する必要はありません。`revision = 1` からの推測でも実は当たります（更新は必ず 2 以上になるため）が、公式プロパティがあるのでそちらを使います。

### 3. 権限要件の変化 — **変わります。運用上の確認をお願いします**

kintone 公式文書は UPSERT モードについて、通常の更新に必要な権限（アプリのレコード編集権限・対象レコードの編集権限・対象フィールドの編集権限）に加えて **「アプリのレコード追加権限」も必要**と明記しています。

現行エンジンは**挿入対象が 0 件なら POST を一度も発行しません**。つまり **追加権限のない API トークンでも「結果的に全件が更新に落ちる UPSERT」は成功していました**。native に切り替えると、同じスクリプトが権限エラーで落ちます。

エンジンはトークンの権限を事前に知る手段がないため、**fail-closed の検査を前倒しできません**（実行時エラーとしてしか出せません）。これが「既定 ON にはしない」と判断している主因です。

→ **確認 ③（§6）: 運用中の API トークンにレコード追加権限は付いていますか。更新専用で追加権限を落としているフローはありますか。**

### 4. 多重ヒット解決規則の廃止 — dialect 1 に限れば認識どおりです

「重複禁止が前提なので多重ヒットは起こり得ない」は **dialect 1 では正しい**です（重複禁止・型・単一キーを静的検証と実行直前の両方で fail-closed）。

**ただし dialect 0 では成り立ちません。** MCP / CLI / プラグインの UPSERT は複合キーも非ユニークキーも受け付け、そこでは現行の「多重ヒット時は最大 `$id`」規則が実際に働いています。したがって native 経路は**キーが単一・重複禁止・文字列（1行）/数値である場合にだけ**選びます。この判定は**追加の API 呼び出しなしにできます**（両経路とも既にフォーム定義を読んでいるため）。

なお、貴側が独自の schema resolver を渡していて `isUnique` を省略している場合は、**「不適格」として現行経路へ落とします**（`isUnique === true` を要求します）。

### 5. 適用範囲 — opt-in を推します

既定 ON は論点 3 の権限退行があるため採りません。dialect 0 / 1 とは直交にします（判定材料はフォーム定義であって方言ではないため、dialect 0 でも条件を満たせば使えます）。

現時点の見立ては、次の 6 条件すべてを満たすときだけ native、そうでなければ現行経路へ自動的に落ちる形です:

1. クライアントが新しい書込メソッドを実装している（§5）
2. 実行オプションで opt-in されている
3. キーが単一・重複禁止・文字列（1行）または数値
4. `CHECK` / `APPLY` を伴わない素の UPSERT（IMPORT 由来を除く）
5. 空文字キーの行がない
6. ソース内に同一キーの行が複数ない（§7 の実機確認次第で外せる可能性あり）

## 5. 公開クライアント契約の変更になります

現行の書込口は `putRecords({app, records: [{id, revision?, record}]})` で、**戻り値を捨てています**（`Promise<void>`）。native upsert には `upsert: true` と `records[].updateKey` を渡す口が要り、内訳を取るにはレスポンス本体が要ります。つまり **`FlowKintoneClient` という公開型の変更**です。

`putRecords` の型を変える（＝貴側の実装を壊す）のではなく、**任意メソッドを 1 つ足して「実装があれば native、なければ現行経路」とする純加法の形**を考えています。同梱の `createKintoneClient` をお使いであれば、こちらの更新だけで済みます。

→ **確認 ②（§6）: `FlowKintoneClient` は自前実装ですか、同梱の `createKintoneClient` ですか。**

### `onChunkWritten` に互換設計が必要です

`FlowChunkWrittenInfo.operation` は `INSERT` / `UPDATE` / `DELETE` の 3 値に閉じており、**native の 1 チャンクは INSERT と UPDATE が混在するため現行の型では表せません**。また `lastKeyValue` は「単一キー UPSERT でキー値を特定できる場合のみ」設定される値で、**まさに native が狙う形**です。

決めるべきことが 3 つあります（①混在を表す値を足すか、チャンクを分けて 2 回通知するか ②`records` を内訳で返すか ③`lastKeyValue` の意味を維持するか）が、**貴側の使い方が決まれば選べます**。

→ **確認 ⑤（§6）: `onChunkWritten` をチェックポイント／進捗保存／再開に使っていますか。使っている場合、`lastKeyValue` に依存していますか。**

## 7. こちらで実機確認する項目（貴側の作業ではありません）

仕様確定前に、公式文書に書かれていない挙動を測ります:

1. `record` に updateKey フィールド自体を含めてよいか（含められない場合、挿入時にキー値が `updateKey.value` から入ることの確認も）
2. ソース内にキー重複があるときの挙動（同一 100 件チャンク内と、チャンク境界をまたぐ場合を分けて）
3. 空文字キーの扱い
4. 数値キーの表記ゆれ（`"5.0"` と `"5"`）の照合、および JavaScript の安全整数を超えるキー値
5. 部分失敗の残り方（2 チャンク目を意図的に失敗させ、確定済みの範囲と再実行時の収束を確認）

**5 は現行との主要な互換差です。** 現行は「新規を全部 → 更新を全部」の順なので、途中失敗時は「新規は入った / 更新は入っていない」と読めました。native はソース順の混在チャンクになるため、**確定済みの範囲がソース順の prefix**に変わります。冪等性（受入基準 4）は維持されますが、途中失敗からの再開の考え方は変わります。

## 9. F-5（bulkRequest）との関係 — **効く指標が違います**

**【重要・当方の認識訂正】`bulkRequest` は「1 日に実行できる API リクエスト数」を減らしません。**

kintone の[共通仕様「1 日に実行できる API リクエスト数」](https://cybozu.dev/ja/kintone/docs/rest-api/overview/kintone-rest-api-overview/)は、アプリごとに**スタンダード 10,000 件 / ワイド 100,000 件**の上限を定めています。そのカウント対象外リストに **`bulkRequest`（複数アプリのレコード操作を一括処理する）自体が含まれています**。これは封筒を二重に数えないための除外であり、**内包するサブリクエストは個別にカウントされる**と読むのが自然です（サブリクエストもカウント対象外なら、`bulkRequest` 経由で日次上限を無制限に迂回できてしまいます）。

したがって 2 つの依頼は**効く指標が違います**:

| 指標 | F-7（native upsert） | F-5（bulkRequest 束ね） |
|---|---|---|
| **1 日の API リクエスト数**（アプリ単位の上限） | **減る**（XL で 300 → 100・事前 GET 200 回が消える） | **減らない**（サブリクエストが個別に計上される） |
| HTTP ラウンドトリップ数・同時接続数・所要時間 | 減る（同じく 300 → 100） | 減る（書込 100 回 → 5 回） |
| 失敗時のロールバック粒度 | 100 件単位のまま | **100 件 → 2,000 件へ粗くなる** |

**日次上限に効くのは F-7 だけです。** 依頼書の「併用時の効果が最大」は所要時間・接続数については成立しますが、**API リクエスト数の削減という観点では F-7 単独と変わりません**。XL（読取 10 万 → UPSERT 1 万）でジョブ全体が 511 → 約 311 回になるという試算は F-7 のみで達成され、F-5 を重ねても**日次カウント上はそこから減りません**。

貴側の `verification/scale-notes.md` が数えている 511 回は HTTP リクエスト数だと理解しています。**日次上限の消費を別指標として併記されると、どちらの依頼がどの制約を外すのかが読み取りやすくなります**（スタンダードコースなら 1 アプリ 10,000 件/日なので、XL 級のジョブを 1 日に何本回せるかが直接効いてきます）。

なお `bulkRequest` の実行可能 API には「複数のレコードを更新する」が含まれるため、**`upsert: true` 付き payload も通る見込み**で、両者の技術的な併用自体は可能です。実機確認は F-5 の検討時にまとめて行います（本件の採否は F-5 の有無で変わりません）。

**この点は当初こちらが「`bulkRequest` は内包サブリクエスト数によらず 1 回」と記録しており、誤りでした**（エンジン側 `docs/flow_dialect1_engine_task.md` §2.8 に訂正を入れます）。F-5 の回答時に、この前提で効果を見積もり直します。
